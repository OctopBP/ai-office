# Пакеты агентов

Здесь лежит то, из чего в офисе заводится роль. Пакет — это **плагин Claude
Code с манифестом офиса**: имя папки — имя пакета, `@область/имя`.

```
packages/
  default-office.json            с каких пакетов начинается новый офис, по порядку
  @office/<роль>/                наши пакеты
    .claude-plugin/plugin.json   имя плагина, версия, описание — формат Claude Code
    agent.json                   манифест офиса: роль, модель, инструменты, скилы
    brief/ru.md, brief/en.md     системный промпт роли по языкам
    skills/<навык>/SKILL.md      навыки — формат Claude Code
```

Формат плагина не наш намеренно: пакет ставится и работает в обычном Claude
Code без офиса вовсе (роль он там не увидит, скилы — увидит), а у плагинов уже
есть маркетплейсы. Что офис из плагина берёт и чего не берёт — ниже.

Спека, ради которой всё это заведено, — маркет агентов:
`docs/design/agent-market/spec.md`. Здесь описано то, что уже сделано (фазы 0–2).

## Пакет, роль, сотрудник

```
Пакет ──────► Роль офиса ──hire──► Сотрудник
(папка,       (пакет + разница    (живая сессия,
 версия)       этого офиса)        стол, задачи)
```

- **Пакет** неизменяем и ничей внутри офиса: один пакет может стоять в десяти
  офисах.
- **Роль** — ссылка на пакет плюс **разница** с ним: человек поменял модель на
  подешевле, дописал в бриф абзац про свой проект. Разница хранится отдельно
  (`Role.package.overrides`, `briefExtra`), а роль всегда **считается заново**
  из пакета: так поправленный бриф или новая версия доезжают до уже заведённого
  офиса, а правки человека остаются.
- **Сотрудник** — как и был: нанимается в роль.

Роль **без** пакета тоже бывает: заведённая из формы или отвязанная от пакета.
Она целиком лежит в сохранении офиса, бриф правится напрямую, обновлений
пакета она не получает.

## `agent.json`

```jsonc
{
  "schema": 1,                       // версия схемы манифеста, не пакета
  "name": "@office/backend",         // @область/имя; область обязательна
  "kind": "agent",                   // задел под пакет-команду; сейчас только agent

  "title":   { "ru": "Backend разработчик", "en": "Backend developer" },
  "summary": { "ru": "…", "en": "…" },
  "tags": ["code", "backend"],
  "color": "#3b82f6",
  "emoji": "⚙️",
  "look": "",                        // внешность из shared/looks.ts; пусто — подберёт офис
  "manager": false,                  // пакет менеджера; такой в офисе один
  "maxInstances": 3,
  "docsDir": "docs/design",          // папка артефактов у ролей, работающих не кодом
  "license": "MIT",

  "runtime": {
    "engine": "claude-code",         // единственный движок сегодня
    "model": "opus",                 // алиас (opus / sonnet / haiku) или полный id
    "tools": ["Read", "Edit", "Bash"], // нет поля — все встроенные
    "permissionMode": "ask-risky",   // предложение, не приказ: агент → роль → офис
    "isolate": true,                 // своя ветка и worktree на задачу
    "maxTurns": null,                // null — лимит офиса
    "mcp": ["figma-bridge"]          // серверы каталога, на которые роль подписана
  },

  // То, что раньше лежало в pack.json — см. «Скилы» ниже.
  "skills": [], "builtin": [], "use": [], "servers": [],

  "requires": { "office": ">=0.6", "env": ["FIGMA_TOKEN"], "network": true }
}
```

Что здесь важно:

- **Версия — в `plugin.json`**, где её ждёт Claude Code. Второго поля версии
  в пакете нет: два разъехались бы при первом обновлении.
- **Модель — алиасом.** Полные id меняются с каждым поколением, и пакет,
  прибитый к `claude-sonnet-4-5`, через год не запустился бы. Алиас разрешает
  офис (`src/shared/models.ts`); полный id проходит как есть.
- **Бриф — файлами**, `brief/<lang>.md`. Язык берётся из настроек офиса, нет
  своего — английский. Хвостовые переводы строк снимаются.
- **`permissionMode` пакет может предложить, но не навязать**: режим доступа —
  решение владельца машины.
- **`requires` — витрина, не механизм**: честный список того, без чего агент
  не работает. Карточка пакета в маркете показывает его до найма.

Название и бриф менеджера (`manager: true`) переопределить нельзя: на этой
роли держится раздача задач.

## Что офис берёт из плагина и чего не берёт

| Часть плагина | Офис |
|---|---|
| `skills/` | берёт — это текст, который читает модель |
| `.mcp.json` | не читает (`skipMcpDiscovery`); серверы — только через `servers` и каталог |
| `hooks/` | **не берёт**: хук — произвольная команда, выполняемая молча |
| `agents/` | не берёт: сабагент — ещё один промпт с инструментами мимо ролей офиса |
| `commands/` | не берёт: команд у сотрудника нет, у него задачи |

Валидатор предупреждает, если в пакете лежит то, что офис проигнорирует.

## Скилы

Бриф и скил делятся не по важности, а по цене и по времени чтения.

**Бриф** уезжает в системный промпт целиком и платится токенами в каждой
сессии роли. В нём — обязанности и границы: за что сотрудник отвечает, чего
не делает, что считается сделанной работой.

**Скил** лежит на диске. Модель постоянно видит только его описание и читает
целиком лишь тогда, когда дело дошло до этого навыка. В нём — подробная
инструкция к одному делу. Отсюда правило: **«как пользоваться инструментом» —
это всегда скил.**

Поля манифеста про скилы — те же, что были в `pack.json`:

- `use` — пути к уже установленным плагинам (`~` раскрывается, `*` в последнем
  сегменте берёт старшую версию). Чужие наборы **не копируются**, а
  подключаются ссылкой: у готовых скилов свои условия распространения, и
  раздавать их файлами из своего репозитория нельзя. Прежде чем сослаться на
  чужой набор, прочитайте его целиком: это инструкции, которые исполнит ваш
  агент.
- `skills` — отбор из найденного: у большого чужого набора роли обычно нужна
  половина, а каждый скил платится описанием в контексте всех её сессий.
- `builtin` — встроенные скилы самого агента (`design`,
  `artifact-capabilities`, `dataviz`…), поимённо. Поле не лишнее: офис
  перечисляет скилы сессии по именам, а такой список **заменяет** умолчание
  «все найденные» — роль со своим пакетом без этого поля разом теряла бы всё
  встроенное. На диске имена не проверяются: опечатка стоит одного молча
  пропавшего навыка.
- `servers` — серверы, без которых навыки пакета бесполезны. Это **просьба, а
  не подключение**: офис показывает её в каталоге («Настройки → Инструменты»)
  вместе с командой, которая будет запущена, а добавляет сервер человек.
  Сервер с замечанием (например, с токеном, записанным в значении переменной)
  не предлагается вовсе. Тот, что в каталоге уже есть, не показывается.

Скил, которому нужен инструмент, требует и подключения: навык про Figma в
пакете, у которого нет `figma-bridge` в `runtime.mcp`, хуже отсутствия навыка.
Встроенные инструменты выдаёт офис (`runtime.tools`), а не скил.

## Язык

Навыки пишутся по-английски, хотя офис говорит по-русски: скил читает модель,
а офис бывает и англоязычным, и русский текст навыка тянул бы ответы на
русский в английском офисе. Бриф — по языкам, файлами.

## Оверрайды и обновление

Правка роли из формы у роли с пакетом ложится в разницу с ним:

- короткие поля (модель, режим, лимиты, внешность, репозиторий, подписки) —
  оверрайд по полю; поле, вернувшееся к умолчанию пакета, из разницы уходит;
- бриф пакета **неприкосновенен**. Своё дописывается в приписку
  (`briefExtra`), которая клеится снизу и никогда не конфликтует с обновлением
  пакета. Кому нужно переписать роль — «Отвязать от пакета»: роль становится
  обычной, без ссылки, и дальше её можно экспортировать как свой пакет.

Сохранения старше пакетов привязываются сами при подъёме: роль, совпавшая с
пакетом, — без оверрайдов; отличающаяся — с разницей; роль с переписанным
брифом остаётся без пакета, как и была (форк). Пакет, пропавший с диска, роль
не роняет: она поднимается из сохранения, а ссылка ждёт, пока пакет вернётся.

## Маркет: реестр, кеш, установка

Окно «Маркет агентов» в оболочке показывает три источника одной витриной:

- **встроенные** — пакеты из этой папки, `@office/*`; обновляются вместе с
  офисом и отдельно не ставятся;
- **реестр** — `registry/registry.json` (или адрес/путь из `OFFICE_REGISTRY`):
  список пакетов со ссылками на репозитории, путями внутри них, версиями с
  коммитами и уровнем доверия (`official`, `verified`, `community`);
- **по ссылке** — репозиторий, который человек добавил сам: адрес на GitHub,
  адрес папки в нём (`/tree/<ветка>/<путь>`), короткое `owner/repo#путь` или
  путь к репозиторию на диске. Реестр такой пакет не видел, и карточка это
  показывает.

Установка кладёт пакет в **кеш на машине** — `~/.office/packages/@область/имя/версия/`
(переопределяется `OFFICE_PACKAGE_CACHE`). Версии не перезаписываются; рядом
лежит `.office-lock.json` с репозиторием, путём, коммитом и отпечатком дерева.
Ставится всегда **по коммиту**: из реестра — по записанному там, по ссылке —
по коммиту старшего тега версии (`<пакет>@1.2.0` в монорепозитории, `v1.2.0`
у одиночного), а нет тегов — по ветке по умолчанию. Сама установка ничего не
запускает: это клон без рабочей копии, выемка папки и та же проверка, что у
встроенных.

**Установка и найм разведены.** Разрешения пакета — модель, инструменты,
серверы с командами запуска, переменные окружения, сеть, скилы и бриф —
читаются из манифеста, а он есть только у установленного пакета. Поэтому
карточка неустановленного пакета из реестра знает лишь то, что в реестре;
«Установить» → посмотреть, что просит → «Нанять». Найм заводит роль с ссылкой
на пакет (с источником: репозиторий, путь, коммит) и первого сотрудника; если
роль из этого пакета в офисе уже есть, нанимает в неё ещё одного.

**Обновления** — руками. «Проверить обновления» смотрит реестр, а потом теги
репозитория у каждой роли с источником; найденное показывается на карточке, и
«Обновить» ставит новую версию в кеш и переводит роль на неё — оверрайды и
приписка остаются. Живых сессий это не касается: новая версия достаётся
следующей задаче.

Роль, чей пакет пропал из кеша (почистили `~/.office`), поднимается из
сохранения и ждёт, пока пакет вернётся, — см. «Оверрайды и обновление».

## Свой пакет: от роли до реестра

Три способа сделать пакет, от простого к дешёвому:

1. **Экспорт из офиса.** Собрали роль в форме — модель, инструменты, бриф,
   скилы в `employees/<роль>/` — и в форме роли жмёте «Экспортировать в
   пакет»: имя `@область/имя` и папка (пусто — `agents/<имя>` в проекте офиса).
   Получается папка по этому формату с заполненным манифестом, брифом
   целиком, скилами и заготовкой стенда. Экспорт — форк: ссылки на исходный
   пакет в результате нет, дальше он живёт сам.
2. **Заготовка:** `npm run office-agent -- init <папка> --name @область/имя --title "…" --lang ru`.
3. **Руками**, по формату выше.

Инструменты автора — `office-agent`:

```
npm run office-agent -- validate <папка>          # схема, plugin.json, скилы, секреты, лишние части плагина
npm run office-agent -- bench <папка> [n]         # стенд по bench/cases.json — стоит токенов
npm run office-agent -- publish <папка> --registry registry/registry.json --write --tag
npm run office-agent -- registry-check registry/registry.json [--fetch]
```

**Стенд** едет внутри пакета: `bench/cases.json` — на каких запросах агент
обязан открыть какой скил (`expect`) и на каких не должен (`avoid`). Прогон —
живые сессии, всё, кроме безопасного чтения, отклоняется; меряется
срабатывание, а не качество работы.

**Публикация** в фазе 2 — запись в реестр: имя, репозиторий (из `origin`,
ssh переписывается в https), путь от корня, версия из `plugin.json` и коммит
HEAD. `--tag` ставит тег версии на HEAD (`<пакет>@1.2.0` в монорепозитории,
`v1.2.0` у одиночного), `--write` вписывает запись в файл реестра. Дальше —
pull request в репозиторий с реестром.

**Правило областей:** `@alice/*` ставится только из `github.com/alice/…`,
`@office` зарезервирована за этим репозиторием. Проверяет `registry-check`,
а в CI (`.github/workflows/registry.yml`) он же с `--fetch` достаёт каждую
старшую версию по её коммиту и сверяет имя и версию пакета — PR в реестр с
неверной записью не пройдёт.

## Проверка

```
npm run test:packages                # манифест, валидатор, роль из пакета, привязка сохранений
npm run test:market                  # ссылки, реестр, установка из git в кеш, найм, обновление (без сети)
npm run test:cli                     # заготовка, валидатор, экспорт роли, publish и registry-check (без сети)
npm run test:skills                  # наборы в employees/: разбор и имена скилов
SKILLS_LIVE=1 npm run test:skills    # плюс живая сессия: видит ли она скил
npm run bench -- design              # стенд: срабатывают ли скилы роли (стоит денег)
```

`test:packages` гоняет через валидатор и наши пакеты из этой папки: битый
базовый пакет обязан ронять прогон, а не первый запуск офиса у пользователя.

## Свои наборы без пакета

Роль, заведённая из формы, может держать свои скилы в `employees/<роль>/` —
там читается тот же `agent.json` (или старый `pack.json`), но без роли: роль
уже есть в офисе. Это путь для локальных экспериментов; путь наружу — пакет.

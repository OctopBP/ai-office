# AI Office — концепт и план MVP

## 1. Идея

Десктоп/локальное приложение, где команда AI-агентов визуализирована как офис с видом сверху.
Каждый человечек — это агент с ролью (PM, backend, frontend, UI/UX, SMM, юрист). Пользователь
ставит задачу PM'у (или общается напрямую с любым агентом), PM декомпозирует и раздаёт задачи
команде. Агенты «ходят» друг к другу, обсуждают задачи, садятся за рабочие места и выполняют
работу. Рабочие места можно расширять — клонировать разработчика, чтобы он делал 3 задачи
параллельно.

Исполнение задач — через Claude Agent SDK (тот же движок, что у Claude Code). В будущем
пода можно подменить (Codex, Gemini CLI, свой раннер) — поэтому исполнитель абстрагируется
за интерфейсом `AgentRunner`.

---

## 2. Ключевой архитектурный принцип

> **Офис — это визуализация, а не источник правды.**

Источник правды — граф задач + лента событий. Анимации, ходьба и пузыри с репликами
рендерятся *из* событий, а не управляют логикой. Это критично, потому что:

- агент может выполнить задачу за 4 секунды или за 8 минут — анимация не должна блокировать;
- при перезапуске приложения офис восстанавливается из БД;
- можно сделать «реплей» рабочего дня;
- можно вообще выключить графику и всё продолжит работать (headless-режим для тестов).

```
Пользователь ──► PM session ──► tools(create_task/assign_task) ──► Task Board (SQLite)
                                                                        │
                                                                        ▼
                                                              Worker sessions (N)
                                                                        │
                                                          SDK-события (tool_use, text, …)
                                                                        │
                                                                        ▼
                                                          Нормализатор → OfficeEvent
                                                                        │
                                                                    WebSocket
                                                                        │
                                                                        ▼
                                                            Рендер офиса (спрайты)
```

## 3. Модель данных

```ts
// Роль — шаблон. Настраивается пользователем, хранится как JSON/MD.
type Role = {
  id: string;              // 'backend'
  title: string;           // 'Backend разработчик'
  sprite: string;          // ключ спрайта/аватара
  systemPrompt: string;    // персона + правила работы
  model: 'claude-opus-5' | 'claude-sonnet-5' | 'claude-haiku-4-5';
  effort?: 'low' | 'medium' | 'high' | 'xhigh';
  allowedTools: string[];  // Read, Write, Edit, Bash, Grep, WebSearch, ...
  permissionMode: 'ask' | 'auto' | 'readonly';
  workspace: WorkspaceSpec; // репозиторий / worktree / папка с доками
  maxInstances: number;     // сколько клонов разрешено (лимит «рабочих мест»)
};

// Инстанс — живой человечек в офисе. Роль может иметь несколько инстансов.
type AgentInstance = {
  id: string;              // 'backend#2'
  roleId: string;
  sessionId: string | null; // id сессии Agent SDK (для resume)
  desk: { x: number; y: number };
  state: AgentState;
  currentTaskId: string | null;
  usage: { inputTokens: number; outputTokens: number; costUsd: number };
};

type AgentState =
  | 'idle'            // сидит за столом
  | 'thinking'        // думает (💭)
  | 'working'         // вызывает инструменты (печатает)
  | 'walking'         // идёт к другому агенту / в переговорку
  | 'talking'         // диалог: два спрайта лицом друг к другу
  | 'waiting_approval'// ждёт подтверждения пользователя (❗)
  | 'blocked'         // ждёт ответа/зависимости
  | 'done';

type Task = {
  id: string;
  parentId: string | null;   // декомпозиция
  title: string;
  description: string;
  acceptanceCriteria: string;
  authorId: string;          // 'user' | 'pm' | 'backend#1'
  assigneeId: string | null; // AgentInstance.id
  roleId: string | null;     // кому по роли предназначена
  status: 'backlog' | 'assigned' | 'in_progress' | 'review' | 'blocked' | 'done' | 'failed';
  workspacePath: string | null; // worktree/папка, где велась работа
  result: string | null;
  artifacts: string[];       // пути к файлам/диффам
  budgetUsd: number | null;
};

type Message = {
  id: string;
  from: string; to: string;  // 'user' | instanceId
  kind: 'task' | 'question' | 'answer' | 'report' | 'chat';
  taskId: string | null;
  text: string;
  createdAt: number;
};

// Событие для UI — единственное, что видит фронт.
type OfficeEvent =
  | { t: 'agent.state'; agentId: string; state: AgentState }
  | { t: 'agent.say'; agentId: string; text: string }        // пузырь
  | { t: 'agent.tool'; agentId: string; tool: string; brief: string }
  | { t: 'agent.walk'; agentId: string; to: Point | string } // к точке или к агенту
  | { t: 'agent.spawn' | 'agent.despawn'; agentId: string }
  | { t: 'task.update'; task: Task }
  | { t: 'permission.request'; agentId: string; requestId: string; tool: string; input: unknown }
  | { t: 'usage'; agentId: string; costUsd: number };
```

## 4. Как работает один агент

Один `AgentInstance` = одна живая сессия Claude Agent SDK (`query(...)` в streaming-input
режиме, чтобы в сессию можно было дописывать новые сообщения, а не пересоздавать её).

Что даёт SDK «из коробки» и что мы из этого используем:

| Возможность SDK | Как используем в офисе |
|---|---|
| Встроенные Read/Write/Edit/Bash/Glob/Grep/WebSearch | Реальная работа агента в рабочей папке |
| `cwd` на сессию | Изоляция рабочих мест (worktree на задачу) |
| Кастомные MCP-инструменты in-process | Командные инструменты: `create_task`, `assign_task`, `ask_agent`, `say` |
| Permission callback (`canUseTool`) | ❗ над головой → модалка «разрешить Bash `rm -rf`?» |
| Hooks | Логирование, бюджеты, запрет выхода за пределы workspace |
| Поток сообщений (tool_use / text / result) | Питает `OfficeEvent` → анимации и пузыри |
| Resume сессии по id | Восстановление офиса после перезапуска |
| Subagents | v2: «внутренняя» декомпозиция внутри одной роли |

> ⚠️ Точные сигнатуры (`query`, `options`, `canUseTool`, `createSdkMcpServer`, `tool`)
> сверять с docs: `code.claude.com/docs/en/agent-sdk`. Ниже — псевдокод для понимания формы.

```ts
// Псевдокод!
const session = query({
  prompt: inputStream,                 // streaming input: можно докидывать сообщения
  options: {
    model: role.model,
    systemPrompt: role.systemPrompt,
    cwd: workspacePath,
    allowedTools: role.allowedTools,
    mcpServers: { team: teamToolsServer },   // командные инструменты
    canUseTool: async (tool, input) => {     // → permission.request в UI
      if (role.permissionMode === 'auto') return { behavior: 'allow', updatedInput: input };
      return await ui.askUser(instanceId, tool, input);
    },
  },
});

for await (const msg of session) {
  bus.emit(normalizeToOfficeEvent(instanceId, msg));  // ← вся визуализация отсюда
}
```

## 5. Оркестрация: PM-луп

Самое хрупкое место всей затеи. Правило: **PM не «болтает», PM дёргает инструменты.**
Доска задач — единственный источник правды, свободный текст PM'а ни на что не влияет.

### Инструменты PM (наш MCP-сервер, in-process)

```
list_team()                    → роли, инстансы, загрузка, свободные рабочие места
create_task({title, description, acceptanceCriteria, roleId, parentId?})  → taskId
assign_task({taskId, instanceId?})   → назначает; при отсутствии instanceId — берёт
                                       свободного или клонирует (в пределах maxInstances)
                                       ВОЗВРАЩАЕТСЯ СРАЗУ (не блокирует)
get_board({status?})           → текущее состояние доски
ask_agent({to, question})      → вопрос конкретному агенту, ответ приходит позже
say({text})                    → реплика в пузырь (для пользователя)
```

Ключевая деталь: `assign_task` **асинхронный**. Благодаря этому PM за один ход может
раздать 3 задачи трём клонам разработчика — это и есть фича «параллельные задачи».

### Инструменты исполнителя

```
say({text})                        → пузырь над головой (прогресс для пользователя)
ask_pm({question})                 → блокирует задачу, состояние → 'blocked'
finish_task({summary, artifacts})  → задача → 'review'/'done'
```

### Цикл

1. Пользователь пишет в чат → сообщение уходит в живую сессию PM.
2. PM: `list_team` → `create_task` ×N → `assign_task` ×N → отвечает пользователю «раздал».
3. Оркестратор поднимает воркеров (или переиспользует idle-инстансы), офис рисует ходьбу
   PM → к столу разработчика → диалог → разработчик садится работать.
4. Воркер закончил → `finish_task` → оркестратор **вбрасывает в живую сессию PM**
   сообщение: `«Задача T-3 закрыта backend#1. Результат: … Артефакты: …»`.
5. PM решает: принять / вернуть на доработку / создать следующую задачу.
6. Всё это время события летят в UI.

Пункт 4 — почему нужен именно streaming-input режим: сессия PM живёт постоянно и в неё
можно «пушить» результаты, не теряя контекст и не переплачивая за пересборку промпта
(prompt caching работает только пока префикс не меняется).

## 6. Клоны и параллельность

Клонирование = поднять второй `AgentInstance` той же роли за соседним столом.
Визуально: бейдж `#2`, лёгкий сдвиг оттенка.

**Главный риск — конфликты по файлам.** Два бэкендера в одном репозитории затрут друг друга.

Решение по типам ролей:

| Тип роли | Workspace | Изоляция |
|---|---|---|
| Код (frontend/backend) | git worktree на задачу: `.office/worktrees/T-12` | Полная. Интеграция — отдельная задача «смержить» |
| Документы (юрист, SMM, PM) | `docs/<role>/<task-id>/` | Достаточная, конфликты редки |
| Дизайн (UI/UX) | `design/<task-id>/` + WebSearch/WebFetch | Достаточная |

Порядок для кодовых задач:
`git worktree add .office/worktrees/T-12 -b task/T-12` → агент работает → `finish_task` →
PM создаёт задачу на ревью/мерж (или мержим сами кнопкой в UI).

Лимиты: `maxInstances` на роль + глобальный кап параллельных сессий (по CPU и по бюджету).

## 7. Визуальный слой

**Комната.** Тайловая сетка (например 28×18 тайлов по 32px). Зоны:
- рабочие места (стол + стул + компьютер) — по одному на инстанс, пустые слоты с «+»;
- переговорка — для групповых обсуждений (v2);
- доска задач на стене — кликабельная, открывает канбан;
- кухня/кулер — idle-анимация, чтобы офис был живым;
- вход — сюда «приходят» задачи от пользователя.

**Персонаж.** 4 направления, 3 анимации (idle / walk / type). Спрайты 32×32 или 48×48.
Бесплатные наборы: Kenney, LPC (OpenGameArt), itch.io. Для MVP хватит плоских
цветных болванок с иконкой роли.

**Соответствие событий и картинки:**

| Событие SDK | Что показываем |
|---|---|
| начало хода модели | 💭, `state: thinking` |
| `tool_use: Read/Grep` | 🔍, печатает |
| `tool_use: Edit/Write` | ✏️, печатает |
| `tool_use: Bash` | ⚙️ + мини-строка команды |
| `tool_use: WebSearch` | 🌐 |
| `canUseTool` → ask | ❗ красный, персонаж встаёт |
| `say(...)` | пузырь с текстом (2–4 сек, кликом — в панель) |
| `assign_task` | PM встаёт, идёт к столу исполнителя, диалог 2 сек, возвращается |
| `finish_task` | ✅ + анимация, задача едет на доске |
| ошибка / fail | 😵 красный |

Клик по человечку → правая панель: транскрипт сессии, текущая задача, usage, кнопки
«поговорить» / «остановить» / «клонировать».

**Важно:** очередь анимаций отдельная от логики. Если событий прилетело 20 за секунду —
логика их уже применила, анимации проигрываются со сжатием/пропуском.

## 8. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Оболочка | Локальный веб (Vite + Node) → позже Tauri | Claude Agent SDK всё равно работает локально; браузер быстрее в разработке, Tauri легче Electron при упаковке |
| Бэкенд | Node 20+, TypeScript, Fastify + `ws` | Agent SDK — TS-нативный |
| Движок агентов | `@anthropic-ai/claude-agent-sdk` за интерфейсом `AgentRunner` | Подмена провайдера в будущем |
| Хранилище | SQLite (`better-sqlite3`) | Задачи/сообщения/события растут быстро; JSON не выдержит |
| Фронт | React + Zustand + Tailwind | Панели, канбан, чат |
| Офис (MVP) | DOM-спрайты: абсолютно позиционированные div'ы + CSS transitions | 6–12 персонажей рендерится отлично; пузыри и клики — обычный HTML, вдвое меньше работы |
| Офис (v2) | PixiJS v8 | Когда офис вырастет, появятся слои, камера, зум |

Рекомендация по DOM vs Pixi: начать с DOM. Переход на Pixi — локальная замена компонента
`<OfficeCanvas>`, если события уже единственный интерфейс между логикой и картинкой.

## 9. План MVP

### MVP-0 — «вау-спайк» (3–5 дней)
Цель: увидеть, как PM реально раздаёт задачи и человечки работают.

- [ ] Одна комната, 4 рабочих места, 3 роли: **PM, Backend, Frontend**
- [ ] Чат-панель → живая сессия PM
- [ ] MCP-инструменты команды: `list_team`, `create_task`, `assign_task`, `get_board`, `say`
- [ ] Воркеры: сессии в директории проекта, инструменты Read/Write/Edit/Bash/Grep
- [ ] Нормализатор SDK-событий → `OfficeEvent` → WebSocket
- [ ] Рендер: состояния, ходьба PM к столу, пузыри
- [ ] Панель списка задач (плоский список, без канбана)
- [ ] Всё в памяти + дамп в JSON

**Критерий успеха:** «Сделай CRUD для заметок: API на бэке и страницу на фронте» → PM
создаёт 2 задачи, оба разработчика работают параллельно, в репозитории появляется код.

### MVP-1 — «рабочий продукт» (+1.5–2 недели)

- [ ] Клоны: `+` на пустом рабочем месте, `maxInstances`, бейджи `#2`
- [ ] git worktree на задачу для кодовых ролей + кнопка мержа
- [ ] Permission-модалка (`canUseTool`) + режимы `ask/auto/readonly` на роль
- [ ] SQLite: задачи, сообщения, события, `sessionId` → resume после перезапуска
- [ ] Счётчик токенов и $ на агента и на задачу, глобальный бюджет-стоп
- [ ] Редактор ролей: имя, промпт, модель, effort, инструменты, права, тип workspace
- [ ] Некодовые роли: **UI/UX, SMM, Юрист** — WebSearch/WebFetch + папки `docs/<role>/`
- [ ] Прямой чат с любым агентом (клик → «поговорить»)
- [ ] Канбан на доске задач

### v2 — то, что делает продукт продуктом

- Переговорка: несколько агентов в групповом обсуждении с фасилитатором
- Редактор офиса: планировка, мебель, зоны
- Пресеты команд («стартап», «агентство», «продуктовая команда») и импорт/экспорт
- Реплей дня + вечерний «стендап-отчёт» от PM
- Несколько офисов = несколько проектов
- Облачный режим: те же роли, но на Managed Agents (Anthropic держит луп и песочницу,
  есть мультиагентные роутеры, бюджеты сессии, вебхуки) — тогда офис работает, когда
  ноутбук закрыт
- Другие движки: Codex CLI, Gemini CLI — через `AgentRunner`

## 10. Риски и что с ними делать

| Риск | Насколько больно | Решение |
|---|---|---|
| PM «галлюцинирует» оркестрацию — говорит, что раздал, но не вызвал инструмент | Убивает продукт | Доска = источник правды. В системном промпте PM: «действие считается совершённым только через инструмент». В UI показывать доску, а не слова PM. Валидация: если PM ответил без tool-вызовов, а задач нет — авто-напоминание |
| Конфликты файлов при параллельной работе | Высоко | worktree на задачу; для доков — папка на задачу |
| Стоимость: 6 агентов × Opus = дорого | Высоко | Модель на роль: PM — Opus 5, разработчики — Sonnet 5, SMM/рерайт — Haiku 4.5. `effort: low/medium` там, где не нужен максимум. Бюджет на задачу с жёстким стопом. Счётчик всегда на виду |
| Длинные сессии, падения, потеря контекста | Средне | Персистить события и `sessionId`, resume; сессии сами компактят контекст |
| Агент делает опасное (`rm -rf`, `git push`) | Высоко | `permissionMode: ask` по умолчанию для Bash; hooks с запретом выхода за пределы workspace; whitelist команд |
| Картинка расходится с реальностью | Средне | Событийный лог рядом с офисом; «показать транскрипт» по клику |
| Overengineering визуала до того, как заработает логика | Средне | MVP-0 на DOM-спрайтах, никакого Pixi/тайлмапов на старте |

## 11. Чего в MVP сознательно НЕ делаем

- Редактор планировки офиса (комната захардкожена)
- Переговорка и групповые обсуждения
- Мультипроектность
- Аутентификация, мультиюзер, облако
- Собственные спрайты и анимации (болванки/готовые бесплатные наборы)
- Автоматический мерж worktree (кнопка «смержить» руками)

## 12. Открытые вопросы

1. **Ревью результата.** Кто принимает работу — PM, отдельная роль QA, или пользователь
   кнопкой? Предложение для MVP: PM принимает, пользователь видит diff и может вернуть.
2. **Что делать, когда агент задал вопрос, а пользователь ушёл.** Таймаут → `blocked` и
   уведомление, или PM отвечает за пользователя по своему усмотрению?
3. **Где живёт проект.** Одна папка на офис (репозиторий) или офис умеет несколько
   репозиториев (фронт + бэк отдельно)? Для MVP — одна.
4. **Биллинг.** API-ключ (прозрачная цена за токен) или авторизация через подписку
   Claude Code. Влияет на то, как считать «стоимость дня офиса».

| Модель | ID | $/1M вход | $/1M выход | Роли |
|---|---|---|---|---|
| Claude Opus 5 | `claude-opus-5` | $5.00 | $25.00 | PM, архитектура, сложные задачи |
| Claude Sonnet 5 | `claude-sonnet-5` | $3.00 | $15.00 | Разработчики, дизайнер |
| Claude Haiku 4.5 | `claude-haiku-4-5` | $1.00 | $5.00 | SMM, простой рерайт, классификация |

Промпт-кеширование даёт ~90% экономии на повторяющемся префиксе — критично, потому что
системный промпт роли уходит в каждый запрос сессии. Живые сессии (streaming input)
сохраняют кеш; пересоздание сессии на каждую задачу — нет.

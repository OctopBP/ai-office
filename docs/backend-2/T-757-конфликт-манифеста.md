# T-757: конфликт манифеста до запуска npm

## Причина и точное основание

Проверка выполнена 2026-11-01 в собственной копии T-757, основанной на main `603f6437279fe6479f235c0d46e8073ab8289c7d` (версия 0.14.0-beta.20).

Маркеры находятся **в коммите ветки задачи**, а не в main:
- `task/T-748 = 39f48c1f67c3a3e72134fcf4aa587aa0a9f1dbdb`, сообщение «T-748: доработка».
- Это merge-коммит родителей `f9bd0cc35916610790e98a9dfc12a61fb23a90fd` и `603f6437279fe6479f235c0d46e8073ab8289c7d`.
- `git show 39f48c1 -- package.json` показывает добавленные строки маркеров в combined diff; в первом родителе маркеров нет, есть test:review-verdict и старый test:review через tsx; во втором родителе маркеров нет, test:review уже через node --import tsx.
- В `git show task/T-748:package.json` строки 103–108 содержат:

```text
<<<<<<< HEAD
    "test:review-verdict": "node --import tsx scripts/test-вердикт-ревью.ts",
    "test:review": "tsx scripts/test-review.ts",
=======
    "test:review": "node --import tsx scripts/test-review.ts",
>>>>>>> main
```

Общая integration-копия `../_base/office-b0cc4212` прочитана без изменения: HEAD равен указанной main, `git ls-files -u` пуст, diff package.json/package-lock.json пуст, package.json без маркеров. На момент осмотра оставшегося конфликта в ней нет. История конкретного прошлого состояния каталога не восстанавливалась; происхождение плохого содержимого доказано непосредственно коммитом задачи.

main является родителем T-748. Git сливает такую ветку без U-конфликта: маркеры для него обычный закоммиченный текст. Старый assembleMerge проверял U только при неуспешной команде merge; при успешной сборке preMergeGate переходил к prepareDeps. Отличающийся package.json заставлял prepareDeps запускать npm ci, который уже распознавал маркеры и падал с EJSONPARSE. Ошибка ошибочно становилась обычным отказом установки зависимостей.

Это не новый неразрешённый конфликт трёхстороннего слияния актуальной main и T-748 и не закоммиченные маркеры в собственной базе T-757. dropAssembled возвращает копию к базе; удаление lock, чужих файлов или общих следов не требуется.

## Исправление

В assembleMerge после успешного merge проверяется индекс результата: отдельные строки маркеров в package.json и package-lock.json, включая вложенные проекты. В JSON такие строки недопустимы; текст внутри JSON-значения не совпадает с проверкой.

При маркерах возвращается существующий результат `kind: conflict` с именами файлов. preMergeGate отдаёт существующую стадию conflict до prepareDeps, npm и проверок. Ошибка самой проверки индекса возвращается как ошибка сборки, без запуска npm.

Собранное только этой операцией дерево возвращается к зафиксированному baseSha в integration-копии, принадлежность которой уже проверена integrationWorktree. Это необходимо и для обычного merge: успешное слияние уже создало коммит, поэтому merge --abort его не уберёт. Никаких новых чисток общих каталогов, удаления lock или чужих изменений не добавлено.

premerge.ts и deps.ts менять не потребовалось. package.json, package-lock.json, версии и скрипты main не изменены. Ветка T-748 и её регистрация test:review-verdict не изменялись; одобренный патч вердикта не переносился.

## Воспроизведение и проверки

Регрессия добавлена в scripts/test-premerge.ts. Используется собственный временный git-репозиторий:
1. Коммит package.json с маркерами успешно сливается git; ls-files -u пуст.
2. Прямой запуск прежней команды npm ci (дополнительно --offline, кеш внутри своего стенда) воспроизводит EJSONPARSE.
3. Исправленный гейт для обычной и squash-сборки возвращает conflict, checks пуст, failed отсутствует; контрольный файл зависимостей сохраняется — prepareDeps не выполнялся.
4. Проверяются маркеры lock и вложенного package.json даже при пустом наборе команд, настоящий U-конфликт, сохранность ссылок main/задачи, возврат копии к базе и успешный чистый прогон в той же копии после отказов.
5. Существующие сценарии depsGate проверяют реальную установку локальной file-зависимости через npm ci, кеш и сохранность зависимостей основной копии.

После последней правки кода и регрессии выполнены:
- node --import tsx scripts/test-premerge.ts — 139 проверок, успешно;
- npm run typecheck — успешно;
- node --import tsx scripts/test-merge.ts — 39 проверок, успешно;
- node --import tsx scripts/test-squash.ts — 29 проверок, успешно;
- npm run test:deps — успешно;
- git diff --check адресно для изменённых файлов — успешно.

Существующие тесты с tsx запущены через node --import tsx без изменения package.json. scripts/test-pm.ts не запускался. Полная git status/diff в этой песочнице натыкается на запись git-lfs в общий .git/lfs/tmp; использованы адресные проверки собственных файлов, права не расширялись.

## Применение и безопасное возобновление T-748

Для нового поведения нужен **новый серверный код**: результат T-757 необходимо штатно слить, собрать и применить к работающему серверу офиса. В рамках задачи сервер не перезапускался и сборка не выпускалась.

Один этот фикс не делает T-748 пригодной для слияния: на существующем коммите она будет правильно остановлена как conflict. До retry_review ответственный за T-748 должен штатно исправить её собственный package.json и закоммитить результат, сохранив одновременно:
- test:review из main: `node --import tsx scripts/test-review.ts`;
- test:review-verdict из T-748: `node --import tsx scripts/test-вердикт-ревью.ts`;
- актуальную версию и остальные скрипты main, без переноса старых значений.

Безопасный retry_review T-748: исправленный серверный код применён, актуальная ветка T-748 содержит корректные манифесты без маркеров и обе регистрации проверок; после этого запускается обычный конвейер с проверками и ревью. Исправлять T-748 руками из этой задачи или менять общую _base-копию не требуется и не выполнялось.

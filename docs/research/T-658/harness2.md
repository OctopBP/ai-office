## 1. Что такое harness2

### Назначение

Это исследовательский фреймворк к статье «Harness²: Recursive Agent Harnessing
for an Open World». Он автоматически улучшает **обвязку агента** (harness), а
веса модели не трогает. Под обвязкой авторы понимают всё вокруг модели: промпты,
инструменты, память, скилы, оркестрацию (`README.md:19-22`).

Рекурсия идёт на двух уровнях (`README.md:23-34`):

- **Внутри задачи** — шаг Propose–Probe–Compose. Агент-редактор предлагает
  правки обвязки, кандидаты прогоняются на той же задаче, а композитор собирает
  итоговую обвязку из различий в поведении прогонов. Правильный ответ при этом
  не нужен.
- **Между задачами** — постоянная «обвязка улучшения» (improvement harness):
  принятые обвязки и уроки с доказательствами копятся по домену и подсказывают
  следующим задачам.

По словам авторов, один шаг даёт до +11,5 пункта на WorkBuddy-Bench, +4,5 на
JobBench и +11,8 п.п. partial pass на LAB для GLM-5 и Gemini 3.5 Flash
(`README.md:41-45`). Независимо я это не проверял.

### Устройство

Свой цикл агента harness2 **не ведёт**. Задачи исполняют чужие агенты-«субстраты»
OpenCode и Codex CLI (`README.md:47-48`, `harness2/substrate/opencode.py`,
`harness2/substrate/codex.py`), а сам harness2 стоит над ними как оптимизатор.

| Часть | Где | Что делает |
|---|---|---|
| Редактируемая поверхность c1..c8 | `harness2/core/tree.py:15-21`, `:42-61`; `README.md:68-73` | Восемь компонентов: системный промпт, guardrails, память (`LongTermMEMORY.md`), описания инструментов, субагенты, скилы, скрипты, плагины. Обвязка — это дерево файлов `dict[путь, текст]`. Правка приходит только с изменёнными файлами, остальное наследуется |
| Валидатор дерева | `harness2/core/tree.py:84-104` (`is_allowed`), `harness2/core/recursion.py:108-132` (`_accept_tree`) | Белый список путей, запрет `..`, проверка имён скилов. Ещё проверяется, что скил упомянут в постоянном тексте: иначе он не сработает |
| Потолок постоянного текста | `harness2/substrate/opencode.py:42-51` | `always_on_max=24_000` символов с пояснением «каждый токен здесь конкурирует с бюджетом вывода агента» |
| Предложение правок | `harness2/core/prompts.py:345-380` | Два независимых редактора. **INV** отвечает за то, *как агент работает*: ошибки инструментов, повторы, порядок шагов. **DOM** — за то, *что знает практик*: структуру результата и правила предметной области. Каждой поломке подбирается самый дешёвый компонент: текст → скил → скрипт → защитный цикл |
| Рекурсия | `harness2/core/recursion.py:343-449` (`run_parallel`), `:452` (`run_sequential`) | Параллельный режим: 2k кандидатов (k INV + k DOM) из общих доказательств, затем k независимых композиций. Последовательный режим: k шагов подряд. Негодная правка получает один повтор, а потом остаётся прежняя обвязка (`recursion.py:36`, `:180-245`) |
| Бюджет | `harness2/core/ledger.py:15-30`, `:76-105` | Жёсткое тождество: R = 4k прогонов и P = 3k сессий улучшения. Каждый шаг пишется в книгу расходов с меткой и долларами, а дубли меток ловятся как ошибка |
| Слепой отбор | `harness2/core/selection.py:268-300`, `:71-86` | Выбирающий видит результаты под анонимными A, B, C…, перемешанными с фиксированным зерном. Какой кандидат базовый, а какой правленый, он не знает |
| Рефлексия → урок | `harness2/core/selection.py:402-505`, `harness2/core/prompts.py:1106-1160` | После принятия обвязки извлекается урок `cue / lesson / evidence / confidence`. Урок без всех трёх полей не сохраняется (`library.py:43-47`) |
| Библиотека опыта | `harness2/core/library.py:15-24` | По каждому домену хранятся `INDEX.md`, принятые деревья целиком и `EXPERIENCE.md`. Задачи одного домена идут по порядку и читают только более ранние записи |
| Защита от утечки оценки | `harness2/core/context.py:399`, `:454-470`; `harness2/core/spec.py:117-127` | Растяжка: в контекст редактора не должны попасть вердикты грейдера. Текст подсказок не может содержать слова «benchmark/rubric/score» |
| Каналы модели-редактора | `harness2/core/spec.py:33`, `harness2/core/proposer.py:210-240`, `harness2/config.py:174-175` | Редактор вызывается через OpenCode или `claude -p --output-format json --dangerously-skip-permissions` |
| Оценка | `harness2/core/judge.py`, `docs/BENCHMARKS.md` | Три профессиональных бенчмарка: JobBench, LAB (юридический), WorkBuddy-Bench (офис, веб, код) |

Оркестрации команды агентов в нашем смысле здесь нет. Субагенты — лишь один из
редактируемых компонентов (c5), а параллельны только прогоны кандидатов.

### Лицензия, язык, зависимости

- **Apache-2.0** (`LICENSE`, `pyproject.toml:10`). Код в `third_party/`,
  бенчмарки и датасеты остаются под своими лицензиями (`README.md`, раздел
  License; `third_party/licenses/`).
- Python 3.12–3.13, только POSIX/Linux (`pyproject.toml:11-15`, `README.md:83`).
  У ядра нет зависимостей (`dependencies = []`), опционально подключаются
  openpyxl, python-pptx и litellm (`pyproject.toml:21-24`). Для бенчмарков
  нужны Node 20+, Google Cloud CLI (Vertex AI), Docker и Pandoc (`README.md:96-100`).
- Около 15,9 тыс. строк Python, из них ядро `harness2/core` около 5,7 тыс.
  Тест один: `tests/test_workflow.py`, 229 строк.

### Активность (на 2026-10-20, GitHub API)

- Репозиторий создан 2026-10-06. В истории **3 коммита**: начальный выпуск
  2026-10-08, «updates» 2026-10-08 и «Fix arXiv link» 2026-10-13.
- 11,5 тыс. звёзд, 1045 форков, 84 открытых issue и PR. Почти всё за 19.10 —
  внешние PR с исправлениями: Windows, судья через `claude_cli`, вход в Codex
  через ChatGPT, «judge_one trusts all_pass…».
- Это свежий исследовательский дамп к статье: популярен, но сопровождение
  пока не показано. Пометка в README: «not an officially supported Google product».

### Безопасность

Авторы прямо пишут, что сеть у исполнителя не ограничена, а Codex работает с
выключенной песочницей (`README.md:168`). Канал Claude запускается с
`--dangerously-skip-permissions` (`harness2/core/proposer.py:213-216`). В
валидационном прогоне Codex сам скачал рубрику задачи из сети
(`docs/EXPERIMENTS.md:95-98`). Для офиса, где важны классификатор риска и
изоляция, это красный флаг: запускать harness2 как есть нельзя.

## 3. Что брать, а что нет

### Можно взять (идеи; код — только под Apache-2.0 с NOTICE, но переписывать с Python на TS всё равно придётся)

**A. Проба правила перед вписыванием в бриф («Probe» для предложений рефлексии).**
Сейчас правило от рефлексии уходит владельцу и в `briefExtra` без проверки. Идея
harness2: прогнать кандидата на той же задаче и сравнить поведение с базой
(`recursion.py:343-449`). У нас это ляжет на стенд. Для правила-кандидата
запускаем `runBenchCase` (`bench.ts:104`) дважды, с правилом и без, на случаях
роли (`bench/cases.json`), и прикладываем разницу (скилы, вызовы, ходы, деньги)
к предложению в `ProposalView.rationale`.
*Куда:* `src/server/bench.ts` (прогон с приписанной строкой брифа),
`src/server/rituals.ts` / `selfchange.ts` (вызов перед показом владельцу),
`ProposalView` — поле `probe`.
*Объём:* средний, 2–3 дня. Цена — порядка десятка центов на случай (`bench.ts:14-16`), поэтому включать
только при заданных случаях и под `ritualLimitThreshold`.

**B. Формат урока `cue / lesson / evidence` и отказ сохранять урок без доказательств.**
Это `prompts.py:1135-1160` и `library.py:43-47`. Урок хранит, *в какой ситуации*
применять, *что делать* и *на чём основано* (ссылки на задачи или отзывы).
Урок без основания не записывается. У нас это лечит болезнь, которую уже видно в
журнале: уроки без опоры и противоречия между записями.
*Куда:* `src/server/journal.ts` (необязательные поля `cue`, `evidence` у записи
вида «урок»), промпт рефлексии и консолидации в `agents.ts` (срез рядом с
`reflect`), `freshness.ts` (проверять урок по его `evidence`).
*Объём:* малый, 1 день.

**C. Потолок и инвентаризация постоянного контекста роли.**
По образцу `always_on_max` (`opencode.py:50-51`) и статической проверки
«скил назван в постоянном тексте» (`tree.py`, `autotrigger` в
`recursion.py:116-118`). Валидатор пакета предупреждает, если бриф +
`briefExtra` + правила роли + порция журнала больше N символов, и если у скила
описание слишком общее или пустое.
*Куда:* `src/server/packages.ts` (валидатор), `src/server/rules.ts` (размер
блока правил), `office-agent validate`.
*Объём:* малый, 0,5–1 день.

**D. Деление правок на INV и DOM.**
Это `prompts.py:345-380`: правки «как работать» (инструменты, порядок, проверка
результата) отдельно от правок «что знать о предметной области». Для нас это
подсказка рефлексии: правило «как работать» уходит в бриф роли, а знание о
проекте — в журнал или `RULES.md` направления. Тогда в пакете с маркета не
окажется сведений о нашем проекте. Сюда же «лестница» самого дешёвого
компонента: текст → скил → скрипт.
*Куда:* промпт рефлексии (`agents.ts`, рядом с `reflect`), поле `rules[].kind`
в `ReflectionOutput` (`rituals.ts:107-110`).
*Объём:* малый, 0,5 дня, вместе с B.

**E. Бюджет эксперимента с проверкой (ledger).**
Это `ledger.py:76-105`: заранее известно, сколько прогонов и сессий будет, и
после прогона это проверяется. Понадобится только вместе с A. Это не отдельная
задача, а часть её: книга расходов пробы.

### Не подходит

- **Подключить harness2 движком или инструментом — нельзя.** Это не движок, а
  оптимизатор над чужими движками. Он требует Python 3.12 и Linux
  (`README.md:83`), Vertex AI и gcloud (`README.md:96-100`), а исполнители
  работают без песочницы и с `--dangerously-skip-permissions`
  (`README.md:168`, `proposer.py:213-216`). Это противоречит нашему
  классификатору риска и Electron-приложению под macOS и Windows.
- **Полный цикл Propose–Probe–Compose на каждой задаче — не по карману.** На
  одну задачу уходит 4k прогонов и 3k сессий редактора (`ledger.py:15-30`); при
  k=1 это 4 полных исполнения задачи вместо одного. Наши задачи меняют
  репозиторий, а не создают отчёт в песочнице, и задача целиком повторяется
  плохо. Под план подписки с лимитами (`limits.ts`) это не ложится.
- **Слепой выбор из нескольких результатов** имеет смысл только при нескольких
  кандидатах. Пока мы не делаем «две ветки на одну задачу», брать нечего.
- **Бенчмарки JobBench, LAB и WorkBuddy** проверяют профессиональные
  документы, а не работу команды над кодом. Как наш стенд они не подходят.
- **Код целиком.** Сам код состоит из Python-обвязки вокруг CLI и разбора их
  потоков. Переносить его на TS дороже, чем написать четыре идеи выше заново.
  Проекту неделя, в нём 3 коммита и пачка внешних исправлений
  (см. «Активность»).

## 4. Рекомендация

**Не брать harness2 как зависимость или движок, но взять идеи «пробы правила на
стенде до вписывания в бриф» и «урока с обязательным основанием»; потолок
контекста и деление INV/DOM — дешёвым довеском.**

### Кандидаты в задачи

1. **Урок с основанием** (B + D) — backend. В записи журнала вида «урок» —
   поля `cue` и `evidence`. Промпт рефлексии и консолидации требует их и делит
   правило на «как работать» и «о проекте». Ритуал свежести проверяет урок по
   `evidence`. `journal.ts`, `agents.ts` (рефлексия), `freshness.ts`. Около
   1 дня.
2. **Проба правила на стенде** (A + E) — backend. Перед показом предложения
   владельцу правило прогоняется на случаях стенда роли с правилом и без, а
   разница и цена ложатся в предложение. Только если у пакета есть
   `bench/cases.json` и не превышен порог лимита. `bench.ts`, `rituals.ts`,
   `selfchange.ts`, `shared/types.ts` (`ProposalView`). 2–3 дня, плюс
   frontend на показ разницы в карточке предложения, около 0,5 дня.
3. **Потолок постоянного контекста роли** (C) — backend. Предупреждение
   валидатора пакета и `office-agent validate`, если бриф, правила и порция
   журнала больше порога, или если у скила пустое или слишком общее описание.
   `packages.ts`, `rules.ts`. 0,5–1 день.

Сравнений с Claude Code, Codex и другими обвязками «по общему знанию» в
документе нет: всё про harness2 подкреплено ссылками на файлы, всё про офис —
путями в нашем репозитории.

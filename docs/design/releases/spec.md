# Спека: выпуски

**Состояние: сделано.** Все четыре фазы (§12) закрыты 2026-09-27: процесс
`workflows/release.json`, хозяин прогона `src/server/releases.ts`, цели
`push`, `tag` и `command`, поводы по политике цели, починка задачей от ветки
выпуска, планы выпусков и панель «Выпуски» (клавиша R). Проверки —
`npm run test:releases`. Где код разошёлся с первым черновиком — §15.

Сценарий: фича закрыта, и офис сам предлагает выпуск. Он собирает список
того, что вошло, пишет заметки, предлагает номер версии, спрашивает владельца
(если так настроено) и выпускает. Как именно выпускать, решает проект: пушем в
ветку, которую забирает CI, тегом, по которому CI собирает установщики (так
выпускается сам офис), или сборкой iOS прямо на этой машине с загрузкой в
TestFlight. Если сборка упала, офис один раз пробует починить её сам, а не
вышло — заводит задачу с логом и останавливается.

Второй сценарий: владелец пишет в чат «собери билд в TestFlight», и выпуск
идёт по тому же процессу, только без повода «фича закрыта».

Чего здесь нет: **сборки на каждую задачу.** Слияние задачи в основную ветку
по-прежнему заканчивается проверкой сборки (`runTypecheck` после слияния), но
не выпуском. Выпуск — отдельный предмет со своим поводом.

Родственные документы:
- `docs/design/workflows/spec.md` — процессы, узлы, прогоны, триггеры.
  Выпуск — это процесс `release.json` из тех же шести узлов; новых видов
  узлов эта спека не заводит (§3);
- `docs/design/living-office/spec.md` — очередь вопросов владельцу, куда
  встаёт согласие на выпуск (§5.4);
- `src/server/runs.ts` — раннер, который поведёт прогон выпуска;
- `src/server/checks.ts` — `runProjectCheck`: чем запускаются команды выпуска;
- `.github/workflows/release.yml` — как выпускается сам офис сегодня: тег
  `v*` руками, CI собирает черновик релиза.

## 1. Что есть сейчас и чего не хватает

| Что | Где | Чего не хватает |
|---|---|---|
| Процессы с триггерами | `workflows/*.json`, `runs.ts`, `flows.ts` | предмета «выпуск»: прогон идёт либо по задаче, либо по офису |
| Фича закрылась | `plan.ts`: `epic.status = 'done'`, сообщение в чат и менеджеру | события, на которое может подписаться процесс |
| Свои проверки проекта | `settings.checks`: имя → команда, узел `project:<имя>` | запуска вне рабочей копии задачи и таймаута дольше 5 минут |
| Триггер `manual` | схема триггеров в `shared/workflow.ts` | того, кто его нажимает: ни кнопки, ни инструмента менеджера |
| GitHub | `github.ts`: PR, слияние, ветки | статуса прогонов CI по коммиту |

Выпуск офиса сегодня делается руками: `npm version`, коммит, тег, пуш,
проверка черновика релиза. Первая фаза (§12) заменяет ровно это, на самом
офисе.

## 2. Главные решения

1. **Выпуск — процесс, а не подсистема.** Один файл `workflows/release.json`
   из существующих узлов (`check`, `step`, `gate`, `decide`). Проект
   перекрывает его своим, как любой другой процесс (workflows §14.16).
2. **Офис решает, готовит и следит, а собирает тот, кто умеет.** Если у
   проекта есть CI, офис пушит ветку или тег и ждёт результата. Если CI нет
   (iOS на этой машине), офис запускает команду проекта. В обоих случаях
   сборка — это команда или внешний прогон, а не сессия агента.
3. **Цель выпуска — настройка проекта, процесс один.** «Куда и как выпускать»
   описывается целью (§4). Процесс получает цель параметром и по её виду
   выбирает ветку в `decide`-узле без модели.
4. **Когда выпускать — политика цели, а не зашитое правило.** По просьбе, по
   закрытой фиче, по накоплению слияний; с согласием владельца или без (§5).
5. **Секреты видят только команды.** Ключ App Store Connect, токены,
   сертификаты подписи лежат там, где их держит проект (связка ключей,
   `~/.fastlane`, секреты CI). Офис их не хранит и не передаёт агенту (§8).
6. **Версия планируется.** У проекта задана схема версий, у фичи — вклад в
   версию, у выпуска — план: какие фичи в него входят (§6).

## 3. Процесс `release`

```
start ─► snapshot (check) ─┬─ empty ─► end
                           └─ pass ─► version (check) ─► notes (step, summarize)
      ─► approve (gate, по политике цели) ─┬─ no ─► end
                                           └─ yes ─► bump (check) ─► ship (decide по виду цели)
      ─┬─ push    ─► push (check) ─► watch (check)
       ├─ tag     ─► tag (check)  ─► watch (check)
       └─ command ─► build (check)
      ─► (watch | build) ─┬─ pass ─► publish (check) ─► end
                          └─ fail ─► fix (step, code.write, max 1) ─► ship
```

Узлы:

| Узел | Вид | Действие | Что делает |
|---|---|---|---|
| `snapshot` | check | `office:release-snapshot` | фиксирует SHA основной ветки и диапазон с прошлого выпуска этой цели; нет новых коммитов — `empty` |
| `version` | check | `office:release-version` | считает версию по схеме проекта и плану выпуска (§6); без модели |
| `notes` | step | — | заметки о выпуске из задач диапазона и их записок при передаче; `needs: ['summarize']`, дешёвая модель |
| `approve` | gate | — | вопрос владельцу: версия, состав, заметки; есть только если политика цели требует согласия (§5) |
| `bump` | check | `office:release-bump` | коммит версии и changelog в основную ветку (если у цели есть `bump`) |
| `ship` | decide | `office:release-kind` | переход по виду цели; менеджер не зовётся, решение — поле цели |
| `push` | check | `office:release-push` | fast-forward ветки цели до SHA выпуска и пуш |
| `tag` | check | `office:release-tag` | аннотированный тег по шаблону цели, пуш тега |
| `watch` | check | `office:ci-watch` | ждёт прогоны CI по SHA или тегу (§7); CI нет — сразу `pass` |
| `build` | check | `project:<имя>` | команда цели в рабочей копии выпуска (§7.2) |
| `fix` | step | `office:fix-build` | исполнитель с `code.write` получает хвост лога и SHA, чинит в ветке от снимка; ветка идёт по процессу `feature` в основную, а в выпуск — снимок плюс эта ветка (§7.3) |
| `publish` | check | `office:release-publish` | записывает результат: ссылку на релиз, номер сборки, сообщение в чат |

`fix` — единственное место, где выпуск тратит деньги на код, и единственная
петля: `fail → fix` с `max: 1`. Второе падение — `stuck` с `needsDecision`:
офис заводит задачу «Починить сборку <цель>» с логом в описании, говорит
менеджеру, выпуск стоит. После слияния этой задачи владелец или менеджер
перезапускает выпуск, и прогон продолжает с узла `snapshot`, а не с `build`:
код изменился, снимок старый (§9.2).

`decide`-узел `ship` не зовёт модель: исход берётся из `target.kind`. Так
процесс остаётся одним файлом, а не тремя почти одинаковыми.

## 4. Цель выпуска

Цель — куда и как выпускать. Лежит в настройках проекта рядом с `checks`:

```ts
interface ReleaseTarget {
  id: string;                       // 'staging', 'desktop', 'testflight'
  title: string;                    // как показывать в интерфейсе
  kind: 'push' | 'tag' | 'command';
  /** push: ветка, которую забирает CI. */
  branch?: string;
  /** tag: шаблон тега, `{version}` подставляется. По умолчанию `v{version}`. */
  tag?: string;
  /** command: имя команды из `settings.checks`, которая собирает и грузит. */
  run?: string;
  /** Сколько ждать сборку или CI, минуты. По умолчанию 30, предел 120. */
  timeoutMin?: number;
  /** Как поднимать версию в файлах перед выпуском (§6.3). Нет — версия только в теге. */
  bump?: string;
  /** Когда выпускать и нужно ли согласие (§5). */
  policy: ReleasePolicy;
  /** Схема версии этой цели (§6.1). */
  version: VersionScheme;
}
```

Три вида и что делает каждый:

| Вид | Сборка | Офис делает | Результат |
|---|---|---|---|
| `push` | CI проекта по пушу в ветку | ветка цели ← SHA выпуска, пуш, ждёт CI | зелёный прогон CI, ссылка на него |
| `tag` | CI по тегу | тег, пуш тега, ждёт CI | ссылка на релиз GitHub (черновик или готовый — как настроен CI) |
| `command` | эта машина | запускает команду в отдельной рабочей копии | код выхода, хвост лога, то, что команда напечатала в строку результата (§7.2) |

Пример для трёх ваших случаев:

```json
{
  "checks": {
    "testflight": "bundle exec fastlane beta"
  },
  "release": {
    "targets": [
      { "id": "staging", "title": "Стенд", "kind": "push", "branch": "deploy",
        "policy": { "when": ["epic.done"], "approve": "never" },
        "version": { "scheme": "none" } },
      { "id": "desktop", "title": "Приложение", "kind": "tag", "tag": "v{version}",
        "bump": "npm version {version} --no-git-tag-version",
        "policy": { "when": ["manual"], "approve": "always" },
        "version": { "scheme": "semver", "level": "plan" } },
      { "id": "testflight", "title": "TestFlight", "kind": "command", "run": "testflight",
        "timeoutMin": 60,
        "policy": { "when": ["manual", "epic.done"], "approve": "always" },
        "version": { "scheme": "semver+build", "level": "plan" } }
    ]
  }
}
```

Целей нет — выпусков нет: процесс `release` не стартует, у менеджера нет
инструмента, кнопки в интерфейсе тоже нет. Выпуск не включается в
существующем проекте сам собой.

## 5. Когда выпускать: политика цели

Ответ на вопрос «выпускать ли самому» — не один переключатель на офис, а
поле каждой цели. Стенд можно обновлять после каждой фичи молча, TestFlight
— только с согласия, стор — только по просьбе.

```ts
interface ReleasePolicy {
  /** Поводы. Хотя бы один. */
  when: Array<'manual' | 'epic.done' | { merged: number }>;
  /** Спрашивать ли владельца перед выпуском. */
  approve: 'always' | 'never' | 'major';
  /** Не чаще, чем раз в N часов, для автоматических поводов. По умолчанию 0. */
  cooldownHours?: number;
}
```

Поводы:

- **`manual`** — владелец попросил: кнопка «Выпустить» у цели в панели
  выпусков или просьба в чате. Менеджер получает инструмент
  `start_release(target, note?)`; просьба «собери билд» без цели при одной
  цели понимается однозначно, при нескольких менеджер спрашивает. Ручной
  выпуск не смотрит на `cooldownHours`.
- **`epic.done`** — фича закрылась с успехом (не `cancelled`). Надзор
  видит это по состоянию: у фичи `status: 'done'` и `finishedAt` позже
  последнего выпуска цели. Несколько фич, закрывшихся за один проход
  надзора, дают один выпуск, а не несколько.
- **`{ merged: N }`** — с прошлого выпуска этой цели слито N задач. Для
  стендов, где фич нет, а поток мелких правок есть.

Согласие:

- **`always`** — узел `approve` задаёт вопрос владельцу. Вопрос встаёт в общую
  очередь (`questions.ts`) и, как любой вопрос, «нет» по умолчанию: пока
  владелец не ответил, выпуск стоит и ничего не тратит.
- **`never`** — узла `approve` в прогоне нет, выпуск идёт сразу.
- **`major`** — спрашивает, только если версия поднимается на старший
  разряд. Для целей, где мелкие выпуски не страшны, а большие должен видеть
  человек.

Режим инициативы офиса (`off` / `propose` / `auto`, workflows §9) на выпуск
влияет одним правилом: при `off` автоматические поводы (`epic.done`,
`merged`) выключены у всех целей, остаётся `manual`. Остальное решает
политика цели.

Ограничители, которые политикой не снимаются:

- **Один выпуск на цель одновременно.** Повод пришёл во время идущего
  выпуска — он запоминается, и после конца выпуска `snapshot` решит, есть ли
  что выпускать.
- **Одна локальная сборка на машину.** Два `command`-выпуска (TestFlight и
  ещё что-то) не собираются параллельно: Xcode и симуляторы делят один диск и
  одну связку ключей, а время сборки у двух параллельных дольше, чем у двух
  последовательных.
- **Новая цель не выпускает прошлое.** Поводы считаются от последнего
  выпуска цели, а у цели без выпусков — от момента, когда офис о ней
  узнал: фичи, закрытые до настройки, выпуск сами не будят.

## 6. Версия

### 6.1 Схема

```ts
interface VersionScheme {
  scheme: 'semver' | 'semver+build' | 'calver' | 'build' | 'none';
  /** Где лежит текущая версия. По умолчанию — последний тег цели. */
  source?: 'tag' | 'package.json' | 'command';
  /** Для source: 'command' — команда, печатающая текущую версию. */
  read?: string;
  /** Как выбирается разряд: по плану выпуска, по составу, всегда один. */
  level: 'plan' | 'auto' | 'patch' | 'minor' | 'major';
}
```

- `semver` — `1.4.2`, как у офиса и у npm-пакетов.
- `semver+build` — версия для людей и номер сборки: `1.4.0 (57)`. Это iOS:
  `CFBundleShortVersionString` и `CFBundleVersion`. Номер сборки растёт на
  каждый выпуск, даже если версия та же; последний офис хранит у цели, а
  команда проекта может свериться со стором (fastlane
  `latest_testflight_build_number`) и напечатать больший (§7.2).
- `calver` — `2026.09.27` плюс порядковый номер за день, для стендов и
  сервисов.
- `build` — только номер.
- `none` — версии нет: пуш на стенд.

### 6.2 Откуда разряд: планирование

Разряд — это решение о том, что обещано пользователю, и принимать его
модель не должна. Поэтому три способа, от самого управляемого:

- **`plan`** — выпуск запланирован заранее. У фичи при планировании
  появляется поле `release`: в какую цель и с каким вкладом (`patch`,
  `minor`, `major`). Менеджер ставит его, когда заводит фичу, из просьбы
  владельца («это в 2.0») или по умолчанию `minor` для фичи и `patch` для
  задачи вне фич. Владелец видит и правит его на карточке фичи, как тип
  задачи. Разряд выпуска — наибольший вклад среди вошедших фич.
- **`auto`** — без плана: по типам вошедших задач (`feature` → `minor`,
  остальное → `patch`). `major` в `auto` не выбирается никогда: он только
  плановый или ручной.
- **фиксированный разряд** — для целей, где версия ничего не значит.

У плана есть ещё один смысл: **выпуск с целью.** Владелец может завести
план «2.0 = фичи E-4, E-5, E-7» (панель выпусков, §11, или просьба
менеджеру). Тогда у цели появляется открытый план. Повод `epic.done` для
фичи из плана не выпускает, пока не закрыты все фичи плана; ручной выпуск —
выпускает то, что есть, и спрашивает, закрывать ли план или оставить
открытым на следующий выпуск. Фичи вне плана в такой выпуск входят, если их
код уже в основной ветке, — выпуск делается по SHA, а не по списку, и
делать вид, что их нет, значит врать в заметках.

### 6.3 Где версия записывается

У цели с `bump` узел `bump` подставляет версию в команду, коммитит результат
и `CHANGELOG.md` (если файл есть в корне) одним коммитом «Выпуск <цель>
<версия>» в основную ветку, и SHA выпуска становится этим коммитом. Без
`bump` версия живёт только в теге и в записи выпуска. Для iOS `bump` — это
`agvtool new-marketing-version {version} && agvtool new-version -all {build}`
или то же внутри Fastfile; тогда `bump` у цели пустой, а версию и номер
команда получает из окружения (§7.2).

## 7. Сборка и наблюдение

### 7.1 CI (`push`, `tag`)

`watch` ищет прогоны CI по SHA выпуска. Для GitHub — через тот же токен,
что у пулл-реквестов (`github.ts`): прогоны Actions по `head_sha` и
проверки коммита. Ждёт, пока все станут завершёнными, с опросом раз в
30 секунд и общим пределом `timeoutMin`.

- Все зелёные → `pass`, артефакт — ссылки на прогоны и на релиз, если тег
  его создал.
- Любой красный → `fail`, артефакт — имя упавшей работы и хвост её лога
  (`gh run view --log-failed` или API логов).
- За первые 3 минуты не появилось ни одного прогона → `pass` с пометкой «CI
  на этот коммит не запускался»: у ветки может не быть CI, и ждать час
  нечего. Если у цели стоит `ci: 'required'`, то `fail`.
- Нет GitHub (локальный репозиторий, другой хостинг) → сразу `pass` с той же
  пометкой. Наблюдение за другими CI — §13.

Наблюдение переживает перезапуск офиса: на узле `watch` ничего не
запускается, только читается статус, поэтому надзор перезапускает прогон с
этого же узла.

### 7.2 Локальная сборка (`command`)

iOS собирается на этой машине: Xcode, сертификаты и ключ App Store Connect
уже здесь, а macOS-раннер в CI — отдельная настройка и отдельные деньги.

- **Рабочая копия выпуска.** Команда запускается не в основной копии
  проекта и не в копии задачи, а в отдельной `<копии офиса>/_release/<цель>`
  — git worktree, сброшенный на SHA выпуска. Основная копия в это время
  может меняться слияниями, а собирать надо ровно снимок. Копия
  переиспользуется между выпусками: DerivedData и поды не скачиваются
  заново.
- **Окружение.** Команда получает в окружении:
  `OFFICE_RELEASE_VERSION`, `OFFICE_RELEASE_BUILD`, `OFFICE_RELEASE_SHA`,
  `OFFICE_RELEASE_NOTES` (путь к файлу с заметками — для «What to Test»),
  `OFFICE_RELEASE_TARGET`. Остальное окружение — как у проверок
  (`projectEnv`).
- **Результат.** Код выхода решает `pass` / `fail`. Если последняя строка
  вывода — `OFFICE_RESULT {json}`, офис берёт оттуда номер сборки, ссылку и
  текст для чата: так Fastfile сообщает «сборка 58 загружена», а офис не
  парсит вывод fastlane.
- **Таймаут** — `timeoutMin` цели вместо 5 минут `CHECK_TIMEOUT_MS`.
  `runProjectCheck` получает таймаут параметром.
- **Офис закрыли посреди сборки.** Процесс команды умирает вместе с
  сервером. При перезапуске прогон на узле `build` начинается заново с
  новым номером сборки: номер, который мог успеть уйти в TestFlight,
  повторять нельзя. Узел помечается «прервано», а не «упало», и `fix` не
  зовётся.
- **Пауза офиса** не прерывает идущую сборку (убить `xcodebuild` на 90% —
  потерять полчаса), но следующий узел не стартует, пока пауза не снята.

### 7.3 Починка

`fix` получает не транскрипт и не весь лог, а артефакт `watch` или `build`:
имя упавшего шага и хвост вывода (4000 символов, как у проверок), плюс SHA и
цель. Исполнитель выбирается по способностям, как в любом `step`; с
`code.write` — тот, кто последним сливал в диапазон выпуска, если свободен.
Он работает в ветке, начатой от SHA выпуска, а не от свежей основной. Ветка
проходит обычный конвейер (`feature.json`: ревью, проверки, слияние в
основную), так что починка не теряется для следующих выпусков. Когда она
принята, офис собирает ветку `release/<цель>/<версия>`: снимок плюс эта
ветка. Её вершина становится новым SHA выпуска, и прогон идёт на `ship`
заново.

Почему `ship`, а не `snapshot`: заметки и согласие владельца уже есть, а
починка сборки не меняет того, что выпускается по смыслу. Если в основную
ветку за это время слилось что-то ещё, оно в выпуск не попадает. Иначе
согласие владельца оказалось бы согласием на то, чего он не видел. Если
ветка починки не ложится на снимок без конфликта, это второе падение:
`stuck`, задача, перезапуск с `snapshot`.

## 8. Секреты и права

Выпуск — первое, что офис делает наружу за пределами git: грузит сборку
тестировщикам, обновляет стенд. Отсюда правила:

- **Офис не хранит секретов выпуска.** Ни в `state.json`, ни в настройках.
  Команда цели берёт их, откуда умеет: связка ключей macOS, `.env` вне
  репозитория, `fastlane match`. Для CI секреты — секреты CI.
- **Команды выпуска запускает офис, а не агент.** Узлы `push`, `tag`,
  `build` — это `check`, у них нет модели. Агент в `fix` получает лог, но не
  окружение сборки.
- **Агентам запрещено выпускать в обход процесса.** В правилах разрешений
  (`permissions.ts`) у всех ролей запрещены: пуш тегов, пуш в ветки целей
  `push`, команды из `release.targets[].run` и их очевидные формы (`fastlane`,
  `xcrun altool`, `xcrun notarytool`, `gh release`). Это защита от случайного
  «сейчас сам и выложу», а не изоляция: у агента есть оболочка, и
  настоящая граница — то, что ключи лежат не в проекте.
- **Лог сборки очищается от строк, похожих на секреты**, прежде чем уйти в
  промпт `fix`, в чат или в задачу: те же шаблоны, что у проверки пакетов
  (`scrubSecrets` в `releases.ts`: известные префиксы токенов, `token=…`,
  `password: …`, заголовки авторизации, закрытые ключи целиком).

## 9. Выпуск как предмет

### 9.1 Состояние

```ts
interface Release {
  id: string;                  // 'testflight/1.4.0+58'
  targetId: string;
  version: string | null;      // null у схемы 'none'
  build: number | null;
  sha: string;                 // что выпускаем
  fromSha: string | null;      // прошлый выпуск этой цели
  epicIds: string[];           // фичи, вошедшие в диапазон
  taskIds: string[];
  planId: string | null;       // план выпуска (§6.2), если был
  notes: string;
  reason: 'manual' | 'epic.done' | 'merged';
  status: 'preparing' | 'waiting' | 'building' | 'done' | 'failed' | 'skipped';
  links: Array<{ title: string; url: string }>;
  startedAt: number;
  finishedAt: number | null;
  costUsd: number;             // notes + fix; сборка бесплатна
}
```

`Run.subject` получает поле `releaseId`. Прогон выпуска — один на выпуск, как
у задачи один прогон на задачу. Выпуски хранятся все (их немного), а не
последние 20, как прогоны процессов офиса: история версий — это то, что
смотрят через полгода.

### 9.2 Перезапуск

Надзор перезапускает вставший выпуск по тем же правилам, что прогоны задач:
с узла, с паузами, с пределом попыток. Исключения:

- `stuck` после исчерпанной петли `fix` — только владелец или менеджер,
  инструментом `resume_release(id)`, и с узла `snapshot`.
- `approve` с ответом «нет» — выпуск `skipped`, не перезапускается; повод
  запоминается, и следующий повод предложит выпуск заново с новым диапазоном.

## 10. Что меняется в движке

### 10.1 Триггеры

```ts
| { on: 'release.due' }     // у цели наступил повод по политике или просьба
```

`release.json` слушает `release.due`; ручной выпуск идёт тем же файлом.
Поводы проверяет надзор тем же проходом, что остальные триггеры по
состоянию (`tickReleases`): цели, их политики, последние выпуски, закрытые
фичи и счётчик слияний. Отдельного события «фича закрыта» нет — хватает
состояния фичи. Так политику не надо дублировать в триггере файла: файл
один, а поводов — сколько целей.

`manual` получает, наконец, вызывающего: кнопку в интерфейсе и инструмент
менеджера `start_release`.

### 10.2 Действия

Новые `office:*` в каталоге действий: `release-snapshot`,
`release-version`, `release-bump`, `release-kind`, `release-push`,
`release-tag`, `ci-watch`, `fix-build`, `release-publish`. Хозяин прогона —
новый модуль `releases.ts` (как `review.ts` у задач и `flows.ts` у офиса):
контекст узла, исполнители, обработчик `stuck`.

### 10.3 Проверки проекта

`runProjectCheck(cwd, command, lang, { timeoutMs, env })` — два необязательных
параметра. Остальные вызовы не меняются.

## 11. Что видно человеку

- **Панель «Выпуски»** — рядом с «Процессами». Цели карточками: вид,
  политика, последний выпуск (версия, когда, ссылка), что накопилось с него
  (фичи и число задач), кнопка «Выпустить». Под целью — история выпусков и
  открытый план, если есть.
- **Выпуск в работе** — прогон на графе процесса, как у задач; стадия видна
  и на карточке цели: «собирается, 12 мин из 60».
- **Чат.** Одно сообщение на выпуск: начали (с поводом), готово (версия и
  ссылки) или встал (что упало, что сделано). Промежуточные узлы в чат не
  пишут.
- **Вопрос владельцу** при `approve`: версия, разряд и откуда он (план или
  состав), список фич, заметки. Ответы — «выпускай», «не сейчас» и правка
  версии текстом.
- **Вклад фичи** — цель и разряд у каждой фичи, на вкладке «Планы» панели
  выпусков и инструментом менеджера `set_feature_release` (§6.2).
- **Настройка целей** — в настройках проекта, полями, с проверкой до
  сохранения, как свои проверки. Первую настройку можно поручить офису
  (§12, фаза 3): это обычная задача.

## 12. Порядок работ

| Фаза | Что | Критерий |
|---|---|---|
| 1 | `Release` и `releases.ts`; цели `push` и `tag`; `release.json` без `watch` и `fix`; повод `manual` — кнопка и `start_release`; схема `semver` с `level: patch/minor/major` и `auto`; `bump`; заметки; `approve: always/never` | сам офис выпускается кнопкой: версия, changelog, тег, пуш, черновик релиза собирает `release.yml` |
| 2 | `watch` по GitHub Actions; петля `fix` с `max: 1` и задача при втором падении; поводы `epic.done` и `merged`, `cooldownHours`, `approve: major`; `release.due` в надзоре; режим инициативы `off` | закрытая фича сама выкатывает стенд демо-проекта; упавший CI чинится или становится задачей |
| 3 | цель `command`: рабочая копия выпуска, окружение, `OFFICE_RESULT`, таймаут цели, прерывание при закрытии, одна локальная сборка на машину; схема `semver+build`; запреты в `permissions.ts`, очистка логов | iOS-проект уходит в TestFlight по просьбе в чате, номер сборки растёт, заметки попадают в «What to Test» |
| 4 | Планирование: поле `release` у фичи, `level: plan`, планы выпусков, панель «Выпуски» с историей и планами | «2.0 = E-4, E-5» выпускается, когда обе закрыты, с разрядом `major` и одним вопросом владельцу |

Тесты — отдельный `test:releases` на настоящем git с голым origin рядом и
подставными CI и заметками: тег с согласием, пуш с починкой, остановка
после второго падения, сборка командой-заглушкой, печатающей `OFFICE_RESULT`
и падающей по флагу, поводы, план, перезапуск. Настоящий TestFlight в тестах
не участвует.

## 13. Что оставляем на потом

- **Другие CI** — GitLab, Bitrise, Xcode Cloud: другой `office:ci-watch`, узел
  тот же.
- **Откат.** «Стенд сломан — верни прошлый» — выпуск прошлого SHA по той же
  цели. Нужен флаг в `start_release`, процесс тот же.
- **Проверка после выпуска.** Смок-тест стенда после пуша — ещё один `check`
  после `watch`. Появится, когда у проектов появятся такие команды.
- **Внешние тестировщики и стор.** Отправка на ревью App Store — отдельная
  цель с `approve: always` и своей командой; процесс тот же.
- **Выпуск в пакете.** Пакет «iOS-инженер» с маркета приносит цель
  `testflight` и Fastfile-шаблон (workflows §11, процесс в пакете).

## 14. Решённые вопросы

### 14.1 Автовыпуск настраивается по цели

Ответ на «выпускать ли самому» разный для стенда и для TestFlight, поэтому
это политика цели (§5), а не режим офиса. Режим инициативы только
выключает автоматические поводы целиком.

### 14.2 Упала сборка — одна попытка, потом задача

Петля `fail → fix` с `max: 1`. Вторая неудача — `stuck` с решением и задача
с логом на доске. Больше одной попытки внутри выпуска — это уже работа, а
работа видна на доске, а не в прогоне.

### 14.3 iOS собирается локально

Xcode, подпись и ключ стора уже на машине владельца. CI с macOS — §13.
Цена решения: офис должен быть открыт всю сборку, и одна локальная сборка
на машину за раз.

### 14.4 Версия планируется, а не угадывается

Разряд берётся из плана фичи или выпуска. `auto` — запасной путь без плана и
никогда не выбирает `major`.

### 14.5 Починка идёт от снимка, а не от свежей основной ветки

Владелец согласился на конкретный состав. Починка собирается поверх снимка
в ветке выпуска, и новое из основной ветки в этот выпуск не попадает (§7.3).

## 15. Как сделано: что разошлось с черновиком

- **Красная основная ветка.** Отдельной проверки в `snapshot` нет: пред-merge
  гейт (`premerge.ts`) и так не пускает в основную ветку то, что не
  собирается, а своей памяти «последняя проверка упала» у офиса нет.
- **Пусто — это «нет своих коммитов».** После выпуска в основной ветке
  остаётся слияние ветки выпуска; `snapshot` считает диапазон через
  `rev-list --no-merges` и такой хвост за новое не принимает.
- **Первый выпуск цели с тегами** считается от последнего подходящего тега:
  выпуски до настройки были, просто руками. У других целей первый выпуск
  берёт в заметки последние 50 задач.
- **Ответ владельца.** «Выпускай», «ship it» и всё, что понимает
  согласование, — «да». Версия в ответе («давай 2.0.0») — «да» с этой
  версией. Остальное и снятый вопрос — выпуск пропущен.
- **Починка — обычная задача.** `fix` заводит задачу с полем `forkFrom` —
  веткой выпуска. Рабочая копия ответвляется от неё, конвейер `feature`
  вливает работу в неё же (база задачи — ветка выпуска), а `publish` потом
  вливает ветку выпуска в основную. Прогон ждёт задачу опросом и после
  перезапуска находит ту же (`Release.fixTaskId`).
- **Тег на повторе** ставится заново (`-f`) только своим же выпуском: на
  первой попытке занятый тег — ошибка с решением (§6), а не перезапись чужого.
- **План закрывается сам**, когда все его фичи вошли в выпуск; иначе он
  остаётся открытым, и в чат уходит одна строка об этом. Вопроса «закрыть
  ли» нет — лишний вопрос владельцу дороже, чем кнопка «Закрыть без выпуска».
- **Инструменты менеджера:** `release_status`, `start_release`,
  `resume_release`, `plan_release`, `close_release_plan`,
  `set_feature_release`.
- **Повтор вставшего** — три попытки с паузами 1, 5 и 15 минут и только у
  последнего выпуска цели; выпуск, ждущий решения, надзор не трогает.

## 16. Цель выпуска по описанию владельца

Владелец не обязан заполнять форму: он пишет менеджеру, как хочет выпускать
(«стенд после каждой фичи», «TestFlight только по моей просьбе и с моим
согласием»), и менеджер переводит это в цель инструментом
`propose_release_target`.

- **Цель применяет владелец, а не менеджер.** Цель — право офиса выкладывать
  наружу. Предложение уходит вопросом в «Жизнь офиса» с целью словами: куда,
  когда, с чьего согласия, какая команда. «Применить» — цель и команда
  сборки ложатся в настройки; «Нет» или снятый вопрос — ничего не меняется.
- **Проверка до вопроса.** Предложение разбирается тем же
  `parseReleaseConfig`, что форма в панели. Ошибка возвращается менеджеру, а
  не владельцу: вопросов с невыполнимой целью не бывает. При применении
  настройка проверяется ещё раз — она могла поменяться, пока ждали ответа.
- **Команда сборки** цели `command` приходит вместе с целью и ложится в
  проверки проекта под именем цели.
- **Ожидание задачи.** Если в проекте нет Fastfile или workflow CI, менеджер
  сначала заводит задачу инженеру и передаёт её id (`waitForTask`). После
  «да» цель применяется, когда задача влита; задача провалилась — цель не
  применяется, и об этом говорится владельцу и менеджеру.
- **Повторное предложение той же цели** снимает прежний вопрос: владелец
  отвечает на последнее.
- **Не угадывать.** Бриф менеджера велит спрашивать то, чего владелец не
  сказал (ветку CI, команду сборки, нужна ли подпись), а не заполнять
  умолчаниями.

Предложения хранятся в состоянии офиса (`releaseSetups`, ключ — id вопроса)
и доводятся до итога по ответу и из надзора (`settleReleaseSetups`): ответ
мог прийти, пока сервер лежал, а задача — слиться позже.

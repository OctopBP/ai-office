# T-510. Скилы для дизайн-агента: разбор статьи и план правок

Источник: Anthropic Academy, «Elevate Claude's design using skills»
(https://academy.claude.com/use-cases/elevate-claudes-design-using-skills).
Документ — только план. Пакет `packages/@office/design/` в этой задаче не менялся.
Ядро (`design-critique`, раздел H в `ui-self-check`, строки брифа, версия 0.2.0) реализовано в T-512.

## 1. Статья своими словами

Идея: дать Claude скил «встроенного арт-директора», который срабатывает на любой
запрос с визуальным результатом (презентация, дашборд, HTML, PDF) и не даёт отдать
первую функциональную версию. Сначала получается рабочий вариант, потом он проходит
доработку. Пользователь видит итог, а не процесс — если сам не попросит.

Устройство скила: один `SKILL.md` (метаданные + короткая инструкция) и пять
справочных файлов, которые читаются по необходимости (progressive disclosure:
сначала только имя и описание, потом тело, потом справочники).

| Файл | Что внутри |
|---|---|
| `DESIGN_INTERROGATION.md` | Пять уровней допроса своей работы: зачем это нужно (первые принципы); разбор элементов — шрифт, цвет, сетка, отступы; сверка с примерами; насколько это не шаблон; тест на удаление («что можно убрать?») |
| `TECHNIQUE_CATALOG.md` | Каталог конкретных приёмов (в статье — «400+»), сгруппированных по эффекту: типографика как форма, цвет, глубина, фактура, движение, композиция. Правило: взять 1–2 приёма и применить сильно, а не десять слабо |
| `REFERENCE_LIBRARY.md` | Эталоны: современные продукты (Stripe, Linear, Airbnb), школы (Bauhaus, Swiss), природные закономерности, проверенные пары шрифтов. Опора на образец вместо усреднённого шаблона |
| `ELEVATION_PROTOCOL.md` | Порядок из 8 фаз: оценка основы → допрос → выбор приёмов → сверка с эталонами → дисциплинированное применение → проверка сдержанности → финальная полировка → подтверждение, что результат не типовой |
| `DESIGN_PHILOSOPHY.md` | Баланс смелости и сдержанности: когда рисковать, когда нет; мастерство видно в деталях; своеобразие ≠ перегруженность; хороший результат выглядит «неизбежным» |

Ключевые приёмы, которые мы забираем:

1. **Тонкое тело + справочники по требованию.** В описании скила — точные триггеры, детали лежат в соседних файлах.
2. **Допрос вместо «сделай красиво».** Конкретные вопросы по каждому элементу, ответы фиксируются.
3. **Тест на удаление и проверка сдержанности** — борьба с украшательством.
4. **Один-два сильных приёма**, а не набор слабых.
5. **Эталоны вместо абстрактных советов**: «как у Linear» проверяемее, чем «современно».
6. **Протокол с фазами** — результат проходит один и тот же путь каждый раз.
7. **Невидимость процесса**: рассуждение не попадает в ответ, если его не просили.

Важная оговорка: статья описывает универсальный скил для свободного визуального
вывода, где дизайн-системы нет. У нас система есть и жёсткая (токены, кит), поэтому
механически переносить каталог из 400+ приёмов нельзя — он будет спорить с
`tokens.css`.

## 2. Текущее состояние пакета `@office/design`

Состав: `agent.json`, `.claude-plugin/plugin.json` (v0.1.0), `brief/ru.md` и `brief/en.md`
(по ~35 строк), `bench/cases.json` (3 случая), 4 скила.

**agent.json.** Модель `sonnet`, инструменты Read/Write/Edit/Glob/Grep/Bash/WebSearch/WebFetch/TodoWrite/Artifact,
`ask-risky`, изоляция вкл.; три MCP-сервера (figma-bridge, figma-console, penpot) с `alwaysLoad`;
`builtin: ["design", "artifact-capabilities"]`. Поля `skills` (фильтр) и `use` (чужие плагины) нет —
значит, грузятся все скилы пакета. Тег `penpot` есть, а скила для Penpot нет.

**Бриф** (грузится в системный промпт целиком). Роль и границы; «макет показывай макетом»;
обязательный проход `ui-self-check` с вердиктом по разделам; 16 правил офиса (пересчитано по `brief/ru.md` на 2026-10-09) (контраст,
фокус, токены, состояния, тексты, анимация, деструктив, Figma); блок «Макет в Figma».
Всё — про корректность и дисциплину. Про вкус, замысел и «не шаблонность» нет ни слова.
Часть правил дублирует `ui-standards`/`ui-self-check` (контраст, размеры, токены).

**Скилы:**

| Скил | Что делает | Замечания |
|---|---|---|
| `ui-standards` | Справочник чисел: WCAG 2.2 AA, Nielsen, сетка, шкала шрифтов, состояния, движение | Хороший, измеримый. В шапке уже сказано, что токены проекта важнее общих значений, и есть ссылка на `tokens.css`; но быстрой таблицы «роль → токен/класс кита» нет — приходится читать CSS |
| `ui-self-check` | Обязательный чек-лист A–G (токены, доступность, состояния, Нильсен, тексты, Figma, разметка) | Проверяет соответствие, но не качество решения: нет вопроса «зачем» и «что убрать» |
| `figma-screen` | Порядок работы с мостом, автолейаут, ноды, верификация скриншотом | Длинный, но по делу; про Penpot ничего |
| `figma-tokens` | Переменные и стили файла вместо выдуманных значений; привязка | По делу |

**Бенч** (`bench/cases.json`): проверяет только срабатывание `figma-screen`/`figma-tokens`
и отсутствие срабатывания без Figma. Скилов `ui-standards` и `ui-self-check` в нём нет.

**Контекст проекта.** `tokens.css`: шкала `--space-1..8` (4–32 px), радиусы, шрифты Inter/Sora,
темы `day`/`night`, палитра `--accent-1..8`, слои `--z-*`. `kit.css` — готовые элементы.
Дизайн-спеки в `docs/design/<задача>/` и тематических папках. Проект сам определяет
визуальный язык — свободы «выбрать шрифт и палитру» у агента нет.

## 4. План правок пакета

### 4.1. Новые скилы

**`design-critique`** (главный, аналог Elevation Protocol + Interrogation)
- Назначение: перед сдачей любого визуального результата и после первой рабочей версии — проверить замысел и убрать лишнее. Идёт ДО `ui-self-check`.
- Триггеры (`description`): сделать/нарисовать/собрать экран, макет, лендинг, презентацию, дашборд, артефакт, иллюстративную страницу; «улучши вид», «выглядит скучно/шаблонно», «отполируй»; любой результат, который увидит пользователь.
- Тело (тонкое, ≤ 80 строк): порядок из 5 шагов — (1) одна фраза замысла: для кого, что главное на экране; (2) допрос по элементам: зачем этот блок, что будет, если убрать; (3) выбрать 1–2 сильных приёма (`design-moves`), остальное — по кит-у; (4) проверка сдержанности: тест на удаление, сверка с `ai-tells`; (5) передать в `ui-self-check`. Процесс в отчёт не выносить — только замысел одной фразой и список убранного.
- Справочники рядом: `reference/interrogation.md` (вопросы по пяти уровням, адаптированные под наш UI), `reference/ai-tells.md` (штампы), `reference/philosophy.md` (смелость vs сдержанность, «выглядит неизбежным»).

**`design-moves`** (каталог приёмов, сжатый)
- Назначение: конкретные приёмы для свободных поверхностей, где токены не диктуют всё (презентации, лендинги, пустые состояния, заставки, артефакты).
- Триггеры: нужен «акцент», «характер», «выразительность»; вопрос «как сделать менее шаблонно» вне интерфейса офиса. Для экранов самого офиса не применять — там работает кит.
- Содержание: ~20 приёмов по группам (типографика как форма: контраст кеглей, крупная цифра; цвет: один акцент на нейтрали; глубина: слои и тени из токенов; ритм и пустота; композиция: асимметрия, сильная ось; микродвижение ≤ 300 мс). У каждого: когда, как применить в наших токенах, чего избегать. Правило «один–два приёма на экран».

**`ui-tokens-map`** (карта токенов под рукой)
- Назначение: быстро ответить «какой токен или класс кита взять» без чтения 229 + 237 строк CSS.
- Триггеры: выбор цвета, отступа, радиуса, шрифта, слоя; «какой компонент из кита».
- Содержание: таблица роль → токен (`--space-*`, `--radius-*`, `--ink*`, `--accent-*`, `--z-*`, шрифты), классы `kit.css` с назначением, отличия тем `day`/`night`, ссылка на стенд `?kit=1`. Обновлять при изменении CSS; в скиле указать дату сверки и команду для проверки (`npm run test:contrast`). Чтобы карта не устаревала, правило: источник истины — CSS, скил — указатель.

**`penpot-canvas`** (закрывает дыру)
- Назначение: порядок работы с Penpot через `mcp__penpot__*`: `high_level_overview`, `execute_code`, возвращать только нужное, `export_shape`, одна вкладка MCP, запись на текущую страницу.
- Триггеры: «нарисуй в Penpot», «макет в Penpot», пилот Penpot (см. `docs/design/T-383`, `docs/design/penpot-mcp/setup.md`).
- Содержание: стартовая последовательность, привязка к токенам, проверка скриншотом, что делать при отсутствии подключения.

### 4.2. Правки существующих скилов

- `ui-self-check`: в начало добавить «Разделы A–G проверяют соответствие; замысел и сдержанность — в `design-critique`, пройти его раньше». Добавить раздел H «Сдержанность» из двух пунктов (что убрано; ни один штамп из `ai-tells` не остался). Остальное не трогать.
- `ui-standards`: в шапке отсылка на `ui-tokens-map`; убрать повтор общего (если число дублируется в брифе — оставить здесь).
- `figma-screen`: в шаге «Verify» добавить ссылку на `design-critique`; вынести длинные разделы («Text», «Colour and radius») в `reference/` — отдельной задачей, не блокирует.

### 4.3. Бриф (`brief/ru.md` и `brief/en.md` вместе)

- Добавить в начало (3–4 строки): «Хороший экран — не только соответствующий нормам, но и осмысленный. Перед сдачей визуального результата пройди `design-critique` (замысел, лишнее, штампы), затем `ui-self-check`. В отчёте — замысел одной фразой».
- Правило «смелость там, где свобода»: для интерфейса офиса следуй кит-у и токенам; выразительные приёмы (`design-moves`) — только для презентаций, артефактов, лендингов.

- Добавить строку про Penpot: «Макет в Penpot — скил `penpot-canvas`».
- Следить за паритетом ru/en.

### 4.4. `agent.json` и плагин

- `builtin` и `servers` не меняются; `skills` (фильтр) не добавлять — все скилы пакета должны грузиться.
- `summary` (ru/en): добавить «замысел и критика» — коротко: «…экраны, состояния, тексты; критика замысла; Figma и Penpot».
- Теги: добавить `critique`, `design-system`.
- Версия: поднять в `.claude-plugin/plugin.json` с 0.1.0 до 0.2.0; описание — не только Figma-мост, но и критика, токены, Penpot. Если в манифесте есть версия — синхронизировать.
- Модель: оставить `sonnet`. Критика дешёвая и прогоняется внутри той же сессии; отдельная модель для неё не нужна.

### 4.5. Бенч (`bench/cases.json`)

Добавить случаи: «улучши вид страницы, выглядит шаблонно» → `design-critique`; «какой токен для отступа между карточками» → `ui-tokens-map`; «собери слайд презентации с акцентом» → `design-moves`; «нарисуй форму в Penpot» → `penpot-canvas`; «поправь тест в backend» → ничего из дизайн-скилов (`avoid`). Существующие три не менять.

## 5. Риски и порядок внедрения

Риски: раздувание контекста (каждый скил — это описание в промпте; держим описания ≤ 2 предложений, тело тонким); конфликт «смелости» с китом (снимает оговорка про свободные поверхности); устаревание `ui-tokens-map` (источник истины — CSS).

Порядок: (1) `design-critique` + правка брифа и `ui-self-check` — максимальный эффект; (2) `ui-tokens-map`; (3) `penpot-canvas`; (4) `design-moves`; (5) бенч и версия. После каждого шага — `office-agent` стенд на бенче, затем сверка, что срабатывают нужные скилы и не срабатывают лишние.

Открытое: у нас нет метрики «стало красивее» — оценивать придётся глазами владельца на 3–5 типовых задачах до/после (сравнить экран настроек и страницу-артефакт).


## 6. Допущения и решения, которых ждём от владельца

Что взято из статьи, а что придумано нами — чтобы реализация не выдавала второе за первое.

**Из статьи** (прочитана через WebFetch, то есть в сжатом пересказе, а не полным текстом): скил `design-elevation` = `SKILL.md` + пять справочников (допрос в 5 уровней с тестом на удаление, каталог приёмов — «400+», эталоны, 8-фазный протокол, философия); срабатывает сам на визуальные запросы; справочники грузятся по надобности. Тела справочников недоступны, поэтому вопросы допроса и фазы протокола в плане адаптированы по смыслу, а не по тексту: при реализации формулировки пишем сами.

**Наши допущения (в статье нет):**
- список штампов «AI-вида» в `ai-tells.md`;
- скил `penpot-canvas` (закрывает пробел пакета: тег и сервер есть, скила нет);
- скил `ui-tokens-map` и разгрузка брифа от чисел, дублирующих `ui-standards`;
- порог «до ~20 приёмов» в `design-moves` и «≤ 80 строк» для тела `design-critique`.

**Что не проверено:** срабатывание новых описаний скилов неизвестно до реализации и прогона бенча. Метрики «стало лучше» нет — оценка глазами владельца на 3–5 задачах до/после.

**Решение владельца до старта:** делаем ядро — `design-critique` + правка брифа и `ui-self-check` (шаг 1 порядка) — это прямо из статьи. Остальное (`ui-tokens-map`, `penpot-canvas`, `design-moves`, сокращение брифа) — по отдельному согласию; вопрос поставлен владельцу (допущение: начинаем с ядра, остальное откладываем).

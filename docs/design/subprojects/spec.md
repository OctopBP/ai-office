# Подпроекты: зоны ответственности в офисе

Статус: спека, кода нет. Задача T-443. Решения владельца от 2026-10-07 (§1)
не пересматриваются; всё остальное — предложение, которое можно оспорить.

## Зачем

Владелец ведёт один большой проект, а внутри него живут несколько частей:
бэкенд, фронтенд, вспомогательные. Ему нужны зоны ответственности: часть
сотрудников закреплена только за бэкендом, часть только за фронтендом, кто-то
работает в обоих. У каждой части свои задачи, своя документация и свои правила.

Сегодня в офисе есть только половина этого — поле роли «Репозиторий роли»
(`Role.repoDir`). Оно разводит роли по репозиториям, но:

- не умеет разделить **один** репозиторий: две папки одного монорепо для офиса —
  одна и та же зона (об этом прямо пишет `docs/design/rules/spec.md`: «два
  направления в одном репозитории так не разделить»);
- привязывает репозиторий к **роли**, а не к работе: универсал, который должен
  уметь и в бэкенд, и во фронтенд, работать в двух репозиториях не может;
- ничего не запрещает: роль без `repoDir` правит что угодно в общем репозитории.

Подпроект — это одна сущность вместо трёх полумер: зона кода, закрепление людей
и область документов и правил.

---

## 1. Решения владельца

1. Подпроект бывает двух видов, оба поддерживаются: **папка внутри репозитория
   офиса** (`server/`, `web/`) или **отдельный репозиторий**.
2. **Закрепление жёсткое, многие-ко-многим.** У роли есть список подпроектов, и
   задачу чужого подпроекта она не получает никогда. Пустой список — «весь
   проект»: так работают все существующие офисы, и их нельзя сломать.
3. **Чужой код читать можно, менять нельзя.** Для подпроекта-папки нарушение
   ловится проверяемо (механизм — §5).
4. **Вложенности нет**, один уровень.

---

## 2. Модель данных

### 2.1. Подпроект

Подпроекты лежат в состоянии офиса (`state.json`) отдельным списком рядом с
ролями, а не в настройках: это не ручка поведения, а структура офиса, и на неё
ссылаются задачи, роли и документы.

```ts
// src/shared/types.ts

/**
 * Вид подпроекта.
 * - `folder` — папка внутри репозитория офиса (`state.projectDir`);
 * - `repo`   — отдельный git-репозиторий целиком.
 */
export type SubprojectKind = 'folder' | 'repo';

export interface Subproject {
  /**
   * Латиница, цифры и дефис, до 24 символов (`slugifyRoleId`). Неизменяем:
   * на него ссылаются задачи, роли, документы и круг правил `sub:<id>`.
   * Переименование — это поле `name`.
   */
  id: string;
  /** Как зону называет человек: «Сервер», «Веб». */
  name: string;
  kind: SubprojectKind;
  /**
   * Корень зоны.
   * folder — путь от корня репозитория офиса через `/`, без `..`, без ведущего
   *          и хвостового слеша: `server`, `apps/web`. Пустой корень запрещён:
   *          «весь репозиторий» — это отсутствие подпроекта, а не подпроект.
   * repo   — путь к репозиторию, абсолютный или от директории офиса (как
   *          нынешний `Role.repoDir`). Обязан быть корнем git (`rev-parse
   *          --show-toplevel` совпадает с путём).
   */
  root: string;
  /** Одна строка: что это за зона. Едет менеджеру в список подпроектов. */
  summary: string;
  /** Цвет зоны из единой палитры `--accent-1..8`: бейдж задачи, пол в 3D. */
  color: string;
  /**
   * Свой набор проверок слияния — готовые команды, как `Settings.mergeChecks`.
   * Нет поля — общий набор офиса. Пустой список — «не гонять ничего».
   * У папки команды идут с рабочей директорией в корне зоны на слитом дереве,
   * у репозитория — в корне его копии.
   */
  mergeChecks?: string[];
  /**
   * Только folder: пути ВНЕ корня, которые задачам этой зоны разрешено
   * менять. Шаблоны git pathspec от корня репозитория: `package-lock.json`,
   * `package.json`. Нужны монорепо, где у зон общий lock-файл. Нет поля —
   * правится только корень.
   */
  sharedPaths?: string[];
  createdAt: number;
}

/** Подпроект для веба и инструментов: с посчитанным и проверенным. */
export interface SubprojectView extends Subproject {
  /** Абсолютный путь репозитория, где живут ветки задач этой зоны. */
  repoDir: string;
  /** Абсолютный путь корня зоны. У repo совпадает с `repoDir`. */
  path: string;
  /** Кто закреплён: роли, у которых id есть в `Role.subprojects`. */
  members: Array<{ id: string; title: string }>;
  /** Открытых задач зоны (не done/failed/cancelled). */
  openTasks: number;
  /**
   * Что с зоной не так: папки нет, путь не корень git, корень пересёкся с
   * другой зоной. null — всё в порядке. Задачи зоны с problem не стартуют.
   */
  problem: string | null;
}
```

Сохранение: `subprojects: Subproject[]` верхним полем `state.json`; в снимок
офиса — `subprojects: SubprojectView[]`. Нет поля в сохранении — пустой список.

**Инварианты** (проверяются при создании и правке, `src/server/subprojects.ts`):

- корни не вложены друг в друга и не совпадают: у двух `folder` ни один корень
  не префикс другого по сегментам; `repo` не может лежать внутри репозитория
  офиса так, чтобы совпасть с корнем `folder` (вложенности нет, §1.4);
- у `repo` корень — не репозиторий офиса: репозиторий офиса целиком — это
  «весь проект», а не зона;
- удалить подпроект можно, только когда у него нет открытых задач; иначе отказ
  со списком задач. Закрытые задачи хранят `subprojectId` удалённой зоны и
  показываются с подписью «зона удалена» — история должна читаться.

### 2.2. Закрепление

**Источник правды один — поле роли.** Набросок предлагал ещё «участников» на
подпроекте; два списка одной связи разъедутся при первой ручной правке
`state.json`, поэтому участники только считаются (`SubprojectView.members`).

```ts
// src/server/roles.ts, interface Role
  /**
   * Подпроекты, за которыми роль закреплена. Нет поля или пусто — весь
   * проект: так работают все офисы до подпроектов. Иначе роль получает задачи
   * только этих зон — никогда чужих (docs/design/subprojects/spec.md §3).
   */
  subprojects?: string[];
```

- `subprojects` входит в `OVERRIDABLE_KEYS` и `RoleEditable`, как сейчас
  `repoDir`: у пакетов умолчания нет, закрепление — дело офиса, а не автора
  пакета, и живёт оверрайдом ссылки.
- Закрепление относится к **роли**, а не к сотруднику: «Фронтендер 2» — это
  отдельная роль, и закрепить его можно иначе, чем первого. Сотрудник (экземпляр
  роли) наследует закрепление роли.
- Менеджер (`isManager`) не закрепляется никогда: он видит весь офис.
- **Потерянный id не расширяет доступ.** Выбросить из списка роли id
  несуществующей зоны нельзя: если он был единственным, пустой список молча
  превратил бы закреплённую роль в «весь проект». Поэтому зону с
  закреплёнными ролями удалить нельзя, пока их не открепили (UI делает это
  одним действием «открепить всех и удалить»), а id, потерянный ручной правкой
  `state.json`, остаётся в списке: роль получает пометку «закреплена за
  несуществующей зоной» и задач этой зоны, понятно, не получает, пока человек
  не поправит.

### 2.3. Задача и фича

```ts
// src/shared/types.ts, interface TaskView (и Task в state.ts)
  /**
   * Зона задачи. null — «весь проект»: задача без зоны, как все задачи до
   * подпроектов. Задаётся при создании, меняется только пока задача не
   * стартовала: репозиторий фиксируется на старте (`repoDir`), и зона вместе
   * с ним.
   */
  subprojectId: string | null;
```

```ts
// src/server/plan.ts, interface PlannedTask
  /** Зона задачи. Пусто — выводится из роли (§6.1). */
  subprojectId?: string;
```

- **Одна задача — одна зона — один репозиторий.** Репозиторий задачи
  выводится из зоны, а не из роли:

  | `subprojectId` | `task.repoDir` на старте | где можно править |
  |---|---|---|
  | null | `state.projectDir` | везде |
  | folder | `state.projectDir` | `root` + `sharedPaths` |
  | repo | `resolve(root)` | весь этот репозиторий |

  Новая функция `state.repoForTask(task)` заменяет `taskOffice.repoFor(role)` в
  `startWorker` (`agents.ts`); правило «после старта путь берётся из
  `task.repoDir`» остаётся как есть.
- **Рабочая папка роли вне задачи.** `repoFor(role)` зовут не только в
  `startWorker`: ещё в четырёх местах сессия роли поднимается или описывается
  без задачи, и зоны задачи там нет. Для них вводится
  `state.repoForRole(role)` — одно правило на все четыре места, и
  `repoFor(role)` после этого из сервера уходит:

  | Место | Код сегодня | Рабочая папка |
  |---|---|---|
  | Совещание | `cwd: meetingOffice.repoFor(role)` (`agents.ts`, совещание с участниками-ролями) | `repoForRole(role)` |
  | Разговор с ролью | `cwd: talkOffice.repoFor(role)` (`agents.ts`, прямой разговор владельца с ролью) | `repoForRole(role)` |
  | `ask_colleague` | `cwd: state.repoFor(role)` в `consultRole` (`agents.ts`) | зона из `subprojectId` вопроса (§6.2); без него — `repoForRole(role)` |
  | `list_team` | `const repo = state.repoFor(role)` в описании состава команды (`agents.ts`) | `repoForRole(role)`; строка «репозиторий» по-прежнему печатается, только если папка не `projectDir` |

  Правило `repoForRole(role)`:

  | Закрепление роли | Рабочая папка |
  |---|---|
  | ровно одна зона | корень этой зоны: `resolve(root)` у repo-зоны, `projectDir/root` у folder-зоны |
  | несколько зон | корень офиса (`state.projectDir`) |
  | ни одной (универсал) | корень офиса (`state.projectDir`) |
  | одна зона, но её нет (битый `state.json`, §2.2) | корень офиса |

  Это папка, в которой сессия **читает**: совещание, разговор и консультация
  ничего не правят, а `list_team` только показывает путь. Граница правок
  (§5) задаётся задачей и сюда не относится. Для роли, мигрированной из
  «репозитория роли» (§7), правило даёт ровно прежний путь: одна repo-зона с
  тем же корнем.
- **Остальные потребители `repoFor(role)`.** Кроме `startWorker` и четырёх мест
  выше, `repoFor` зовут проверка окружения и круги правил. Им `repoForRole` не
  подходит: они спрашивают не «где сессия этой роли читает», а «какие
  репозитории и папки есть в офисе», и ответ на это — список зон, а не роли.
  Поэтому они переходят на `state.subprojects`:

  | Место | Код сегодня | После |
  |---|---|---|
  | Проверка окружения | `envcheck.ts`, цикл по `activeRoles()`: `const dir = state.repoFor(role)`, при `dir !== projectDir` — `roleRepoCheck(state, role, dir)` с id `repo:<roleId>` | цикл по **repo-зонам**: `repoProblem(resolve(root))`, id проверки `sub:<subId>`, заголовок и подсказка по имени зоны (новые ключи `env.sub.title`, `env.sub.fix` вместо `env.repo.*`). Folder-зоны git не проверяют — у них репозиторий офиса, его уже проверил `gitCheck`; пропавшая папка folder-зоны — отдельная строка `sub:<subId>` с подсказкой «папки нет» (тот же расчёт, что `SubprojectView.problem`, §2.1). Одна проверка на зону, а не на роль: две роли в одной зоне больше не дают двух одинаковых строк |
  | Круги правил: список кругов | `rules.ts`, `ruleScopes`: `dirs = roles.map((r) => state.repoFor(r))` | круги `sub:<id>` строятся из `state.subprojects` (§4.3); `repoFor` не нужен |
  | Круги правил: кто в круге | `rules.ts`, `ruleScopes`: `atDir(dir)` — роли, у которых `repoFor(r) === dir` | круг `sub:<id>` — роли, закреплённые за зоной (`role.subprojects` содержит `id`); круг `office` — **все** активные роли (правила офиса получают все, §4.3), а не только те, чья папка совпала с корнем |
  | Круги правил: свой круг исполнителя | `rules.ts`, `rulesBrief`: `const dir = role ? state.repoFor(role) : projectDir`, свой круг — `repo` с этим путём | по зоне, а не по папке: `rulesBrief(state, roleId, subprojectId)` из §4.3 — зона задачи, без задачи — все зоны роли |

  Ещё один вызов — в тестах, не в сервере: `scripts/test-setup.ts:145`
  проверяет мастер нового офиса через `state.repoFor(backends[0]) ===
  resolve(root, 'backend')`. С удалением `repoFor` тест переводится на
  `repoForRole(backends[0])` — мастер заводит repo-зону с корнем `backend` и
  закрепляет за ней нанятого (§7), значит путь тот же; если тест проверяет
  задачу, а не роль, — на `repoForTask`.

  После этих двух файлов, `startWorker` и теста у `repoFor` не остаётся вызовов, и
  он удаляется из `state.ts` вместе с чтением `Role.repoDir` (§7). Метод
  проверки пути из формы (`state.ts`, рядом с `repoFor`) остаётся: им
  валидируется корень repo-зоны.
- **`null` — это явная зона «весь проект»**, а не пропуск. В офисе с
  подпроектами она нужна для сквозной работы: корневые конфиги, `OFFICE.md`,
  CI. Её берут только роли без закрепления (§3).
- **Фича зоны не имеет.** Она может охватывать несколько подпроектов; её задачи
  — каждая в своей зоне. Связь «фронтенд ждёт API» выражается как сейчас —
  `dependsOn`: зависимость считается выполненной, когда результат в основной
  ветке **того** репозитория. У задачи-папки и задачи-папки репозиторий общий,
  у repo-зоны — свой; правило «результат в основной ветке» от этого не меняется.
- Граница правок задаётся **задачей**, а закрепление роли решает только, **кому**
  задачу можно отдать. Отсюда: универсал на задаче зоны `web` правит только
  `web/`, как и закреплённый фронтендер. Нужна правка в двух зонах — это две
  задачи (или одна задача зоны «весь проект»).

## 3. Правила назначения

### 3.1. Допуск

Одна функция на весь офис, в новом `src/server/subprojects.ts`:

```ts
/**
 * Может ли роль взять задачу этой зоны. Роль без закрепления — любую.
 * Закреплённая — только задачу своих зон; задачу «весь проект» (null) —
 * никогда: сквозная работа меняет чужой код по определению.
 */
export function admits(role: Role, subprojectId: string | null): boolean {
  if (role.isManager) return false;
  const own = role.subprojects ?? [];
  if (!own.length) return true;
  return subprojectId !== null && own.includes(subprojectId);
}

/** Почему нельзя — словами для менеджера, ленты и карточки. null — можно. */
export function admitProblem(state: OfficeState, role: Role, task: Pick<Task, 'subprojectId'>): string | null;
```

Офис **с пустым списком подпроектов** ведёт себя ровно как сейчас: у всех задач
`subprojectId: null`, у всех ролей закрепления нет, `admits` всегда истина.
Это и есть совместимость со старыми офисами (§1.2): ни одна ветка кода не
меняет поведения, пока владелец не завёл первую зону.

### 3.2. Где проверяется

Сегодня исполнителя выбирают так: роль задачи (`task.roleId`) называет
менеджер, офис берёт свободного сотрудника этой роли (`findFree ?? spawn ??
findFree`). Закрепление встаёт **проверкой допуска пары «роль × зона»** — до
выбора сотрудника. Сотрудники одной роли закреплены одинаково, поэтому выбор
внутри роли не меняется.

В таблице **14 мест**, где задаче выбирают или подтверждают исполнителя: в 13
из них появляется проверка допуска, четырнадцатое — совещание в узле процесса —
не меняется (оно не привязано к задаче, см. последнюю строку).

| Место | Код сегодня | Что меняется |
|---|---|---|
| Заведение задачи | `create_task` (`agents.ts`) | зона выводится или проверяется (§6.1); недопустимая пара — отказ инструмента со списком ролей, которым зона по силам |
| План | `plan_features` → `createPlan` (`plan.ts`) | та же проверка для каждой задачи; план целиком отклоняется, как при битой ссылке |
| Правка задачи | `edit_task` (`tasks.ts`) | смена `roleId` или `subprojectId` — повторная проверка; у стартовавшей задачи зона не меняется |
| Выпуск из плана | `releaseReady` → `agents.assign` → `officeAssign` | `officeAssign` проверяет допуск до слота; отказ — задача в backlog с пометкой (§3.3) |
| Очередь за слотом | `startWaiting` → `officeAssign` | через `officeAssign` |
| Окружение починили | `onEnvReady` → `officeAssign` | через `officeAssign` |
| Надзор: не раздали | `watchBoard` → `officeAssign` (`supervisor.ts`) | через `officeAssign` |
| Надзор: прервано перезапуском | `watchBoard` → `retryTask` | `retryTask` проверяет допуск; предпроверка `findFree(roleId)` в надзоре не меняется |
| Возобновление после лимита | `resumeTask` (`agents.ts`) | тот же сотрудник или коллега той же роли — плюс проверка допуска (роль могли перезакрепить, пока задача стояла) |
| Перезапуск | `retryTask` | проверка допуска |
| `assign_task` | инструмент менеджера (`agents.ts`, `tool('assign_task')`) | проверка допуска роли задачи; при явном `instanceId` — допуск **роли этого сотрудника**. Сверено с кодом: сегодня при явном `instanceId` берётся `state.instances.get(id)` без сверки роли сотрудника с `task.roleId`, без проверки, что это не менеджер, и с пропуском `noStaffReason`; проверяются только существование и занятость (`currentTaskId`). Сверка роли и допуска появляется здесь же, до `slotProblem` |
| Доработка после ревью | `waitForFree(state, roleId, assigneeId)` | автор и так своей роли; проверка допуска на случай перезакрепления |
| Ревью | `reviewerRole(state)`: сначала базовая роль `reviewer`, если она не в архиве; иначе — первая активная не-менеджерская роль с `code.review` | `reviewerRole(state, task)` проверяет `admits(role, task.subprojectId)` **в обеих ветках**: (1) базовая `reviewer` берётся, только если она не в архиве **и** допущена к зоне задачи; не допущена — офис не останавливается на ней, а идёт во вторую ветку (**на согласование владельцу:** переход к запасному ревьюеру вместо отказа, когда базовый `reviewer` не допущен к зоне, — предложенное поведение, а не решение владельца; альтернатива — отказ с причиной из `admitProblem`); (2) запасной вариант — первая активная не-менеджерская роль с `code.review`, **допущенная к зоне задачи**. Нет ни одной — тот же отказ, что сейчас при отсутствии ревьюера (`review.noReviewerRole` в `reviewPr`), с причиной из `admitProblem` |
| Совещание в узле процесса | исполнитель `meeting` в `flows.ts`: менеджер плюс до двух свободных сотрудников разных ролей, отсортированных по пересечению `node.needs` с `role.capabilities` | не меняется. Сверено с кодом: прогон процесса офиса (ритуал, совещание) не привязан к задаче — у него нет `taskId`, значит нет и зоны. Это разговор, а не работа над кодом, правок он не делает, допуск к нему не применяется. Итог совещания — предложения фич через `proposeFeature`; зоны у их задач проставит менеджер при заведении, и там сработает обычная проверка. Рабочая папка участников — по правилу `repoForRole` (§2.3) |

**Последний рубеж — `startWorker`.** Каждое место выше проверяет само, чтобы
отказ был внятным и дешёвым. Но данные приезжают и из правленого руками
`state.json`, поэтому `startWorker` ещё раз зовёт `admitProblem` и при отказе
не поднимает сессию: задача уходит в `blocked` с причиной в карточке. Ровно один
вызов на весь сервер, денег до него не тратится.

`noStaffReason(roleId, state)` получает зону: «в зоне «Веб» нет ни одного
сотрудника роли frontend» отличается от «роль уволена» и подсказывает менеджеру
другое действие (переназначить на допущенную роль, а не просить нанять).

### 3.3. Задача, которую некому взять

Перезакрепление роли не трогает идущие задачи: допуск проверяется на старте, а
стартовавшая сессия доработает и сдаст. Задачи в `planned`/`backlog`, ставшие
недопустимыми, не переназначаются молча: офис ставит им `attention` и один раз
пишет менеджеру (как `reportStalls` про упавшую зависимость), а в карточке —
«некому взять: роль X не закреплена за зоной Y». Фича с такой задачей получает
`hold` нового вида `unstaffed`.

### 3.4. Менеджер и раздача

Раздачу ролям по-прежнему решает менеджер: он видит список зон с закреплёнными
ролями (§6.1) и выбирает роль из допущенных. Офис не подменяет роль сам: если
менеджер назвал недопустимую, это отказ инструмента, а не тихая замена —
иначе задача уехала бы не тому, кого он имел в виду.

## 4. Документы, бриф, правила, журнал

### 4.1. Бриф зоны

Бриф зоны — файл `OFFICE.md` в корне подпроекта (`server/OFFICE.md`, корень
отдельного репозитория). Не поле в состоянии — по той же причине, что и
`RULES.md` (`docs/design/rules/spec.md`): он уезжает с кодом, виден в diff и
правится руками мимо офиса. В состоянии лежит только `summary` для списков.

В промпт исполнителя бриф зоны клеится сразу после брифа офиса, в статическую
часть до маркера кеша, с лимитом 4000 символов и подписью «Зона «Веб»
(`web/`)». Получают его сессии задач этой зоны и разговоры роли, закреплённой
ровно за одной зоной. Менеджер брифы зон не получает — только `summary`.

### 4.2. Область документов

```ts
// src/shared/types.ts, interface OfficeDoc
  /**
   * Область документа: зона, к которой он относится. Нет поля — весь офис.
   * Рабочий материал задачи наследует зону задачи.
   */
  subprojectId?: string;
```

- `ListDocsQuery` (`docs.ts`; сейчас в нём `kind`, `includeArchived`,
  `query`) получает `subprojectId?: string | 'office'`; `listDocs` фильтрует по
  нему вместе с `kind`. HTTP (`docs-api.ts`, сейчас
  `GET /api/docs?kind=&query=&archived=1`) — параметр `subproject=<id>|office`;
  тело `POST /api/docs` и `PUT /api/docs/<id>` — поле `subprojectId` (в списке
  разрешённых полей `serve`, рядом с `taskId`). `CreateDocInput` и `DocPatch` —
  то же поле.
- **Где оглавление собирается сегодня** (сверено с кодом):
  `docIndexForPrompt(office, maxChars)` строит его из `listDocs(state)` целиком,
  `docsBrief(state)` в `docs-tools.ts` оборачивает его в блок, а блок кладётся
  в **динамическую** часть системного промпта (`systemBlocks` в `agents.ts`,
  после маркера кеша, рядом с журналом) и в `projectBrief`. Ни туда, ни туда
  задача не передаётся — только `roleId`. Поэтому `docIndexForPrompt` и
  `docsBrief` получают третий аргумент `zone: string | null | undefined`
  (`undefined` — как сейчас, всё оглавление), а `systemBlocks` и
  `projectBrief` — зону сессии: зону задачи для сессий задачи, единственную
  зону роли для разговоров роли с одним закреплением, `undefined` для
  менеджера. Кеш от этого не страдает: оглавление уже стоит за маркером.
- **Оглавление в промпте** у исполнителя на задаче зоны X: основа офиса (`kind: 'foundation'` без зоны) + все неархивные документы
  зоны X. Документация и рабочие материалы офиса и чужих зон в оглавление не
  едут — они доступны через `docs_list` и `docs_read`. Задача «весь проект» и
  офис без подпроектов — оглавление как сейчас, целиком.
- Менеджер получает оглавление целиком, с подписью зоны у каждой строки.
- `docs_list` получает параметр `subproject` (`''` — своя зона и общее, `office`
  — только общее, `all` — всё, `<id>` — эта зона). Чужое **читать можно**.
  Зону сессии инструменты берут из задачи: `docTools(state, author, taskId)`
  уже получает `taskId` (сессии задачи и возобновления — `task.id`, менеджер —
  `null`), так что новый аргумент не нужен — `state.tasks.get(taskId)?.subprojectId`.
  `docs_read` не меняется.
- `docs_write`: новый документ без явной зоны ложится в зону задачи. Закреплённая
  роль не может создать или править документ чужой зоны — отказ инструмента
  («читать чужое можно, менять нельзя» распространяется и на документы).
  Документ «весь офис» правят роли без закрепления и менеджер; закреплённая роль
  — только создаёт рабочий материал своей задачи (он и так в её зоне).
- Тот же запрет у **`docs_set_kind`** (четвёртый инструмент `docTools`, сейчас
  меняет тип любого документа): сменить тип документа чужой зоны или «весь
  офис» закреплённая роль не может. Проверка одна на оба инструмента —
  `docEditProblem(state, author, taskId, doc)` в `docs-tools.ts`. Владельца
  через HTTP (`author: OWNER`) запрет не касается.
- Импорт (`importFromDir`): файлы из корня папки-зоны получают её
  `subprojectId`; повторный импорт сверяет по `source`, как сейчас.

### 4.3. Круг правил подпроекта

Кругов становится три плюс ролевой:

| Круг | id | Где лежит `RULES.md` | Кто получает |
|---|---|---|---|
| Весь офис | `office` | корень офиса | все |
| Подпроект | `sub:<id>` | корень зоны (`web/RULES.md` или корень repo-зоны) | сессии задач зоны; разговоры закреплённых за ней ролей; менеджер — списком |
| Роль | `role:<id>` | приписка к брифу | одна роль |

- `RuleScopeKind` = `'office' | 'subproject' | 'role'`; `RuleScopeView` получает
  `subprojectId`. Круги подпроектов строятся из `state.subprojects`, а не из
  `repoDir` ролей: `ruleScopes` перестаёт гадать по репозиториям.
- `rulesBrief(state, roleId, subprojectId)`: исполнитель на задаче — правила
  офиса + правила **зоны задачи** (а не роли: универсал на задаче веба живёт по
  правилам веба). Разговор и совещание без задачи — правила офиса + правила всех
  зон роли, каждая с подписью. Менеджер — все круги, как сейчас.
- Это снимает оговорку rules/spec.md «два направления в одном репозитории так
  не разделить»: у папок-зон свои `RULES.md`.

**Миграция круга `repo:<папка>`.** Файл не переезжает: repo-зона создаётся
миграцией (§7) ровно на том репозитории, где лежал `RULES.md` круга `repo:`,
и с id из того же `slug`, поэтому `repo:web` превращается в `sub:web` с тем же
файлом. Для старых ссылок (`edit_rule('repo:web#2')` в памяти менеджера,
записи ленты) `locate` в `rules.ts` принимает `repo:<slug>` как синоним
`sub:<slug>` — навсегда, это одна строка. Корень офиса кругом-зоной не бывает
(он и есть `office`), как и сейчас.

### 4.4. Журнал (по желанию, фаза 3)

Запись журнала сегодня видна всем (`scope: 'project'`) или одной роли. Третья
область — `scope: 'sub:<id>'`: видят сессии зоны. Ритуалы (консолидация,
противоречия) при выводе факта о файле зоны ставят ей область. Без этого
подпроекты работают; это экономия токенов, а не правило.

## 5. «Читать чужое можно, менять нельзя»

### 5.1. Что есть и почему одного классификатора мало

- **Чтение.** Исполнитель стартует в корне своей рабочей копии — у папки-зоны
  это копия всего репозитория офиса, поэтому чужие папки на месте и `Read`,
  `Grep`, `Glob` их видят (`SAFE_TOOLS`). У repo-зоны чужие репозитории лежат на
  диске вне копии: песочница их читать не мешает (запрещена запись, не чтение),
  `Read` безопасен. Промпт исполнителя перечисляет все зоны с абсолютными
  путями: «Сервер — `/…/server`, только чтение».
- **Запись в repo-зону** уже закрыта: всё вне рабочей копии — `danger` в
  `classify` (`perm.reason.outside`) и запрещено песочницей ОС (запись только в
  `.`). Новый механизм нужен только для **папки-зоны**.
- **Классификатор** (`permissions.ts`) видит путь у `Write`/`Edit`/`NotebookEdit`,
  но не видит, что пишет `Bash`: `sed -i`, `>`, `npm version`, генератор кода,
  `git mv`. Разобрать оболочку надёжно нельзя. Значит, классификатор **не
  может** быть гарантией — только ранней подсказкой.
- **Песочница ОС** сузить запись до `web/` не может: исполнителю нужны корневой
  `package-lock.json`, `.git` копии, кеши сборщика, и всё это вне папки зоны.

### 5.2. Решение: гейт — граница, классификатор — подсказка

**Гарантия — пред-merge гейт** (`premerge.ts`), потому что он смотрит на
**результат**, а не на способ: какие файлы ветка меняет относительно точки
ветвления. Ему всё равно, `Edit` это был, `sed` или генератор, — и проверка
воспроизводима (`git diff`), её видно в отчёте, её нельзя обойти внутри
сессии. Тем же гейтом сливает конвейер офиса, поэтому дыры «слили мимо гейта» нет.

1. **Новая стадия гейта `scope`** — сразу после пробного слияния, до
   зависимостей и проверок (она дешёвая, а проверки — нет):

   ```ts
   export interface PreMergeOptions {
     // …
     /**
      * Зона задачи-папки: что ветке можно менять. Нет — без ограничения
      * (задача «весь проект», repo-зона, ручной запуск scripts/premerge.ts).
      */
     zone?: { roots: string[]; sharedPaths: string[]; label: string };
   }

   export type PreMergeStage = /* … */ | 'scope';

   export interface PreMergeReport {
     // …
     /** Файлы ветки вне зоны задачи. Непусто — стадия `scope`, слияния нет. */
     outside: string[];
   }
   ```

   Список файлов — `git diff --name-status --no-renames <merge-base>..<branch>`:
   переименование считается удалением и добавлением, поэтому вынести файл из
   чужой папки в свою тоже нельзя. Файл разрешён, если его путь лежит в одном из
   `roots` (по сегментам, не по префиксу строки: `web` не пускает в `webhooks/`)
   или совпадает с pathspec из `sharedPaths`. Ветка с хотя бы одним файлом вне
   зоны не сливается: отчёт `scope` со списком, задача возвращается автору на
   доработку тем же путём, что красная проверка.

   Почему от точки ветвления, а не от слитого дерева: после подтягивания основной
   ветки в ветку задачи слитое дерево содержит чужие правки, и они не нарушение.
   `overlap.ts` уже считает точку ветвления (`forkPoint`) — берём её.

2. **Проверка при сдаче.** `finish_task` у исполнителя папки-зоны считает тот же
   список по своей ветке и, если есть файлы вне зоны, **не принимает сдачу**, а
   возвращает текст: какие файлы и что делать (откатить; нужна правка чужой
   зоны — описать её в отчёте, менеджер заведёт задачу той зоне). Сессия ещё
   жива и откатывает за один ход — дешевле, чем круг ревью. Это та же функция,
   что в гейте (`outsideZone(repoDir, base, branch, zone)` в
   `subprojects.ts`), а не вторая реализация.

3. **Классификатор — ранний отказ, не гарантия.** `Write`/`Edit`/`NotebookEdit`
   по пути вне зоны задачи получают **отказ без вопроса** (не `ask`: владельцу
   нечего решать, правило уже принято), с причиной `perm.reason.foreignZone` —
   «это зона «Сервер», у тебя только чтение». В `classify` добавляется
   необязательный аргумент `zone`, вердикт — флаг `deny: true`, который
   `decide` уважает при любом режиме доступа, включая «разрешать всё».
   `Bash` классификатор по-прежнему не разбирает: его ловят пункты 1 и 2.

Почему не только классификатор: обходится одной командой оболочки. Почему не
только гейт: агент узнал бы о нарушении через весь конвейер, после ревью, и
переписывал бы работу. Связка даёт и гарантию, и дешёвую обратную связь.

### 5.3. Проверки слияния зоны

`review.ts` передаёт гейту `checks` из зоны: `subproject.mergeChecks ?? общий
набор`. У папки-зоны команды идут с `cwd` в корне зоны на слитом дереве
(`runProjectCheck(join(worktree, root), …)`), набор по умолчанию ищется по
`package.json` в корне зоны, а если его нет — в корне репозитория. Зависимости
(`prepareDeps`) остаются на весь репозиторий: lock-файл общий.

## 6. Инструменты

### 6.1. Менеджер

- **Блок «Подпроекты» в системном промпте** (статическая часть): id, имя, вид,
  корень, `summary`, кто закреплён, кто универсал. Пустой список зон — блока нет.
- **`create_task`**: новый параметр `subprojectId` (`''` по умолчанию). Пусто —
  выводится: у роли ровно одна зона → она; роль закреплена за несколькими →
  отказ «укажи зону: web, server»; роль без закрепления → `null` («весь
  проект»). Указан — проверяется существование зоны и `admits`.
- **`plan_features`**: `subprojectId` у каждой задачи, та же логика; отказ
  целиком, с перечнем задач.
- **`edit_task`**: можно менять `subprojectId` у задач в `planned`/`backlog`.
- **`assign_task`**: проверка допуска (§3.2), включая явный `instanceId`.
- **`list_subprojects`** — только чтение, то же, что блок промпта, плюс открытые
  задачи по зонам. Заводить и удалять зоны менеджер **не** может: это
  структура офиса и решение владельца (как найм). Может предложить в чате.
- **`set_role_base`** (T-518): менеджер сам перезакрепляет роль —
  `subprojectId` (id зоны, несколько через запятую, `none` — снять) либо
  `path` (репозиторий роли; пусто — общий репозиторий офиса). Правит тем же
  `editRole`, что и форма роли: путь без repo-зоны заводит её, как и форма.
  Идущие задачи остаются в своём `task.repoDir`, ответ их перечисляет; смена
  пишется в ленту «было → стало, сменил менеджер».
- `list_team` показывает у каждой роли её зоны или «весь проект»; сводка
  доски группирует задачи по зонам, если зоны есть.

### 6.2. Исполнитель

- **Блок «Твоя зона»** в промпте задачи: имя, корень, `sharedPaths`, бриф зоны
  (§4.1) и список чужих зон с путями на чтение. У задачи «весь проект» блока нет.
- **`finish_task`** — проверка зоны (§5.2 п. 2).
- **`docs_list`, `docs_write`, `docs_set_kind`** — область и запрет правки чужого (§4.2); `docs_read` без изменений.
- **`ask_colleague({role, question})`** получает необязательный `subprojectId`:
  отвечает сотрудник роли, закреплённой за этой зоной (или универсал), и
  рабочая папка консультации (`cwd` в `consultRole`) — **корень этой зоны**, а
  не `repoFor(role)`: у repo-зоны `resolve(root)`, у folder-зоны
  `projectDir/root`. Роль, не допущенная к зоне, — отказ с причиной из
  `admitProblem`. Без `subprojectId` — рабочая папка по правилу
  `repoForRole(role)` (§2.3). Спросить «как устроено API сервера» у бэкенда — ровно то,
  ради чего чужое можно читать.

## 7. Миграция с «репозитория роли»

Разовая миграция при загрузке офиса, отметка `subprojects-from-repoDir` в
`roleMigrations` (механизм уже есть в `state.ts`). Идемпотентна **по
содержимому**, а не только по отметке: если кто-то руками вернёт `repoDir` в
`state.json`, следующая загрузка разберёт его тем же правилом.

Для каждой роли, у которой `repoDir` непуст (в самой роли или в
`package.overrides.repoDir`):

1. `abs = resolveRepoDir(repoDir)`. Совпал с `projectDir` — это «общий
   репозиторий»: поле снимается, зона не заводится.
2. Ищется repo-зона с `resolve(root) === abs`. Нет — заводится:
   `id` = тот же `slug(basename(abs))`, что круг правил `repo:` (со
   суффиксом `-2`, `-3` при совпадении — в том же порядке обхода, что
   `ruleScopes`: по отсортированным путям), `name = basename(abs)`,
   `kind: 'repo'`, `root` = **исходная строка** `repoDir` (относительная
   остаётся относительной), цвет — следующий свободный из палитры.
3. В `role.subprojects` добавляется id зоны (без дублей).
4. `repoDir` снимается с роли и из оверрайдов ссылки.

Задачи:

- `planned`/`backlog` без `repoDir` и с `roleId` мигрированной роли получают
  `subprojectId` её зоны — иначе они ушли бы в репозиторий офиса;
- стартовавшие и закрытые задачи получают `subprojectId` по своему
  `task.repoDir` (совпал с корнем repo-зоны — она, иначе `null`); их `repoDir`
  не трогается — он записан на старте и остаётся правдой;
- задачи без `subprojectId` в сохранении — `null`.

Две роли в одном репозитории → одна зона, обе закреплены. Роль, закреплённая
так, получает ровно те задачи, что получала раньше: все её задачи и так шли в
её репозиторий. Поведение меняется в одном месте, и это намеренно: универсалы
теперь могут работать в этой зоне, если менеджер даст им её задачу.

`Role.repoDir` после миграции **не читается**: `repoFor(role)`, который его
читал, заменяют `repoForTask(task)` в `startWorker` и `repoForRole(role)` в
совещании, разговоре с ролью, `ask_colleague` и `list_team`, а проверка
окружения и круги правил считают по `state.subprojects` (§2.3); тест мастера
`scripts/test-setup.ts:145`, который зовёт `state.repoFor(backends[0])`,
переходит на `repoForRole` (§2.3). Поле остаётся в типе на одну
версию с пометкой «устарело, читается только миграцией», форма роли его не
показывает, `PATCH` роли с `repoDir` отвечает подсказкой «заведите подпроект».
Мастер нового офиса (`setup.ts`, `hireFromPackage(..., { repoDir })`) вместо
поля роли заводит repo-зону и закрепляет за ней нанятого.

Откат на версию без подпроектов не поддерживается, как и у прочих миграций:
старый сервер увидит роли без `repoDir`, и их задачи уйдут в репозиторий офиса.
Владельцу это говорится в заметках выпуска.

## 8. Интерфейс (словами)

Рендер ничего не решает: допуск, зона задачи и границы считает сервер, веб
показывает `SubprojectView`, `TaskView.subprojectId` и отказы сервера.

**Настройки офиса → раздел «Подпроекты».** Список зон карточками: цветная метка,
имя, вид («Папка `web/`» / «Репозиторий `../shop-api`»), `summary`, аватарки
закреплённых, число открытых задач, `problem` красной строкой. Кнопка «Добавить»
открывает форму: имя, корень — поле с выбором папки (тот же нативный диалог, что
в мастере, `pickfolder.ts`); вид определяется сервером по пути и показывается
подсказкой, вручную переключается только при неоднозначности. Дальше —
`summary`, цвет из палитры, «Свои проверки слияния» (список команд, по умолчанию
свёрнут с подписью «общий набор»), «Общие файлы» (`sharedPaths`, только папка),
ссылки «Открыть бриф» и «Открыть правила» (файлы в корне зоны; нет — «создать»).
Удаление — с подтверждением; при открытых задачах кнопка неактивна с причиной.

**Окно «Команда» и окно роли.** У карточки сотрудника — чипы зон или серый чип
«Весь проект». В окне роли поле «Подпроекты»: мультивыбор с вариантом «Весь
проект» (пусто). Снятие зоны, у которой у роли есть задачи в очереди, —
предупреждение «N задач останутся без исполнителя» до сохранения.

**Доска.** Ряд чипов-фильтров над колонками: «Все», зоны, «Весь проект». У
карточки задачи — цветной бейдж зоны. Фильтр — состояние веба, сохраняется по
офису, как размеры окон.

**Документы.** Тот же ряд фильтров; в карточке документа — поле «Область»
(«Весь офис» / зона); в диалоге нового документа — выбор области.

**Лента и «Жизнь офиса».** Фильтр по зоне: события задач и документов несут
зону, записи без зоны видны всегда.

**Правила.** В панели «Правила» группы «Весь офис» → зоны → роли.

**3D-офис.** Зоны — участки пола, подкрашенные цветом зоны, с табличкой имени;
столы закреплённых ролей стоят в своём участке, универсалы — в общем. Раскладка
участков — дело раскладки (`layout.ts`) и дизайнера; если у роли несколько зон,
стол в общем участке и чипы зон над головой. Без 3D (графика выключена) всё
работает — участок пола только картинка.

## 10. Открытые вопросы

1. **Универсал на задаче зоны правит только зону.** Так следует из «одна задача
   — одна зона», но строже, чем «универсал работает везде». Альтернатива —
   граница по роли, а не по задаче. Предлагаю строгий вариант: для сквозной
   работы есть зона «весь проект».
2. **Ревьюер.** Сейчас ревьюер закрепляется наравне со всеми, и закреплённый за
   вебом не ревьюит сервер. Ревью — это чтение, и можно сделать ревьюера
   исключением («читает всё, сливает всё»). Но ревьюер же и сливает, и правит
   конфликты — предлагаю не делать исключения и держать ревьюера-универсала.
3. **Общие корневые файлы монорепо** (`package.json`, lock-файл, `tsconfig`).
   Сейчас — явный `sharedPaths` у каждой зоны. Может, нужен общий список на офис
   по умолчанию (`package-lock.json` для всех папок-зон)?
4. **Зона «весь проект» в офисе с зонами.** Нужна ли она вообще, или в таком
   офисе каждая задача обязана иметь зону? Без неё правка `OFFICE.md` или CI
   становится некому.
5. **Папки внутри repo-зоны** (отдельный репозиторий, а в нём `api/` и `admin/`).
   По §1.4 не поддерживается: вложенности нет. Если понадобится — это второй
   уровень, и решение за владельцем.
6. **Выпуски и деньги по зонам.** Цели выпуска (`releases`) и доска расходов
   (`MoneyBoard`) по зонам не делятся. Нужна ли разбивка расходов по зонам?
7. **Может ли менеджер заводить зоны** инструментом (с согласием владельца, как
   правила через `selfchange`)? Предлагаю: нет в фазах 1–4, только предложение в
   чате.
8. **Роли с `docsDir`** (документные роли) пишут вне репозитория в свою папку;
   граница зоны на них не распространяется — они не меняют код. Закрепление
   при этом работает (получают задачи только своих зон). Проверить, что это
   устраивает.

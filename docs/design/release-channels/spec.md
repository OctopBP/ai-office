# Спека: каналы выпуска (stable / beta / alpha)

Статус: проект, к реализации. Задача T-384, решение владельца — Q-110.
Продолжает `docs/design/releases/spec.md` (дальше — «спека выпусков»):
там цель выпуска, процесс `release`, версия и проверка видимости; здесь —
что меняется, когда у цели появляются каналы.

Задача владельца: выпускать тестовые сборки приложения (например, с новыми
инструментами UI/UX) в бету или альфу так, чтобы **пользователи основного
канала их не получали автообновлением**, а стабильный выпуск не получал
ничего, что не прошло бету.

Решение владельца: отдельные ветки для выпусков по общепринятой практике —
`main` → `beta` → `release`. Ниже — модель, уточнённая по коду.

---

## 1. Что есть сейчас

| Где | Как устроено сейчас |
|---|---|
| `src/shared/release.ts` | Цель выпуска (`targetSchema`): `kind` push/tag/command, `tag` (по умолчанию `v{version}`), `bump`, `assets`, `ci`, `policy`, `version.scheme`/`level`. `nextVersion` поднимает разряд; `parseSemver` **выбрасывает** суффикс пререлиза (`1.4.2-beta` → `[1,4,2]`). |
| `src/server/releases.ts` → `snapshot` | Снимок **основной ветки** (`baseBranch`), диапазон с прошлого выпуска цели, временная ветка `release/<id>` на снимке. |
| `releases.ts` → `currentVersion`, `lastTagSha`, `versionFromTag` | Текущая версия — первый тег по `git tag --sort=-v:refname`, подходящий под шаблон. Пререлизы шаблон пропускает (`[0-9A-Za-z.+-]*?`), а git без `versionsort.suffix` ставит `v1.5.0-beta.1` **выше** `v1.5.0`. |
| `releases.ts` → `bump`, `tag` | Коммит «Выпуск» в `release/<id>`, аннотированный тег на его вершине, пуш тега. |
| `releases.ts` → `visible` | Релиз с тегом опубликован, не черновик, в нём файлы `assets` (`parseGithubRelease`). |
| `releases.ts` → `publish` | `release/<id>` вливается **обратно в основную** (`mergeBranch` под `withMergeLock`), ветка удаляется. |
| `workflows/release.json` | snapshot → version → notes → approve → bump → ship → tag/push/build → watch → visible → publish; починка `fix` задачей с `forkFrom: release/<id>`. |
| `src/server/agents.ts` | Инструменты менеджера `release_status`, `start_release`, `resume_release`, `plan_release`, `close_release_plan`, `propose_release_target`. |
| `.github/workflows/release.yml` | Сборка по тегу `v*`, черновик релиза, публикация только при наличии `latest.yml`, `latest-mac.yml` и установщиков; `gh release edit --draft=false --latest`. |
| `.github/workflows/ci.yml` | Проверки на PR и на пуш в `main`. |
| `desktop/builder.config.js` | `publish: github`, файлы автообновления `latest*.yml`; каналов нет. |
| `desktop/updater.js` | electron-updater, ручной поток (`autoDownload = false`), `channel`/`allowPrerelease` не задаются. |
| Цель `desktop` у владельца | `tag v{version}`, `bump: npm version {version} --no-git-tag-version && npm --prefix desktop version {version} --no-git-tag-version`, `assets: ["latest-mac.yml"]`, semver по плану, согласие всегда. Последний тег — `v0.10.0`. |

Чего не хватает: выпускать можно только снимок `main`, и любой выпуск — это
сразу стабильный релиз, который GitHub помечает «latest», а electron-updater
раздаёт всем.

**Найденная ловушка с именем ветки.** Временные ветки выпусков называются
`release/<id>` (в репозитории сейчас лежат `release/desktop-11`,
`release/desktop-13`). Ветка `release` с ними несовместима: git хранит
`refs/heads/release` файлом, а `refs/heads/release/…` — каталогом, и одно
не может существовать рядом с другим. Поэтому временные ветки переезжают
в `office/rel/<id>` (§5.4) — имя `release` за стабильным каналом остаётся,
как решил владелец.

## 2. Главные решения

1. **Канал — свойство выпуска, а не отдельная цель.** У цели `desktop`
   появляется поле `channels`; выпуск запускается с каналом. Отдельные цели
   `desktop-beta` / `desktop` отвергнуты (§5.1).
2. **Три постоянные ветки, движутся только вперёд.** `alpha` ← `main`,
   `beta` ← `main`, `release` ← `beta`. Продвижение — только fast-forward на
   **проверенный коммит**, никогда не force-push.
3. **Стабильный выпуск берёт коммит последней состоявшейся беты, а не
   вершину ветки `beta`.** Код стабильного тега отличается от проверенной беты
   только строкой версии. Это и есть гарантия «в стабильный не попадает
   ничего, что не прошло бету».
4. **Вниз — слиянием, не cherry-pick.** Всё, что офис закоммитил в ветку
   канала (коммит версии, починки сборки, хотфиксы), после выпуска вливается
   вниз по цепочке: `release` → `beta` → `main`, `alpha` → `main`.
   Инвариант после каждого выпуска: `release ⊆ beta ⊆ main`, `alpha ⊆ main`
   (по предкам). Благодаря ему следующее продвижение — всегда перемотка.
5. **Хотфикс** — задача от ветки `release` и в неё же, затем стабильный
   выпуск с `hotfix: true` прямо из `release` (патч-версия), затем слияние
   вниз. Без cherry-pick.
6. **Версии — semver-пререлизы** `X.Y.Z-beta.N` / `X.Y.Z-alpha.N`, тег
   `v{version}`. Счёт — по тегам git, сравнение — по правилам semver, а не
   по сортировке git.
7. **CI различает канал по суффиксу тега**: пререлиз → GitHub Release с
   флагом prerelease и файлами `beta*.yml`/`alpha*.yml`; `latest*.yml` и
   метку «Latest» получает только стабильный.
8. **Канал в приложении выбирает пользователь**; по умолчанию — стабильный
   (или канал установленной сборки, если она пререлиз). Возврат с беты на
   стабильный **не откатывает версию**: ждём следующий стабильный, откат —
   только явной кнопкой с предупреждением (§7.4).
9. Цель без `channels` работает ровно как сейчас: снимок `main`, тег,
   слияние обратно. Каналы включаются, а не появляются сами.

## 3. Модель веток и каналов

### 3.1 Каналы

| Канал | Ветка | Откуда продвигается | Тег | Кто получает |
|---|---|---|---|---|
| alpha | `alpha` | `main` | `vX.Y.Z-alpha.N` | выбравшие альфу |
| beta | `beta` | `main` (или `alpha`, если так настроено) | `vX.Y.Z-beta.N` | выбравшие бету (и альфу) |
| stable | `release` | `beta` (коммит последней беты) | `vX.Y.Z` | все |

`main` — разработка, как сейчас: конвейер офиса вливает туда задачи.

Альфа необязательна. Для приложения предлагается начать со `stable` + `beta`
(§8), альфу добавить, когда понадобится канал «совсем сырого».

### 3.2 Поток

```
 задачи ──► main ──────────────┬───────────────────────────────┐
             ▲ ▲                │ продвижение: снимок main        │ снимок main
             │ │ слияние вниз   ▼                                 ▼
             │ └──────────── beta   (vX.Y.Z-beta.N)            alpha (vX.Y.Z-alpha.N)
             │                  ▲ │                               │
             │   слияние вниз   │ │ продвижение: коммит           │ слияние вниз
             │                  │ ▼ последней беты                ▼
             │              release (vX.Y.Z)                    main
             │                  ▲
             └── хотфикс ───────┘  задача от release → в release → vX.Y.(Z+1)
```

Один выпуск канала, шаг за шагом:

1. **Снимок источника.** beta/alpha — вершина `main`. stable — коммит тега
   последней состоявшейся беты (`status: 'done'`). stable с `hotfix` —
   вершина `release`.
2. **Проверка перемотки.** Ветка канала должна быть предком снимка (§3.4).
3. Временная ветка `office/rel/<id>` на снимке; версия, заметки, согласие.
4. **Коммит версии** в `office/rel/<id>` (команда `bump` цели), починки
   сборки — туда же, как сейчас.
5. **Тег** на вершине `office/rel/<id>`, пуш тега → CI собирает.
6. CI зелёный, релиз виден автообновлению своего канала.
7. **Продвижение ветки канала:** `git push origin <tip>:refs/heads/<канал>`
   без `+` — сервер сам отвергнет не-перемотку. Локальная ветка — туда же.
8. **Слияние вниз** по цепочке (§3.5), удаление `office/rel/<id>`.

Ветка канала движется **в конце**, после зелёного CI и видимого релиза: в
ветке канала лежат только выпущенные коммиты. Упавший или брошенный выпуск
оставляет только тег-черновик и временную ветку, ветка канала не тронута.

### 3.3 Продвижение: кто и как

- Делает **узел выпуска офиса** (`publish`), ручного git нет. Владелец
  нажимает «Выпустить бету» / «Перевести бету в стабильный» или отвечает
  «да» на вопрос; менеджер — `start_release({target, channel})`.
- **Только fast-forward.** Слияний в ветку канала при продвижении нет:
  слияние родило бы коммит, которого никто не тестировал. Новые коммиты в
  ветке канала появляются только из коммита версии, починки сборки и
  хотфикса — и все они проходят CI до продвижения.
- Перед снимком офис делает `fetchRemote`: локальная ветка канала отстаёт от
  `origin/<канал>` — перематывается; опережает или разошлась — это
  расхождение (§3.4).
- Пока у цели идёт выпуск (`activeRelease` — один на цель, как сейчас),
  конвейер не вливает задачи с `baseBranch` = ветка канала этой цели
  (хотфиксы ждут): иначе перемотка в шаге 7 сорвалась бы.

### 3.4 Если ветки разошлись

Расхождение — ветка канала не предок снимка. Откуда берётся: прошлое слияние
вниз не удалось; хотфикс влит в `release`, но новой беты с ним ещё не было;
кто-то запушил в ветку канала руками.

| Случай | Что делает офис |
|---|---|
| beta/alpha: в ветке канала есть коммиты, которых нет в `main` | Сначала **слияние вниз** (ветка канала → `main`, как в §3.5), затем снимок заново. Это лечение: всё, что лежит в ветке канала, по инварианту и так должно быть в `main`. |
| stable: `release` не предок коммита последней беты (был хотфикс после беты) | **Стоп, вопрос владельцу:** «В стабильном есть хотфикс 1.4.3, которого нет в бете 1.5.0-beta.3. Сначала нужна новая бета». Кнопка «Выпустить бету» — запускает бету; бету с хотфиксом проверяют, и только её переводят в стабильный. Подмешать хотфикс в стабильный без беты нельзя — это нарушило бы гарантию. |
| Слияние вниз дало конфликт не только в файлах версии (§3.5) | Стоп с `needsDecision`, задача на сведение веток (§5.6). |
| `origin` отверг перемотку в шаге 7 | Стоп с `needsDecision`, в `release_status` — «ветка `beta` на GitHub ушла вперёд». Force-push офис не делает никогда; ruleset его и не даст (§6.5). |

### 3.5 Слияние вниз

После выпуска канал вливается в ветку, из которой продвигается, и так до
`main` (обратный порядок цепочки `from`):

- stable: `release` → `beta` → `main`;
- beta: `beta` → `main` (если `beta.from = alpha`: `beta` → `alpha` → `main`);
- alpha: `alpha` → `main`.

Правила:

- Если принимающая ветка — предок вливаемой, это перемотка (обычный случай:
  `beta` после перевода в стабильный перематывается на `release`). Иначе —
  **настоящий merge-коммит** (`mergeBranch`, автор `OFFICE_PERSON`), не
  squash: сквош потерял бы предка, и следующая перемотка не прошла бы.
- В `main` — под `withMergeLock` в копии интеграции, как сейчас делает
  `publish`. В `beta`/`alpha` — в той же копии с другой базой и пушем ветки
  без `+`.
- **Конфликт в строках версии разрешается сам.** Хотфикс 1.4.3 и бета
  1.5.0-beta.3 оба правили `"version"` в `package.json`, `package-lock.json`,
  `desktop/package.json`. Если все конфликтующие файлы входят в набор файлов
  коммитов «Выпуск» офиса с общего предка (их видно по автору `OFFICE_PERSON`
  и сообщению `rel.commit`), берётся сторона принимающей ветки: версия в `beta`
  остаётся `1.5.0-beta.3`. Любой другой конфликт — стоп (§3.4).
- Слияние вниз не удалось — выпуск всё равно состоялся (как сейчас с
  `rel.mergeBackFailed`): статус `done`, но `Release.mergedDown` неполон, в
  `release_status` строка «ветки разошлись», менеджеру — `tellPm`. Следующий
  выпуск цели начинается с лечения (§3.4).

### 3.6 Хотфикс

Выбор: **обратное слияние** (хотфикс в `release`, затем `release` → `beta` →
`main`), а не cherry-pick в `main`.

Почему не cherry-pick: копия коммита — другой коммит; git не знает, что
хотфикс уже в `main`, `release` перестаёт быть предком `beta`, и следующий
перевод беты в стабильный упирается в расхождение. Плюс двойные правки ловит
`overlap.ts` и шумит предупреждениями. Обратное слияние сохраняет инвариант
§2.4, и всё остальное (перемотка, проверка «нет непроверенного») держится
на нём.

Поток:

1. Менеджер заводит задачу `create_task({…, onto: 'release'})` — задача
   ответвляется от `release` (`forkFrom`) и вливается в неё же
   (`baseBranch`). Обычный конвейер: ревью, гейт `premerge` на слитом с
   `release` дереве, squash-слияние в `release` — это новый коммит в ветке
   канала, ему так можно.
2. `start_release({target: 'desktop', channel: 'stable', hotfix: true})`:
   снимок — вершина `release`, версия — патч от последнего стабильного
   (`1.4.2` → `1.4.3`), согласие владельца, CI, видимость.
3. Продвигать нечего (источник и есть ветка канала), только слияние вниз:
   `release` → `beta` (merge, версия беты остаётся своей) → `main`.
4. Следующая бета `1.5.0-beta.4` уже содержит хотфикс; стабильный `1.5.0`
   — тоже, через неё.

Бета-тестеры хотфикс 1.4.3 автообновлением не получат: `1.4.3 < 1.5.0-beta.3`,
а откат версии выключен (§7.3). Они получат его со следующей бетой.

## 4. Версии

### 4.1 Вид

semver 2.0 с пререлизом: `X.Y.Z-beta.N`, `X.Y.Z-alpha.N`, N с 1. Тег — по
шаблону цели, для приложения `v{version}`: `v1.5.0-beta.2`. Порядок по semver:
`1.5.0-alpha.3 < 1.5.0-beta.1 < 1.5.0-beta.2 < 1.5.0`. Этот же порядок
использует electron-updater, поэтому стабильный 1.5.0 сам доходит до
сидящих на 1.5.0-beta.N.

Каналы допускаются только при `kind: 'tag'` и `version.scheme: 'semver'`
(у `semver+build`, `calver`, `build` пререлиз смысла не имеет — разбор
настройки это запрещает, §5.1).

### 4.2 Как считаются базовая версия и N

Источник правды — **теги git по шаблону цели** (у цели с каналами
`version.source` всегда `tag`). История выпусков офиса добавляется как
сейчас: если тег не запушен, берётся старшая из двух.

Обозначения (всё по тегам, сравнение — `compareSemver` по полному semver):

- `S` — старшая стабильная версия (без пререлиза), например `1.4.2`;
- `L` — «открытый цикл»: старшая база среди пререлизов любого канала,
  которая **больше `S`**, например `1.5.0` из `v1.5.0-beta.3`;
- `level` — разряд, как сейчас (план → вклад фич → `auto`/фиксированный),
  но по диапазону **с тега `S`** — то есть по всему, что ещё не стало
  стабильным;
- `want` — `plan.version`, если открыт план с версией, иначе `bump(S, level)`.

**Пререлиз канала `c` (beta или alpha):**

```
base = L, если L есть и L ≥ want;  иначе want        // новый цикл или старше
N    = 1 + max(n среди тегов v{base}-{c}.n), 0 если таких нет
version = {base}-{c}.{N}
```

Примеры при `S = 1.4.2`:

| Что было | Что пришло | Выпуск |
|---|---|---|
| пререлизов нет | фича (minor) | `1.5.0-beta.1` |
| `1.5.0-beta.1` | ещё задачи (patch) | `1.5.0-beta.2` — патч не дробит открытый цикл |
| `1.5.0-beta.2` | фича с разрядом major | `2.0.0-beta.1` — цикл переоткрыт выше |
| `1.5.0-beta.2` | альфа | `1.5.0-alpha.1` (у альфы свой счёт N) |
| план «1.6 = F-4, F-5» | бета | `1.6.0-beta.1` — версия плана — база |

**Стабильный из беты:** `version = база беты` (`1.5.0-beta.3` → `1.5.0`).
Разряд заново не считается — он уже посчитан для цикла. Ответ владельца с
другой версией («выпускай 2.0.0») принимается, если она `> S` и `≥ база`;
меньше — отказ с объяснением.

**Стабильный-хотфикс:** `version = bump(S, 'patch')` (`1.4.2` → `1.4.3`).

**Цель без каналов** — как сейчас, но через тот же исправленный счёт (§4.3).

### 4.3 Исправление текущего счёта

Сейчас `currentVersion` и `lastTagSha` берут первый тег по
`git tag --sort=-v:refname`, а `parseSemver` отрезает пререлиз. Как только
появится `v1.5.0-beta.1`, стабильная цель без каналов насчитает от него
`1.6.0`. Поэтому независимо от каналов:

- все теги по шаблону разбираются полным semver и сортируются
  `compareSemver` с пререлизами;
- стабильная версия и `lastTagSha` стабильной цели берутся только из тегов
  **без** пререлиза.

### 4.4 Версия в файлах

`bump` цели получает полную версию (`{version}` = `1.5.0-beta.2`; npm
пререлизы понимает). Коммит «Выпуск» ложится в `office/rel/<id>` — то есть,
после продвижения, в **ветку канала** — и слиянием вниз доезжает до `main`.
В `main` поле `version` поэтому показывает последний выпуск любого канала
(`1.5.0-beta.2`), что честно: это последняя собранная версия.

electron-builder берёт версию сборки из `desktop/package.json`, и имена
файлов (`AI-Office-1.5.0-beta.2-arm64.zip`), и сами `*-mac.yml` — от неё,
поэтому коммит версии обязан быть в теговом коммите. Так и есть: тег ставится
на вершину `office/rel/<id>` после `bump`.

`CHANGELOG.md` пополняется только **стабильным** выпуском (заметки за весь
цикл); бета-заметки живут в описании GitHub-релиза и в выпуске офиса —
иначе журнал изменений зарос бы десятком `beta.N`.

### 4.5 Заметки

- beta/alpha: диапазон — с коммита прошлого выпуска **этого канала** в
  открытом цикле (или с тега `S`): «что нового с прошлой беты».
- stable: диапазон — с тега `S`: всё, что вошло за цикл, одной сводкой.
- хотфикс: с тега `S`.

## 5. Сервер

### 5.1 Канал в цели: поле, а не отдельные цели

Рассматривались два способа: отдельные цели `desktop-beta` и `desktop`
или одна цель с полем `channels`. Выбрано **поле**, потому что:

- версия у каналов общая: бете нужно знать последний стабильный, стабильному
  — последнюю бету. Сейчас всё в выпусках считается по цели (`lastDone`,
  `releasesOf`, `activeRelease`, `releaseDir`); две цели пришлось бы связывать
  ссылками друг на друга;
- `bump`, `ci`, `timeoutMin`, `repo`, шаблон тега — одни и те же, в двух
  целях они бы расходились;
- один выпуск на цель за раз (`activeRelease`) — ровно то, что нужно: бета
  и стабильный двигают общие ветки и слияния вниз, параллельно им нельзя;
- владелец видит одну карточку «Приложение» с каналами, а не две цели,
  которые выглядят независимыми, хотя нет.

Контракт `src/shared/release.ts`:

```ts
export const RELEASE_CHANNELS = ['stable', 'beta', 'alpha'] as const;
export type ReleaseChannel = typeof RELEASE_CHANNELS[number];

const channelSchema = z.object({
  /** Постоянная ветка канала: 'release', 'beta', 'alpha'. */
  branch: z.string().regex(BRANCH_RE).max(200),
  /** Откуда продвигается: основная ветка или другой канал. По умолчанию — §3.1. */
  from: z.enum(['main', 'alpha', 'beta']).optional(),
  /** Своя политика канала; нет — политика цели. */
  policy: policySchema.optional(),
  /** Файлы релиза для проверки видимости в этом канале (beta-mac.yml, beta.yml). */
  assets: z.array(z.string().trim().min(1).max(200)).max(20).optional(),
}).strict();

// в targetSchema:
channels: z.object({
  stable: channelSchema,
  beta: channelSchema.optional(),
  alpha: channelSchema.optional(),
}).strict().optional(),
```

Проверки в `parseReleaseConfig` (ошибка — человеку, как сейчас):

- `channels` только у `kind: 'tag'` и `scheme: 'semver'`; в шаблоне тега
  есть `{version}`;
- ветки каналов разные, не основная ветка, не `office/…`, и ни одна не
  является префиксом-каталогом другой (`release` и `release/x` вместе нельзя);
- `from` образует цепочку до `main` без циклов; `stable.from` — `beta`, если
  бета есть, иначе `main`; `alpha.from` — только `main`;
- у канала с `assets` — только у тега (как сейчас у цели).

`assets` и `policy` цели остаются и значат «для стабильного канала», если у
`channels.stable` своих нет.

Пример цели приложения:

```json
{ "id": "desktop", "title": "Приложение", "kind": "tag", "tag": "v{version}",
  "bump": "npm version {version} --no-git-tag-version && npm --prefix desktop version {version} --no-git-tag-version",
  "policy": { "when": ["manual"], "approve": "always" },
  "version": { "scheme": "semver", "level": "plan", "source": "tag" },
  "channels": {
    "stable": { "branch": "release", "assets": ["latest-mac.yml", "latest.yml"] },
    "beta":   { "branch": "beta", "assets": ["beta-mac.yml", "beta.yml"],
                "policy": { "when": ["manual", "epic.done"], "approve": "always" } }
  } }
```

### 5.2 Выпуск

`Release` (`src/shared/release.ts`) получает:

```ts
/** Канал выпуска; null — цель без каналов (поведение как раньше). */
channel: ReleaseChannel | null;
/** Стабильный выпуск прямо из ветки release (§3.6). */
hotfix: boolean;
/** Что продвигали: источник и его коммит; ветка канала после выпуска. */
promote: { from: string; sha: string; branch: string } | null;
/** Куда уже влито вниз: ['beta', 'main']. Неполный список при done — ветки разошлись. */
mergedDown: string[];
```

`branch` выпуска теперь `office/rel/<id>` (а не `release/<id>`), `fromSha` —
начало диапазона по правилам §4.5. Старые выпуски в состоянии читаются как
`channel: null, hotfix: false, promote: null, mergedDown: []`.

`ReleasePlan` не меняется: план — про стабильную версию («1.6 = F-4, F-5»),
пререлизы цикла берут его версию базой (§4.2). Открытый план сдерживает
автоматический **стабильный** выпуск по `epic.done`, как сейчас; бета по
закрытой фиче выходит и при открытом плане — для того бета и нужна.

### 5.3 Процесс `release`

`workflows/release.json` узлов не добавляет; меняются действия в
`src/server/releases.ts`:

| Узел | Что меняется |
|---|---|
| `snapshot` | `fetchRemote`; выбор источника по каналу (§3.2 п.1); лечение и проверка расхождения (§3.4); диапазон по §4.5; «нечего выпускать»: beta/alpha — вершина источника уже в последнем теге канала, stable — коммит последней беты уже в `S`, хотфикс — в `release` нет коммитов после тега `S`. Нет беты со `status: 'done'` для stable — отказ «сначала выпустите бету». |
| `version` | Счёт по §4.2 (`nextChannelVersion`); проверка «такой тег уже есть» — как сейчас. |
| `notes` | Диапазон §4.5; в подсказке модели — канал. Фильтр конфиденциального по заметкам и списку коммитов (§6.7). |
| `approve` | В вопросе канал словами: «Бета 1.5.0-beta.2 — увидят только выбравшие бету», «Стабильный 1.5.0 из беты 1.5.0-beta.3 — получат все». Версия в ответе — §4.2. |
| `bump` | Без изменений по сути; `CHANGELOG.md` — только у stable. |
| `tag` | Без изменений: тег на вершине `office/rel/<id>`. |
| `visible` | `assets` канала; плюс тип релиза (§6.4). |
| `publish` | Продвижение ветки канала (§3.2 п.7), слияние вниз (§3.5), удаление временной ветки. У цели без каналов — как сейчас. |
| `fix` | Без изменений: починка от `office/rel/<id>` и в неё. |

`dueRelease`/`tickReleases`: автоматические поводы считаются **по каналу**
(своя `policy` канала, `merged` — с прошлого выпуска этого канала,
`cooldownHours` — по каналу). Сработали два канала сразу — сначала бета.

### 5.4 Git

В `src/server/git.ts`:

- `promoteBranch(repo, branch, sha, token, lang)` — локально
  `update-ref refs/heads/<branch> <sha> <old>` только если `<old>` — предок
  `<sha>`, затем `pushRef(repo, sha, refs/heads/<branch>, token, lang)` **без**
  `force`. Нет ветки — создаётся (первый выпуск канала, §8);
- `mergeDown(repo, from, into, …)` — перемотка или merge-коммит в копии
  интеграции, с автоматическим разрешением конфликта в файлах версии (§3.5);
  возвращает `ff | merged | conflict(files)`;
- временные ветки — `office/rel/<id>`. Миграция при старте сервера: влитые в
  основную `release/*` удаляются, невлитые переименовываются в
  `office/rel/<id>` (у идущих выпусков в состоянии меняется `branch`).
  Без этого ветку `release` создать нельзя (§1).

### 5.5 Инструменты менеджера (`src/server/agents.ts`)

- `start_release`: новые поля `channel: 'stable' | 'beta' | 'alpha'` и
  `hotfix: boolean`. У цели с каналами `channel` обязателен — ошибка
  перечисляет каналы цели; у цели без каналов он запрещён. `hotfix` — только
  со `stable`. `startRelease(state, targetId, reason, note, now, { channel, hotfix })`.
- `propose_release_target`: новое поле `channels` — список
  `{ channel, branch, from?, when?, mergedEvery?, approve?, assets? }`.
  Не переданы `assets` канала, а у цели они есть — офис выводит их по
  правилу electron-builder `latest*.yml` → `<канал>*.yml` и **показывает в
  вопросе владельцу**; повторное предложение без `channels` сохраняет
  прежние (как `proposedAssets`). `describeTarget` пишет каналы строками:
  «Бета: ветка beta, теги v{version}-beta.N, по просьбе и по закрытой фиче».
- `release_status` (`releaseStatusText` → `targetRows`): по каждому каналу —
  последний выпуск и дата, вершина ветки, сколько задач в источнике сверх
  канала («в main 12 задач сверх беты», «бета 1.5.0-beta.3 ждёт перевода в
  стабильный»), строка «ветки разошлись» при неполном `mergedDown` или
  обнаруженном расхождении, и хотфиксы в `release`, ещё не выпущенные.
- `plan_release` — без изменений.
- `create_task`: поле `onto` — ветка канала из целей офиса (`release`,
  `beta`); ставит `forkFrom` и `baseBranch`. Не ветка канала — ошибка.

Бриф менеджера (`packages/@office/pm`) — абзац: тестовое в бету, стабильный
только из беты, хотфикс через `onto: 'release'` и `hotfix: true`, не
предлагать выпуск в stable того, чего не было в бете.

### 5.6 Задача на сведение веток

Конфликт при слиянии вниз (§3.5) не решается squash-задачей: нужен
merge-коммит. Задача получает `mergeMode: 'merge'` (новое поле `Task`):
рабочая копия создаётся от принимающей ветки с начатым `git merge <канал>`,
исполнитель разрешает конфликты и коммитит слияние, конвейер вливает её в
принимающую ветку **перемоткой**, без squash. После слияния задачи выпуск
продолжает слияние вниз дальше по цепочке (`resume_release`).

### 5.7 Интерфейс выпусков (`src/web/ReleasesPage.tsx`)

  канала, файлы видимости.
- Карточка цели: строка на канал — версия, ветка, «N задач сверх»; кнопки

- Выпуск в списке — со значком канала.
- Тексты — в `src/web/i18n` на оба языка, серверные — в `src/server/i18n`.

## 6. CI

### 6.1 Сборка (`.github/workflows/release.yml`, `desktop/builder.config.js`)

- Канал определяется по тегу в первом шаге обоих джобов:
  `channel=$(sed -n 's/^v[0-9.]*-\([a-z]*\)\..*/\1/p' <<< "$GITHUB_REF_NAME")`,
  пусто — `latest`. Вывод в `GITHUB_OUTPUT`.
- `builder.config.js`: `generateUpdatesFilesForAllChannels: true`.
  electron-builder определяет канал по суффиксу версии (`detectUpdateChannel`
  включён по умолчанию) и пишет файлы:
  - стабильная `1.5.0` → `latest*.yml`, `beta*.yml`, `alpha*.yml`;
  - бета `1.5.0-beta.2` → `beta*.yml`, `alpha*.yml`;
  - альфа → `alpha*.yml`.
  Так стабильный выпуск виден и тем, кто сидит на бете: в его релизе лежит
  `beta-mac.yml`. Набор нужно подтвердить пробной сборкой пререлиза на
  установленной версии electron-builder 26 — это первый пункт задачи CI.
- `upload-artifact`: вместо `desktop/out/latest*.yml` — `latest*.yml`,
  `beta*.yml`, `alpha*.yml` (не `*.yml`: в `out/` лежит `builder-debug.yml`).

### 6.2 Релиз

- `softprops/action-gh-release`: `prerelease: ${{ contains(github.ref_name, '-') }}`.
- Описание: у пререлиза перед «Что нового» — абзац «Тестовая сборка канала
  бета: придёт автообновлением только тем, кто выбрал бету в настройках.
  Предоставляется «как есть», без гарантий, может терять данные». Это
  памятка для читающих релизы, а не согласие пользователя: согласие даётся
  в приложении (§7.7). Текст — черновик, проходит юриста вместе с §7.7
  (§7.9).
- `scripts/release-notes.mjs`, запасной список коммитов: у стабильного —
  с прошлого **стабильного** тега, у пререлиза — с прошлого тега любого вида.
- Шаг «публикация релиза»: список обязательных файлов — по каналу
  (`latest.yml latest-mac.yml` / `beta.yml beta-mac.yml` / `alpha.yml
  alpha-mac.yml` плюс установщики с полной версией в имени). Публикация:
  - stable: `gh release edit "$TAG" --draft=false --latest`;
  - пререлиз: `gh release edit "$TAG" --draft=false --prerelease --latest=false`.

### 6.3 Почему бета не дойдёт до стабильных

Файлы каналов лежат **в своём релизе**, а не в общем месте, поэтому
«перезаписать `latest-mac.yml`» бета не может в принципе. Стабильный
пользователь не увидит бету по двум независимым причинам:

1. electron-updater с `allowPrerelease = false` ищет релиз через
   `releases/latest` GitHub, а GitHub никогда не отдаёт там пререлиз
   (и CI снимает с беты метку `--latest`);
2. в бета-релизе нет `latest-mac.yml` — даже найденный, он для канала
   `latest` пуст.

### 6.4 Проверка видимости канала

`visible` в `releases.ts` и `parseGithubRelease` в `src/shared/release.ts`:

- файлы — `assets` канала;
- новое состояние `wrongKind`: у пререлиза `prerelease !== true` или у
  стабильного `prerelease === true` — это значит, что бета попала бы ко всем
  (или стабильный — никому);
- у stable дополнительно `GET /repos/{o}/{r}/releases/latest` должен
  вернуть этот тег (`ReleaseHost.latest`): иначе стабильные пользователи
  обновление не увидят. Хотфикс эту проверку проходит так же: он всегда
  старше последнего стабильного (`bump(S, 'patch')`), и GitHub делает его
  «Latest».

### 6.5 Защита веток и проверки на них

- `ci.yml`: `push: branches: [main, beta, alpha, release]` — проверки на
  коммитах версии и слияниях вниз.
- Ruleset для `beta`, `alpha`, `release` (делает владелец в настройках
  GitHub, как для `main`): запрет удаления, запрет force-push, обновление —
  только из списка обхода (владелец-админ; офис пушит токеном владельца,
  `githubToken()`). Требования PR и обязательных проверок **не ставить**:
  офис продвигает перемоткой уже собранный коммит, а обязательная проверка
  на пуш в ветку остановила бы перемотку до CI, который запускается тегом.
- Тегов `v*` ruleset не трогает: повтор выпуска переставляет тег
  (`tag -f` + пуш с `force`, `releases.ts` → `tag`).

### 6.6 Подпись и заверение — одинаково для всех каналов

Сейчас `release.yml` при отсутствии секретов не падает: без `CSC_LINK`
сборка подписывается «для себя» (`identity: '-'`), без `APPLE_API_KEY_P8`
нотаризация молча выключается (`builder.config.js` → `notarize`). Для
стабильного выпуска это видно по логу, но бета с такой сборкой ушла бы к
пользователям неподписанной — риск безопасности и репутации, а не только
неудобство Gatekeeper.

Правило: **бета и альфа подписываются и заверяются так же, как стабильный**
(v0.1.1 и дальше — Developer ID + нотаризация). В `release.yml`:

- для тега `v*` (любого канала) отсутствие `CSC_LINK` или данных
  нотаризации — ошибка шага, а не предупреждение; сборка «для себя»
  остаётся только для `workflow_dispatch` без тега;
- после сборки — проверка на раннере macOS: `codesign --verify --deep
  --strict` и `spctl -a -vv` на `.app`, `xcrun stapler validate` на `.dmg`;
  провал — релиз не публикуется (остаётся черновиком);
- Windows — тот же порядок, что у стабильного на момент выпуска: пререлиз не
  получает более слабую подпись, чем стабильный.

**Windows сейчас без подписи.** Сертификата для Windows нет: `release.yml`
прямо пишет это в описании релиза, SmartScreen предупреждает при установке.
«Не слабее стабильного» здесь значит «так же без подписи» — правило не
делает бету хуже, но и не делает её подписанной. Это не юридический дефект,
а вопрос доверия: неподписанный `.exe` тестовой сборки труднее отличить от
подделки, а бета публична (§6.7). Владелец решает при включении (§8, шаг 7):

- выпускать бету для Windows без подписи, как стабильный (по умолчанию);
- или не выкладывать Windows-установщик в пререлизы, пока нет сертификата
  (`matrix` в `release.yml` пропускает `win` для тега с `-`; Windows-
  пользователи беты остаются на стабильном) — решение записывается в цель
  (`channels.beta.platforms`, на потом, §10), если владелец его выберет.

Появится сертификат Windows — `release.yml` начинает требовать его для
любого тега так же, как `CSC_LINK` для macOS.

### 6.7 Бета публична

Бета- и альфа-релизы публикуются в **публичном** GitHub Release того же
репозитория. «Только для выбравших бету» означает только автообновление:
скачать установщик и прочитать заметки может любой, кто смотрит релизы.
Публикация необратима: удалённый релиз остаётся в кешах и зеркалах.

Следствия:

- в бету не выпускать то, что нельзя показывать всем (неанонсированные
  функции, ключи, внутренние адреса). Менеджер при `start_release` на
  пререлизный канал видит это предупреждение в описании инструмента, а
  вопрос владельцу о выпуске пререлиза (согласие из цели, спека выпусков)
  показывает строку «Сборка и заметки будут публичны»;
- **проверка заметок перед публикацией** — шаг процесса, а не только
  текст. Узел `notes` процесса `release` (§5.3) для пререлизного
  канала (и для стабильного тоже — релиз публичен всегда) прогоняет
  заметки и список коммитов через фильтр: строки, похожие на ключи и
  токены (те же шаблоны, что у секретных переменных офиса), внутренние
  адреса (`localhost`, приватные диапазоны IP, `*.internal`), пути
  домашних каталогов, имена задач с пометкой «не публиковать». Нашлось —
  выпуск не идёт дальше: вопрос владельцу с найденными строками («убрать»
  / «оставить как есть»). Сами заметки целиком владелец видит в вопросе о
  выпуске пререлиза до тега — его «Выпускай» и есть проверка содержания;
- сборка: в установщик попадает только то, что собирает `builder.config.js`
  (`files`), секреты CI в сборку не пишутся (§6.6 — сертификат передаётся
  именем). Новые файлы в `files` — пункт ревью задачи, которая их добавляет;
- если владельцу нужна закрытая бета, это другой канал доставки (приватный
  репозиторий обновлений или `generic`-провайдер с доступом по ключу) —
  продуктовый выбор, вынесен в §10.

## 7. Приложение

### 7.1 Где хранится канал

`desktop/paths.js` → `updatePrefsFile()` = `<userData>/update-channel.json`:
`{ "channel": "stable" | "beta" | "alpha", "consent"?: { "channel", "text",
"version", "at" } }` — `consent` пишется диалогом §7.7: какой канал принят,
версия текста согласия, версия приложения и время. Не в `web-storage.json`: канал
нужен главному процессу при старте, до окна. Файла нет — канал по
установленной версии: `app.getVersion()` с `-beta.` → `beta`, с `-alpha.` →
`alpha`, иначе `stable`. Так скачанный руками бета-установщик остаётся на
бете.

### 7.2 Настройка electron-updater (`desktop/updater.js`)

```js
function applyChannel(channel) {
  updater.allowPrerelease = channel !== 'stable';
  updater.channel = channel === 'stable' ? 'latest' : channel;
  // Сеттер channel в electron-updater 6 сам включает allowDowngrade —
  // откат версии без спроса нам не нужен, выключаем после него.
  updater.allowDowngrade = false;
}
```

Вызывается в `init` до первой проверки и в `setChannel`. Явное
`allowPrerelease = false` обязательно: electron-updater по умолчанию
включает его, если текущая версия — пререлиз, и вернувшийся на stable
пользователь беты продолжал бы получать беты.

По логике `GitHubProvider` electron-updater 6: канал `beta` берёт первый в
ленте релиз, который бета или стабильный (альфы пропускает); `alpha` — любой;
`latest` — только `releases/latest`.

**Проверено по коду `electron-updater@6.8.9`** (версия из
`desktop/package-lock.json`; T-403, без сборки и живого релиза):

- **Какой релиз выбирает `GitHubProvider` при `allowPrerelease`**
  (`out/providers/GitHubProvider.js`, `getLatestVersion`). Читается Atom-лента
  `releases.atom`. Канал берётся из `updater.channel`, а если он пуст — из
  суффикса текущей версии. Дальше обход ленты сверху вниз до первого
  подходящего: для `beta` и `alpha` подходит тег с валидным semver без
  суффикса или с суффиксом `alpha`/`beta`; для `beta` дополнительно
  пропускается `alpha`. Своё имя канала (`-rc.1` и т. п.) пропускается.
  Выводы:
  - описание выше верно: `beta` — первая в ленте бета или стабильная, `alpha` —
    первая любая из трёх;
  - «первая» — по порядку ленты, то есть **по времени создания релиза, а не по
    semver**. Хотфикс `1.4.3`, вышедший после `1.5.0-beta.3`, бета-канал
    увидит первым; electron-updater ответит `update-not-available`, потому что
    `1.4.3 < 1.5.0-beta.3` и `allowDowngrade = false`. Это и нужно: бета не
    откатывается на хотфикс. Следующая бета снова окажется сверху;
  - лента отдаёт только последние записи (у GitHub около десяти), черновики в
    неё не попадают;
  - файл канала: для тега с суффиксом — `beta-mac.yml` / `alpha-mac.yml`
    (`beta.yml` на Windows), при 404 — откат на `latest-mac.yml`. Для
    стабильного релиза на бета-канале сначала запрашивается `beta-mac.yml`, а
    после 404 — `latest-mac.yml`. Лишний 404, но обновление находится;
  - с `allowPrerelease = false` (наш stable) лента не используется: тег берётся
    из `releases/latest` (GitHub не отдаёт там пререлизы и черновики), файл —
    `latest-mac.yml`.
- **Включает ли сеттер `channel` сам `allowDowngrade`** (`out/AppUpdater.js`,
  `set channel`). Да, безусловно: `this._channel = value; this.allowDowngrade =
  true`, это же написано в его JSDoc. Отсюда `allowDowngrade = false` после него
  в `applyChannel` (`desktop/channel.js`). Конструктор, кроме того, ставит
  `allowPrerelease = hasPrereleaseComponents(текущая версия)`, поэтому явное
  `allowPrerelease` в `applyChannel` тоже нужно. Флаг проверяется только в
  `isUpdateAvailable` при проверке. `downloadUpdate` найденное обновление не
  перепроверяет: он берёт сохранённый `updateInfoAndProvider`. Поэтому при
  откате флаг включается на одну проверку и сразу выключается
  (`desktop/updater.js` → `downgrade`).
- **Пройдёт ли откат через Squirrel.Mac** (`out/MacUpdater.js`). Скачанный zip
  `MacUpdater` раздаёт с локального прокси на `127.0.0.1`. Нативному
  `autoUpdater` Electron он отдаёт `setFeedURL` с JSON `{ "url": … }` без
  версии, а потом вызывает `checkForUpdates`. Squirrel.Mac в режиме
  JSON-ответа версии не сравнивает: ответ 200 для него означает «есть
  обновление», решение принимает сервер. Проверяет он только подпись нового
  бандла: designated requirement должен совпадать с установленным. Значит,
  откат через Squirrel.Mac проходит, если стабильная версия подписана тем же
  Developer ID (§6.6). Версию решает только `isUpdateAvailable` в
  electron-updater. Вывод сделан по коду electron-updater и устройству
  Squirrel.Mac; вживую (собранная бета → откат на стабильную) **не
  проверен**. Это пункт ручной проверки §8. Откат на Windows (NSIS, тихая
  установка старшей версии поверх младшей) по коду не разбирался и тоже
  остаётся на ручную проверку.

### 7.3 Переключение канала

- `setChannel(c)`: запись в файл, `applyChannel`, сброс состояния в `idle` и
  проверка. Пока идёт загрузка (`downloading`), смена канала недоступна.
  Скачанное, но не поставленное обновление (`ready`) другого канала
  сбрасывается: оно ставится только по `restartNow`
  (`autoInstallOnAppQuit = false` до согласия), так что просто забываем его.
- stable → beta (и любой переход на более сырой канал): **сначала диалог
  согласия** (§7.7), канал меняется только по кнопке «Перейти на бету».
  Отмена или закрытие диалога — канал прежний. Это касается и радиокнопок в
  меню приложения: они не переключают сразу, а открывают тот же диалог.
  Следующая проверка найдёт старшую из беты и стабильного.
- beta → stable не требует согласия: обновлений станет меньше, не больше
  (поведение версии — §7.4).

### 7.4 Возврат с беты на стабильный

Пример: стоит `1.5.0-beta.3`, последний стабильный — `1.4.2`.

**По умолчанию — ждать следующего стабильного.** С `allowDowngrade = false`
electron-updater ответит `update-not-available` с версией `1.4.2` в info.
Пользователь остаётся на `1.5.0-beta.3` без новых бет, и как только выйдет
стабильный `1.5.0` (а он по semver старше `1.5.0-beta.3`), получит его
обычным обновлением. Блок обновлений пишет:

> Вы на бете 1.5.0-beta.3. Стабильный канал пришлёт обновление с выходом
> 1.5.0 — новых бет больше не будет. [Вернуться на 1.4.2 сейчас]

**Откат — только явной кнопкой и только после подтверждения.** «Вернуться
на 1.4.2 сейчас»:

1. **Предупреждение до любого действия** — модальный диалог; ничего не
   скачивается и не копируется, пока пользователь его не подтвердил. Текст
   (черновик, на проверку юристу — §7.9):

   > **Откат на 1.4.2 может испортить данные.** Версия 1.5.0-beta.3 могла
   > записать офисы, доски задач и журнал в виде, который 1.4.2 не понимает.
   > После отката часть этих данных может пропасть или отображаться неверно.
   > Перед откатом мы сохраним полную копию данных в папку
   > «{путь к копии}». Вернуть её можно в настройках обновлений:
   > «Восстановить данные из копии».
   >
   > Копия хранится только на этом компьютере и никуда не отправляется. В ней
   > всё, что есть в офисах: задачи, переписка с агентами, журнал, а также
   > ключи и секретные переменные офисов, если они там записаны. Приложение
   > само копию не удаляет — удалите её в настройках обновлений, когда она
   > станет не нужна.
   >
   > ☐ Я понимаю, что часть данных может быть потеряна
   >
   > [Отмена] [Откатить на 1.4.2]

   Кнопка «Откатить» недоступна, пока не отмечена галочка; кнопка по
   умолчанию (Enter, Esc) — «Отмена». Без согласия — никакого отката.
2. Копия **всего каталога состояния** `<userData>/office/` (state.json и
   файлы офисов) в `<userData>/backups/<дата>-before-downgrade-<версия>/`
   плюс `manifest.json` (версия, канал, время, список файлов с размерами).
   Копия не удалась (нет места, ошибка записи) — откат отменяется с
   сообщением, а не идёт дальше без копии.
3. `allowDowngrade = true` на одну проверку, `checkForUpdates`, загрузка,
   `restartNow` — тот же ручной поток с `busy`. После перезапуска флаг снова
   `false` (не хранится).

**Хранение и возврат копии.**

- Копии в `<userData>/backups/` приложение **само не удаляет** — ни при
  откате, ни при обновлении. Удаляет только пользователь (кнопка «Удалить»
  у копии) или вручную. Почему не автоудаление: копия — единственный путь
  назад после неудачного отката, и стереть её молча хуже, чем держать.
- Копия содержит то же, что каталог состояния: персональные данные из
  задач и переписки и, возможно, секреты офисов. Поэтому: каталог копии
  создаётся с правами только владельца учётной записи (`0700`, на Windows —
  в профиле пользователя, как и `<userData>`); секретные переменные из
  системной связки ключей (`keys.ts`) в копию **не** выгружаются — копируется
  только то, что уже лежит в `<userData>/office/`; в списке копий у каждой
  строка «Содержит данные офисов, в том числе личные — храните как сами
  данные». Пользователь об этом узнаёт в диалоге отката (п. 1), до создания
  копии.
- Напоминание: копия старше 30 дней — в блоке обновлений одна строка
  «Есть копии данных старше 30 дней: {n}. [Посмотреть]». Ничего не удаляет,
  только напоминает.
- В блоке обновлений (§7.6) и в меню «Помощь» — пункт «Восстановить данные
  из копии…»: список копий (дата, версия, из которой сделана), «Показать в
  Finder/Проводнике», «Восстановить». Восстановление: подтверждение («текущие
  данные будут заменены; их копия тоже будет сохранена»), остановка сервера
  офиса, копия текущего состояния тем же способом, замена каталога,
  перезапуск сервера.
- Восстанавливать копию беты имеет смысл в версии не младше той, что её
  записала (например, вернувшись на бету или дождавшись 1.5.0). Если версия
  младше — перед восстановлением то же предупреждение, что в п. 1.
- Поэтому восстановление должно быть уже в стабильной версии, на которую
  откатываются: оно входит в стабильный выпуск с выбором канала (§8, шаг 6),
  и откат ниже этой версии кнопка не предлагает: если последний стабильный
  младше первой версии с выбором канала, кнопки отката нет, остаётся только
  ожидание стабильного.

Почему не откат по умолчанию: тихий даунгрейд на старый формат состояния —
худший исход для доски задач; ожидание стабильного ничего не ломает. Почему
не «вообще без отката»: если бета сломала работу, у человека должен быть
выход без переустановки.

Если стабильный уже не младше текущей (например, сидит на `1.4.3-beta.1`,
вышел `1.4.3`) — это обычное обновление, отката нет.

### 7.5 Контракт и мост

- `src/shared/types.ts`: `export type UpdateChannel = 'stable' | 'beta' | 'alpha'`;
  в `UpdateState` — `channel: UpdateChannel`, `current: string` (версия
  приложения) и `stableBehind?: string` — версия стабильного, если он
  младше текущей (условие текста §7.4).
- `src/shared/desktop.ts` → `OfficeDesktopUpdates`: `setChannel(c):
  Promise<UpdateState>`, `downgrade(): Promise<UpdateCommandResult>`.
  Канал читается из `getState()`. Старое приложение без этих методов — веб
  прячет выбор канала.
- `desktop/main.js`: IPC `office:update-channel`, `office:update-downgrade`
  (с той же проверкой `fromOffice`), подменю «Канал обновлений» с
  радиокнопками в меню приложения рядом с «Проверить обновления…».
- `desktop/preload.js` / `desktop/office-preload.js` — мост.
- `desktop/i18n.js` — строки меню и диалога отката.

### 7.6 Интерфейс (`src/web/shell/UpdateBlock.tsx`)

Переключатель «Канал обновлений»: «Стабильный» / «Бета — новое раньше, может
быть сыро» / «Альфа — для разработчиков». Альфа показывается, только если
текущая версия — альфа или пользователь включил её с зажатым Alt (не
мозолит глаза). Под переключателем — текст §7.4, если `stableBehind`.
Выбор беты или альфы открывает диалог согласия §7.7, а не переключает
сразу. Ниже — «Восстановить данные из копии…» (§7.4), если копии есть.

### 7.7 Согласие на тестовый канал

Переход на бету или альфу — осознанное согласие на риск, а не радиокнопка.
Диалог (черновик текста, на проверку юристу — §7.9):

> **Бета-версии — тестовые сборки.** Они выходят раньше стабильных и могут
> работать с ошибками, в том числе терять или портить данные офисов, досок и
> журнала. Бета-версии предоставляются «как есть», без каких-либо гарантий
> (см. лицензию Apache 2.0, раздел 7). Делайте копии важных данных.
>
> Вернуться на стабильный канал можно в любой момент; откат версии может
> привести к потере данных, записанных бетой.
>
> Бета-сборки публичны: их заметки и установщики видны всем на странице
> релизов.
>
> ☐ Я понимаю риски и хочу получать бета-версии
>
> [Отмена] [Перейти на бету]

- Кнопка подтверждения недоступна без галочки; кнопка по умолчанию —
  «Отмена». В приложении (T-403) диалог нативный (`dialog.showMessageBox` с
  `checkboxLabel`), а он не умеет выключать кнопку. Поэтому подтверждение без
  галочки ничего не меняет: диалог показывается снова с подсказкой «отметьте
  галочку». Так же устроен диалог отката §7.4.
- Для альфы — тот же диалог с усиленной первой фразой («сборки для
  разработчиков, ломаются чаще»).
- Согласие записывается в `update-channel.json` → `consent` (§7.1) с
  версией текста (`text: 1`). Поменялся текст (`text` вырос) — при следующей
  проверке обновлений на бете диалог показывается снова; без нового согласия
  приложение возвращается на `stable` (поведение §7.4, без отката).
- Скачанный руками бета-установщик (канал по версии, §7.1) без записи
  согласия при первом запуске показывает тот же диалог; «Отмена» — канал
  `stable`.

### 7.8 Канал не меняет сбор данных

Выбор беты или альфы **не включает никакого сбора данных**:

- проверка обновлений обращается к GitHub так же, как на стабильном; канал
  никуда не отправляется;
- телеметрия исходов задач (`Settings.marketTelemetry`, `tellOutcome`)
  остаётся отдельной галочкой, по умолчанию выключенной, на любом канале;
  код беты не может её включить или изменить умолчание;
- отчёты о сбоях не собираются (§10). Если появятся — отдельным согласием и
  с обновлением политики конфиденциальности, не через выбор канала.

### 7.9 Юридические тексты — до включения беты

Репозиторий под Apache 2.0, раздел 7 лицензии — отказ от гарантий «как
есть»; он распространяется и на бета-сборки. Отдельного пользовательского
соглашения и политики конфиденциальности у приложения сейчас нет.

До того как бета станет доступна пользователям (§8, шаг 6), **живой юрист**
проверяет:

- текст согласия §7.7 и предупреждения об откате §7.4, включая абзац о
  содержимом и хранении копии данных;
- достаточно ли ссылки на Apache 2.0 или нужен отдельный пункт о тестовых
  сборках в пользовательском соглашении (и нужно ли само соглашение).
  Сомнение конкретное: Apache 2.0 — лицензия на исходный код, а
  пользователь беты получает готовую бинарную сборку через автообновление
  и лицензию не читал; кроме того, отказ от гарантий может не действовать
  там, где закон о защите потребителей его не допускает;
- в каких юрисдикциях пользователи и какое право применимо — сейчас не
  определено, и от этого зависит ответ на предыдущий пункт;
- нужна ли политика конфиденциальности уже сейчас (локальные копии с
  персональными данными, §7.4), даже без сбора данных (§7.8);
- текст в описании пререлиза (§6.2) — он не заменяет согласие в
  приложении, но тоже публичен.

Что офис **не делает** до ответа юриста: не пишет в интерфейсе, заметках
и документах «соответствует закону …» или «отвечает требованиям …» —
проверки по первоисточникам не было. Обзор с открытыми вопросами —
`docs/legal/T-384/review.md`.

Если юрист скажет, что нужно пользовательское соглашение, — это отдельная
задача (текст, показ при первом запуске, версия принятия рядом с
`consent`), и включение беты для пользователей (§8, шаг 6) ждёт её.

Тексты в спеке — черновики. В интерфейс они попадают через словари
(`src/web/i18n`, `desktop/i18n.js`) на обоих языках, и версия текста
(`text` в §7.7) растёт при каждой правке по итогам проверки.

### 7.10 Открытые юридические вопросы — гейт до включения беты для пользователей

Пока на каждый пункт нет ответа или решения владельца, бета для
пользователей не включается (§8, шаг 6). Сборки беты при этом выпускать
можно — стабильные приложения их не увидят (§6.3).

1. **Тексты — черновики.** Согласие на бету (§7.7), предупреждение об
   откате (§7.4) и описание пререлиза (§6.2) проверяет живой юрист. Он же
   отвечает, нужно ли пользовательское соглашение сверх отказа от гарантий
   Apache 2.0 §7.
2. **Юрисдикция и применимое право не определены.** От них зависит ответ
   на пункт 1.
3. **Копии данных.** `<userData>/backups/` может содержать персональные
   данные и секреты; копии хранятся бессрочно — приложение само их не
   удаляет (§7.4).
4. **Бета-релизы публичны и не отзываются** (§6.7). Защита процессная:
   фильтр заметок и согласие владельца на каждый выпуск.
5. **Windows-сборка без подписи** — решение владельца (§8, шаг 7, §6.6).
6. **Отчёты о сбоях не планируются** (§7.8, §10). Если появятся —
   отдельное согласие пользователя.

В интерфейсе, заметках и документах не писать «соответствует закону X»
или «отвечает требованиям X» (§7.9). Разбор — `docs/legal/T-384/review.md`.

## 8. Включение для приложения

1. Влиты задачи §9.1–§9.4 (сервер + CI). Сервер перезапущен.
2. Владелец заводит ruleset для `beta` и `release` (§6.5) и проверяет, что
   секреты подписи и нотаризации на месте: без них выпуск по тегу теперь
   падает (§6.6).
3. Менеджер предлагает цель `desktop` с каналами (`propose_release_target`,
   пример §5.1); владелец применяет.
4. **Первые ветки.** Нет ветки канала — офис создаёт её на коммите
   последнего стабильного тега (`v0.10.0`) при первом выпуске этого канала:
   `release` и `beta` от `v0.10.0`, оба — предки `main`, инвариант выполнен.
5. Первая бета: `0.11.0-beta.1` (разряд по плану) из `main`.
6. Приложение с выбором канала (§9.5) должно выйти **стабильным** выпуском
   до того, как на бету кто-то переключится, — иначе переключать нечем.
   Порядок: стабильный 0.11.0 с выбором канала → дальше беты. Перед этим
   стабильным выпуском тексты §7.7 и §7.4 проверены юристом (§7.9);
   восстановление из копии (§7.4) входит в него же.
7. Владелец знает, что бета публична (§6.7), и решает, устраивает ли это.
   Тот же вопрос — про Windows: бета без подписи, как стабильный, или без
   Windows-установщика, пока нет сертификата (§6.6).

До шага 6 бета-сборки уже безопасны: стабильные приложения 0.10.x их не
увидят (§6.3).

## 9. Задачи реализации

Порядок: 9.1 → 9.2 → 9.3; 9.4 и 9.5 параллельно с ними; 9.6 после 9.3 и 9.5.

### 9.1 Сервер: версии (backend)

`src/shared/release.ts`: `parseVersion` (полный semver с пререлизом),
`compareSemver` по semver, `RELEASE_CHANNELS`, `channelSchema` и проверки
`parseReleaseConfig` (§5.1), `nextChannelVersion(tags, channel, level,
planVersion)` по §4.2. `releases.ts`: `currentVersion`/`lastTagSha` на новом
счёте (§4.3). Тесты в `scripts/test-releases.ts`: таблица §4.2, сортировка
пререлизов, стабильная цель без каналов не считает от беты.

### 9.2 Сервер: ветки и продвижение (backend)

`git.ts`: `promoteBranch`, `mergeDown` с разрешением конфликта версии;
временные ветки `office/rel/<id>` и миграция `release/*`. `releases.ts`:
источник снимка по каналу, расхождение и лечение (§3.4), `publish` с
продвижением и слиянием вниз, поля `Release` (§5.2), поводы по каналу,

временном репозитории: бета → стабильный → хотфикс → бета, инвариант
`release ⊆ beta ⊆ main` после каждого шага; расхождение после хотфикса
останавливает стабильный.

### 9.3 Сервер: инструменты и статус (backend)

`agents.ts`: `start_release({channel, hotfix})`, `propose_release_target({channels})`,
`create_task({onto})`, `release_status` по каналам; `describeTarget`;
команда клиента `release_start` с каналом; i18n сервера; абзац в брифе
менеджера.

### 9.4 CI (backend)

`release.yml`: канал из тега, файлы каналов, prerelease/latest, обязательные
файлы по каналу; `builder.config.js`: `generateUpdatesFilesForAllChannels`;
`release-notes.mjs`: прошлый тег по виду; `ci.yml`: ветки каналов. Пробная

`ReleaseHost.latest`, проверка видимости по каналу. Обязательная подпись и
нотаризация для любого тега и проверка `codesign`/`spctl`/`stapler` перед
публикацией (§6.6). Строка «Сборка и заметки будут публичны» в согласии на
пререлиз и предупреждение в описании `start_release` (§6.7); фильтр
конфиденциального в узле `notes` с вопросом владельцу и тестом на
шаблонах (§6.7). Памятка
владельцу про ruleset и секреты подписи (§6.5, §6.6) — в

### 9.5 Приложение (backend)

`updater.js` (`applyChannel`, `setChannel`, `downgrade`, `stableBehind`),

## 10. На потом

- Выдержка беты перед стабильным («бета не младше 3 дней и без жалоб») —
  поле `stable.minBetaHours` и проверка в `snapshot`.
- Раздача беты части пользователей (`stagingPercentage` electron-updater).
- Каналы для `push`- и `command`-целей (TestFlight уже сам по себе бета).
- Сбор отчётов о сбоях с пометкой канала — только с отдельным согласием и
  обновлённой политикой конфиденциальности, проверенной юристом (§7.8).
- `channels.beta.platforms` — платформы пререлиза (например, без Windows,
  пока нет сертификата, §6.6), если владелец выберет этот вариант.
- Пользовательское соглашение и политика конфиденциальности — если их
  потребует юрист (§7.9).
- Закрытая бета (приватный репозиторий обновлений или `generic`-провайдер
  с доступом), если публичность пререлизов (§6.7) владельца не устроит.

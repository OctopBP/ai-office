**Токены (`src/web/styles/tokens.css`, `kit.css`)** — основа для правил уже хорошая:

- радиусы 5/8/9/10/12/16/pill; высоты контролов 32/28/26; слои `--z-*`;
- кегли: 10 / 11 / 12 / 12.5 / 13 / 15 / 16; шрифт Inter; две темы (day/night) через `[data-theme]`;
- акценты `--accent-1..8` с парой `-ink` (подобраны по яркости, в комментарии есть требование проверять контраст при смене цвета).

Замечания по токенам, которые правила обнаружат сразу (расчёт вручную, перед внедрением проверить скриптом):
1. `--ink-4: #95979e` на белом ≈ **2,9:1** — ниже 4,5:1 для текста; подписано «подпись в активной строке», т.е. это текст.
2. `--ink-3: #6e6e6e` на белом ≈ 5,1:1 — проходит, но на `--film`/`--canvas` запас маленький.
3. `--warn: #f2a33a` как цвет **текста** на белом ≈ 2:1 — годится только как заливка/иконка с подписью.
4. `--fs-caption: 10px` и `--fs-small: 11px` — ниже общепринятого минимума 12 px для читаемого текста; для подписей допустимо, для основного содержимого — нет.
5. Шкала отступов заканчивается на 32, а в Figma-макетах есть 40/48; шкала 12/20 — вне 8-pt сетки (она 4-pt, что осознанно).
6. Высота контрола 32 px (WCAG 2.5.8 требует ≥ 24 — проходит; 44 нужны только для тач-режима).

## 3. База стандартов, которые стоит превратить в проверки

Источники: [WCAG 2.2](https://www.w3.org/TR/WCAG22/), [10 эвристик Нильсена](https://www.nngroup.com/articles/ten-usability-heuristics/), [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/), [Material 3](https://m3.material.io/), [Figma: variables, auto layout, components](https://help.figma.com/hc/en-us).

| Область | Что берём (измеримое) |
|---|---|
| Контраст (WCAG 1.4.3, 1.4.11) | Текст ≥ 4,5:1, крупный (≥ 18 px или ≥ 14 px жирный) ≥ 3:1; границы полей, иконки-кнопки, состояния ≥ 3:1 против фона. Проверять в **обеих темах** |
| Не только цвет (1.4.1) | Статус = цвет + иконка/слово |
| Фокус (2.4.7, 2.4.11, 2.4.13) | У каждого интерактивного элемента виден фокус-индикатор ≥ 2 px, контраст ≥ 3:1; не перекрывается липкими панелями |
| Размер цели (2.5.8) | ≥ 24×24 CSS px (или 24 px зазор); для тач-режима — HIG 44 pt, Material 48 dp |
| Клавиатура (2.1.1, 2.1.2) | Всё доступно с клавиатуры, нет ловушки, порядок Tab = порядок чтения; Esc закрывает оверлей |
| Текст и масштаб (1.4.4, 1.4.12) | Интерфейс живёт при масштабе 200 % и увеличенных интервалах; кегль в относительных единицах |
| Движение (2.3.3, `prefers-reduced-motion`) | Любая анимация отключаема; ничего не мигает > 3 раз/с |
| Эвристики Нильсена | #1 видимость состояния; #3 контроль и свобода (отмена, назад); #4 единообразие; #5 предотвращение ошибок; #6 узнавание вместо припоминания; #9 понятные сообщения об ошибках (что случилось + что делать); #10 помощь |
| Сетка и отступы | Базовая сетка 4/8 px, отступы только из шкалы; у нас — `--space-*`; внутренний отступ ≤ внешнего (близость по Гештальту) |
| Типографика | Ограниченная шкала (у нас 6 кеглей), ≤ 2 семейства, ≤ 3 начертаний на экране; межстрочный 1,4–1,6 для текста; длина строки 45–80 знаков |
| Состояния компонента | default · hover · focus · pressed/active · disabled · loading · error · selected; для экрана — пусто · загрузка · ошибка · частично · полный · нет прав/офлайн |
| Токены | Ни одного «голого» hex/px в макете и CSS; цвет только `--ink*/--surface/--accent*`; семантика (`--danger`), а не цвет (`--red`); обе темы — из одного набора |
| Figma | Каждый повторяющийся блок — компонент; варианты вместо копий; Auto Layout везде, где есть список/ряд; переменные для цвета/отступа/радиуса; имена слоёв осмысленны (`Row/Task`, не `Frame 427`); состояния лежат рядом с экраном |
| HIG / Material (по месту) | Для **приложения macOS/Windows** (`desktop/`): стандартные меню и хоткеи платформы, Cmd/Ctrl, области перетаскивания окна; Material — только как справочник по состояниям и анимации (стандартные кривые, 150–300 мс), не как стиль |
| Тексты (UX-writing) | Кнопка — глагол («Сохранить», не «ОК»); ошибка: что произошло + что сделать; одинаковые слова для одного действия; тексты на обоих языках интерфейса (словари `i18n`) |

## 4. Черновик правил (формулировки для `RULES.md`)

Каждое правило — одна проверяемая фраза ≤ 500 знаков; по возможности с числом или ссылкой на токен. Помечено, кто проверяет: **Д** — дизайнер, **Ф** — фронтенд, **Р** — ревьюер.

1. Текст и значимые иконки имеют контраст ≥ 4,5:1 (крупный текст ≥ 3:1) в обеих темах; считай по формуле WCAG, а не на глаз; `--ink-4` не используй для текста (светлая тема 2,92:1, тёмная 3,68:1 — обе ниже 4,5:1). **Д Ф Р**
2. Границы полей, значки-кнопки и состояния имеют контраст ≥ 3:1 к соседнему фону. **Д Ф**
3. Смысл не передаётся одним цветом: статус, ошибка и выбор — цвет плюс иконка или слово. **Д Ф Р**
4. У любого интерактивного элемента нарисован и реализован видимый фокус (обводка ≥ 2 px, контраст ≥ 3:1) и все действия доступны с клавиатуры; Esc закрывает оверлей. **Д Ф**
5. Область нажатия ≥ 24×24 px (в тач-режиме ≥ 44); мелкая иконка получает увеличенную невидимую зону. **Д Ф**
6. Отступы, радиусы, кегли, цвета и слои — только токены из `tokens.css`; число вне шкалы не вводи — спроси или предложи новый токен отдельным пунктом. **Д Ф Р**
7. Основной текст ≥ 12 px; 10–11 px — только подписи секций и второстепенные метки; не более 6 кеглей и 3 начертаний на экране. **Д Ф**
8. У каждого экрана и компонента с данными нарисованы и реализованы состояния: пусто, загрузка, ошибка (с действием «повторить»), частичные данные; у контрола — hover, focus, pressed, disabled. **Д Ф Р**
9. Сообщение об ошибке говорит, что случилось и что делать; кнопка называется глаголом действия («Сохранить», не «ОК»). **Д Ф**
10. Разрушительное действие (удалить, откатить, сбросить) подтверждается или отменяется («Отменить» в тосте) и визуально отличается от обычного. **Д Р**
11. Любая асинхронная операция > 1 с показывает прогресс или состояние; состояние системы всегда видно (Нильсен №1). **Д Ф**
12. Одно действие называется одним словом во всём интерфейсе; новый элемент берётся из кита (`kit.css`), а не рисуется заново; новый вариант заводится в ките. **Д Ф Р**
13. Все тексты интерфейса лежат в словарях `i18n` на обоих языках; в макете проверена длина русской строки (она на ~20–30 % длиннее английской), обрезка — с многоточием и подсказкой. **Д Ф**
14. Анимация ≤ 300 мс, только для показа смены состояния, и отключается при `prefers-reduced-motion`; ничего не мигает чаще 3 раз в секунду. **Д Ф**
15. Макет в Figma собран на Auto Layout с переменными, повтор ≥ 2 раз — компонент с вариантами; слои названы по смыслу; светлая и тёмная версия сданы вместе. **Д**
16. Интерфейс не ломается при масштабе 200 %, размеры текста — относительные; ширина строки текста ≤ 80 знаков. **Ф Р**
17. В макетах приложения (`desktop/`) используй стандартные для платформы хоткеи и меню (Cmd на macOS, Ctrl на Windows); не придумывай свои для знакомых действий. **Д Ф**

Бюджет: 17 правил × ≈ 280 знаков ≈ **4,8К знаков**, а лимит блока `RULES.md` — **4000 на всех**, включая прочие правила офиса. Поэтому либо сократить до ~10 самых критичных, либо вынести часть в «круг роли» (приписка к брифу design/frontend). См. §6.

## 5. Черновик чек-листа самопроверки (перед сдачей макета / вёрстки)

Лежит скилом `ui-self-check`; агент проходит его и **в отчёте пишет «пройдено / нарушено + почему» по каждому разделу** — не «всё ок».

**A. Токены и сетка**
- [ ] Ни одного цвета, отступа, радиуса или кегля вне `tokens.css` (в Figma — из переменных файла).
- [ ] Расстояния кратны 4; внутри группы отступ меньше, чем между группами.
- [ ] Новый компонент похож на существующий из `kit.css`; различия объяснены.

**B. Доступность**
- [ ] Контраст проверен числом для каждого цвета текста в светлой и тёмной теме (3 наименее контрастных пары названы в отчёте).
- [ ] Фокус виден у всех интерактивных элементов; порядок Tab совпадает с порядком чтения.
- [ ] Цели нажатия ≥ 24 px; статус не передаётся только цветом.
- [ ] Анимации отключаются при `prefers-reduced-motion`.

**C. Состояния**
- [ ] Для экрана: пусто · загрузка · ошибка · частично · полный нарисованы/проверены.
- [ ] Для контрола: default · hover · focus · pressed · disabled (+ selected/error, если применимо).
- [ ] Экстремальные данные: очень длинный текст, 0 и 1000 элементов, русский текст длиннее английского.

**D. Эвристики Нильсена (по одной строке «где соблюдено»)**
- [ ] Видимость состояния · [ ] отмена/выход из действия · [ ] единообразие слов и элементов · [ ] защита от ошибки (подтверждение, ограничение ввода) · [ ] узнавание, а не припоминание · [ ] понятные ошибки с действием.

**E. Тексты**
- [ ] Кнопки — глаголы; ошибки — «что случилось + что делать»; нет технических кодов в тексте для человека.
- [ ] Строки на обоих языках в `i18n` (для вёрстки).

**F. Figma (для дизайнера)**
- [ ] Auto Layout, переменные, компоненты с вариантами, осмысленные имена слоёв.
- [ ] Светлая и тёмная версии рядом; скриншот проверен (`get_screenshot`), а не «собрано вслепую».

**G. Фронтенд (при вёрстке)**
- [ ] Семантические теги (`button`, `label`, `nav`), `aria-*` там, где нет нативной семантики.
- [ ] Масштаб 200 % не ломает раскладку; проверено в обеих темах.

## 6. Рекомендация: что куда и в каком порядке

### Раскладка

| Что | Куда | Почему |
|---|---|---|
| Короткие числовые правила (§4: 1, 2, 3, 4, 5, 6, 8, 9, 11 — самые «острые») | **Правила круга роли** design и frontend (приписка к брифу), а не общий `RULES.md` | `RULES.md` репозитория едет **всем** ролям, включая бэкенд и ревьюера; у блока лимит 4000 знаков. UI-правила бэкенду — шум и токены. Ревьюеру их дать надо — ему можно приписать отдельно |
| Общепроектные принципы (§4: 6, 8, 12 в 1–2 фразах) | `RULES.md` репозитория, ≤ 3 правила | Единственное, что касается всех, кто трогает `src/web`: «только токены», «состояния обязательны», «не рисуй новый элемент, если есть в ките» |
| Справочник стандартов (§3), эвристики, WCAG, типографика, Figma-практика | **Скилы** пакета design: `ui-standards` (≈ 2К токенов, на базе szilu `03/04/06/07` + trevorgrogers `design-heuristics`, переписано в проверяемую форму), он же читается фронтендом | Скил грузится по описанию и стоит токенов только когда нужен |
| Чек-лист самопроверки (§5) | **Скил** `ui-self-check` (≈ 0,8–1К) + строка в брифе: «перед сдачей пройди `ui-self-check` и приведи результат в отчёте» | Чек-лист — это процедура, не запрет: ему место в скиле; одна строка в брифе гарантирует, что его вызовут |
| Контраст и размеры цели как проверка | **Скрипт** `scripts/check-contrast.ts`: считает контраст пар `--ink*/--surface/--accent*-ink` обеих тем по `tokens.css`, падает при < 4,5:1 | Единственный способ сделать правило действительно «проверяемым»; запускает конвейер, а не агент; сразу ловит `--ink-4` |
| Готовые наборы целиком (`frontend-design`, plugin87) | **Не ставить** | Либо уводят в «выразительность» против нашей системы, либо несут свои токены и вес 6К в каждую сессию |

Лицензии: MIT/Apache допускают копирование выдержек в пакет, нужно сохранить заметку об авторстве (строка «Источник» в начале скила + файл `THIRD_PARTY.md`). Для `tommyjepsen/awesome-ux-skills` (без лицензии) и `trevorgrogers/ux-designer-skills` (нет файла LICENSE) — только ссылки и свои формулировки.

Бюджет токенов: бриф +0,2К, два скила — по описанию ≈ 0,1К на сессию; полное чтение при вызове ≈ 3К. Приписка к брифу design/frontend на 10 правил ≈ 1К. Итого постоянная нагрузка ≈ 1,3К на сессию дизайнера — меньше одного `frontend-design` (2,4К).

### Что внедрять первым (порядок)

1. **Скрипт контраста + исправление `--ink-4`/`--warn` для текста** — самое «проверяемое» и самое дешёвое; закрывает правило 1 без участия агента. *(Фронтенд, 1 задача.)*
2. **Скил `ui-self-check` + строка в брифе дизайнера** («перед сдачей — чек-лист, результат в отчёт»). Даёт эффект сразу, ничего не весит в сессии, пока не вызван. *(Дизайн, 1 задача.)*
3. **Правила круга роли design и frontend: 8–10 правил из §4** (1–6, 8, 9, 11, 14). Бриф не раздувается: короткие формулировки с числами. Фронтенду приписать то же — он верстает.
4. **`RULES.md` репозитория: 3 общих правила** (токены · состояния · кит). Файла пока нет — создаётся с шапкой по спеке.
5. **Скил `ui-standards`** (справочник из §3) — вторым этапом, когда первые три показали, что агенты читают скилы; иначе вес без эффекта.
6. **Стенд (`bench/cases.json`)**: кейсы «экран без состояний» и «текст `--ink-4`» — проверить, что правила реально ловят нарушения (до/после).

### Что решить владельцу

- Давать ли UI-правила ревьюеру (рекомендую: да, правила 1, 3, 6, 8, 12 — для вёрстки; цена — ≈ 0,5К токенов).
- Тач-режим (44 px) пока не требуем: продукт десктопный (Electron + веб). Если появится мобильный экран — включить 44 px.
- Допустимо ли поднять `--fs-caption`/`--fs-small` до 11/12 (затронет плотность доски) — решение дизайнера с макетом, отдельной задачей.

# Спека: мастер нового офиса

Офис перестаёт быть равен папке проекта. **Офис — это команда плюс рабочее
пространство**, и создаётся он мастером из четырёх шагов, а не формой «имя и
путь». Проект при этом необязателен: его может ещё не быть, и офис заводит его
сам внутри выбранной папки, — или его не будет вовсе.

Состояние: фаза 1 реализована (2026-09-16), см. §9.

Родственные документы:
- `docs/design/office-menu/spec.md` — экран меню, из которого мастер открывается;
- `docs/design/agent-market/spec.md` — пакеты агентов и пакеты-команды (`kind: team`), из которых набирается штат;
- `docs/design/living-office/spec.md` §7.1 — направления владельца, куда уходит описание проекта;
- `docs/design/brainstorm/spec.md` — совещание с владельцем, естественное продолжение первого запуска.

---

## 1. Чем плохо сейчас

Форма нового офиса берёт имя и абсолютный путь. Путь обязателен и служит ключом
офиса. При первом открытии офис делает `mkdir`, кладёт README, делает `git init`
и нанимает **все десять** официальных пакетов из `packages/default-office.json`
— включая юриста, SMM и 3D-художника — в любой проект, хоть в бэкенд-сервис.

Три следствия:

1. **Проекта ещё нет, а путь уже нужен.** Человек хочет завести продукт через
   офис, а форма требует, чтобы папка уже была и он сам придумал ей место.
2. **Команда не выбирается, а достаётся.** Найм и увольнение — потом, руками,
   по одному, в окне «Команда».
3. **Несколько репозиториев — только вручную.** Роль умеет работать в своём
   репозитории (`Role.repoDir`), но папку никто не создаёт и не инициализирует:
   на старте её только проверяют, а ошибку человек узнаёт из проваленной задачи.

Половина кирпичей при этом лежит: пакеты-команды с составом и настройками
офиса уже есть (`@office/dev-team`), `market_hire_team` ставит недостающих и
нанимает по счёту, `repoFor(role)` разводит задачи по репозиториям. Не хватает
мастера, который складывает это в один проход.

## 2. Модель: офис = команда + рабочее пространство

У офиса **всегда есть корневая папка** (`OfficeEntry.projectDir`). Это решение,
а не пробел: путь используется в 88 местах в 15 файлах, и везде ожидается
директория — артефакты, журнал, `OFFICE.md`, worktree задач. Делать его
нулевым значит переписать всё это ради состояния «папки нет», которое всё равно
надо было бы чем-то заменить.

Вместо этого корень бывает трёх видов, и мастер решает, какой:

| Режим | Что за корень | Кто заводит | git в корне |
|---|---|---|---|
| **существующий проект** | папка, которую указал человек | человек | не трогаем |
| **новый проект** | `<родитель>/<папка>`; родитель существует, папка — нет | офис | `git init`, README, `.gitignore` |
| **без проекта** | `~/Office/<slug>` | офис | `git init`, README |

Признак «без проекта» — `OfficeEntry.noProject`. В меню такая карточка
подписана «без проекта», а не путём в домашней папке: путь там служебный.
Когда проект появится, к офису его прикрепляют как репозиторий роли (§4) или
меняют корень — второе на потом (§8).

**Корень мультирепо — репозиторий, а не просто папка.** Иначе документы PM и
дизайнера (`docs/`, `OFFICE.md`, артефакты) живут без истории. Вложенные
репозитории ролей корень не отслеживает: их имена попадают в `.gitignore`
корня до первого коммита — иначе `git add -A` записал бы их как gitlink и
пугал предупреждением о встроенном репозитории.

## 3. Мастер: четыре шага

Мастер открывается с карточки «+ Новый офис» и живёт окном поверх сетки, как
нынешняя форма. Шаги идут по одному, назад можно всегда; сеть трогает только
последний.

### 3.1 Что строим

Название и описание в пару строк. Описание необязательно и **не пропадает**:
после создания оно становится первым направлением владельца
(`createDirection`) и записью в ленте. Оно **не** уходит менеджеру
сообщением: это подняло бы сессию PM и начало тратить деньги ещё до того, как
человек увидел комнату. Диалог с менеджером — следующий шаг человека, не
мастера.

### 3.2 Где

Три переключателя из §2.

- **Существующая папка** — абсолютный путь, как сейчас. Опечатка не заводит
  пустую папку молча (`mustExist`).
- **Новая папка** — родитель и имя папки. Родитель предзаполнен родителем
  последнего открытого офиса, имя — slug от названия (кириллица
  транслитерируется, пусто → `project`). Папка не должна существовать: если она
  есть, это существующий проект, и мастер об этом говорит.
- **Без проекта** — полей нет, только подсказка, где будет лежать рабочая папка.

### 3.3 Кто

Список пакетов агентов: встроенные, установленные и доступные в реестре — та
же витрина, что в маркете, без ролей офиса (офиса ещё нет). У каждого —
счётчик сотрудников (0…`MAX_HIRE_COUNT`) и **рабочее место**:

| Рабочее место | Смысл | Что сделает мастер |
|---|---|---|
| общий корень | роль работает в корне офиса | ничего; `repoDir` пустой |
| своя папка `<имя>` | подпапка корня со своим репозиторием | `mkdir`, README, `git init`; `repoDir` = имя папки (относительный) |
| готовый путь | уже существующий репозиторий где-то ещё | проверка `repoProblem`; `repoDir` = абсолютный путь |

Умолчания рабочего места — из пакета: у участника команды появляется поле
`workspace` (§5), у одиночного пакета — общий корень. Менеджер в списке не
показывается: он есть всегда (`withManagerRole`), и его не нанимают.

Над списком — **готовые команды** (`kind: team`): выбор команды заполняет
счётчики и рабочие места её участниками. После этого список можно править:
команда — стартовая точка, а не контракт.

Внешние серверы роли (Figma-мост у дизайнера) видны в карточке как подпись,
без отдельного согласия: они из каталога офиса и включаются вместе с ролью,
как и при найме из маркета.

### 3.4 Строим

Экран прогресса со списком шагов; каждый — `pending → running → done | failed`
с текстом. Порядок:

1. **Корень и запись в реестре.** Для новых режимов корень заводит запись
   (`createOffice`), и реестр запоминает, что папка своя, — иначе открытие не
   стало бы делать в ней `git init`.
2. **Папки ролей.** Подпапки с README и `git init`, имена — в `.gitignore`
   корня, но только у своего корня: `.gitignore` чужого проекта без спроса не
   правим.
3. **Открытие** (`openOnce`): README корня, `git init` корня, надзор. Команда
   при этом — **только менеджер**, а не набор по умолчанию (§6).
4. **Команда.** По участнику: установить пакет, если его нет
   (`ensureInstalled`), нанять нужное число раз (`hireFromPackage`) с
   `repoDir` из рабочего места. Если начинали с пакета-команды, после найма
   применяются его настройки офиса — даже когда состав подправили: конвейер
   ревью и число фич в работе — это про офис, а не про людей.
5. **Направления.** Описание → направление владельца.

**Шаг может упасть, и офис при этом не теряется.** Не удалось поставить пакет
— остальные нанимаются; не удалось инициализировать репозиторий роли —
роль нанята с этим `repoDir`, а в ленте офиса лежит запись, что именно не
вышло, и та же проверка сработает при старте (`reportRoleRepos`). Без офиса
остаются только два случая: не удалось создать корень и не удалось открыть
офис — тогда это `office.error` с op `create`, как сегодня.

По окончании клиент получает снапшот нового офиса и входит в комнату: команда
уже за столами, в ленте — что сделано и что не вышло.

**Мастер создаёт контейнеры, а не код.** Папки, git, README, `.gitignore`.
Scaffold фреймворка — первая задача команды: иначе мастер обрастёт знанием про
Next, FastAPI и остальное, и это знание устареет быстрее, чем его напишут.

## 4. Сценарии

| Сценарий | Где | Кто | Что делает мастер |
|---|---|---|---|
| Новый продукт, несколько репозиториев | новая папка | PM, бэкенд → `backend/`, фронтенд → `frontend/`, дизайнер → корень | корень-репозиторий, два вложенных, `.gitignore` |
| Новый продукт, монорепозиторий | новая папка | все в общем корне | один репозиторий |
| Существующий проект | существующая папка | по вкусу, все в корне | ничего с папкой; найм |
| Существующие несколько репозиториев | существующая папка или без проекта | роли с готовыми путями | проверка путей; найм |
| Офис без кода (SMM, юрист, иллюстратор) | без проекта | без разработчиков | `~/Office/<slug>` с git ради истории артефактов |
| Такая же команда, другой проект | любой | команда из маркета | это пакет-команда — экспорт офиса в `kind: team` остаётся авторским путём маркета |

Не покрыто мастером и не планируется в нём: клонирование по ссылке (это
`git clone` руками до мастера, а дальше «существующая папка»).

**Выбор папки диалогом ОС.** Браузер абсолютных путей не отдаёт, но сервер
работает на той же машине, что и человек, — и диалог открывает он
(`src/server/pickfolder.ts`): на macOS панель AppKit (`NSOpenPanel`) из
`osascript -l JavaScript` — свою панель процесс показывает без разрешений, а
`choose folder` через System Events требовал бы разрешения «Автоматизация» и
падал с «Not authorized to send Apple events» (-1743); на Linux zenity или
kdialog, на Windows PowerShell.
Команда `pick_folder` несёт метку поля (`purpose`), ответ `folder.picked`
возвращает её вместе с путём: так клиент знает, в какое из трёх полей пути
класть ответ. Отмена — тишина, ошибка — строкой под полем. Диалог один на
процесс. Есть ли он на этой системе, витрина говорит полем `folderPicker`;
без него кнопки «Выбрать…» нет, а поле остаётся текстовым.

## 5. Контракт

### 5.1 Пакет-команда: рабочее место участника

```jsonc
{ "package": "@office/backend", "count": 2, "workspace": "backend" }
```

`workspace` — имя подпапки корня; пусто или нет поля — общий корень. Имя
проверяется как имя папки: без слэшей, точек в начале и пустоты. Поле
**подсказка для мастера**: `market_hire_team` в живой офис его не читает —
найм в работающий офис не должен заводить папки, которых человек не просил.

`@office/dev-team` получает `backend` и `frontend`.

### 5.2 План мастера (клиент → сервер)

```ts
type SetupWhere =
  | { mode: 'existing'; dir: string }
  | { mode: 'new'; parent: string; folder: string }
  | { mode: 'none' };

type SetupWorkspace =
  | { kind: 'root' }
  | { kind: 'folder'; name: string }
  | { kind: 'path'; dir: string };

interface SetupMember { package: string; count: number; workspace: SetupWorkspace }

interface OfficeSetupPlan {
  name: string;
  description: string;
  where: SetupWhere;
  team: SetupMember[];
  /** Команда, с которой начали: её настройки офиса применяются после найма. */
  teamPackage: string | null;
}
```

Команды: `{ c: 'setup_catalog' }` — витрина для шага «Кто» и подсказки для
шага «Где»; `{ c: 'setup_office'; plan }` — строить.

События: `{ t: 'setup.catalog'; packages; recentParents; defaultRoot }`,
`{ t: 'setup.progress'; steps: SetupStep[] }` — просившему, целиком при каждом
изменении. Итог — снапшот нового офиса (тот же путь, что у `switch_office`)
или `office.error` с op `create`.

```ts
interface SetupStep {
  id: string;                 // 'dirs' | 'office' | 'hire:@office/backend' | 'directions'
  label: string;
  status: 'pending' | 'running' | 'done' | 'failed';
  detail: string;             // что именно сделано или не вышло
}
```

### 5.3 Реестр офисов

`OfficeEntry.noProject?: boolean`, `OfficeView.noProject: boolean`. Ключ
офиса по-прежнему `projectDir`: два офиса без проекта получают разные slug.

## 6. Стартовая команда

Офис из мастера открывается **только с менеджером**; кого нанимать, сказал
план. запись реестра несёт `initTeam: 'manager-only'` (снимается после первого
открытия вместе с `initGit`), и `openOfficeState` сводит набор к менеджеру до
`seed`. `default-office.json` остаётся для офиса,
который заводится переменной окружения на старте сервера, и для старой формы
из комнаты: их поведение не меняется.

## 8. На потом

- **Сменить корень офиса** («проект появился»): перенос `OFFICE.md`, журнала
  и артефактов. Пока — репозиторий роли.
- **Начать с брейншторма** кнопкой на экране прогресса: описание уже в
  направлении, менеджер его увидит на планёрке; отдельная кнопка — когда
  брейншторм стабилизируется.
- **Определение стека** существующей папки (`package.json`, `pyproject`,
  вложенные репозитории) и подсказка состава. Мастер уже устроен так, что
  подсказка — это предзаполнение шага «Кто».
- **Сохранить офис как команду** из окна «Команда» — экспорт в `kind: team`
  с `workspace` по `repoDir` ролей.

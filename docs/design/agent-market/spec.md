# Спека: маркет агентов

**Состояние: фазы 0 и 1 сделаны** (§11) — манифест `agent.json`, бриф
файлами, загрузчик и валидатор пакетов, роль как ссылка на пакет с разницей,
базовые роли — пакетами в `packages/@office/`; кеш пакетов на машине,
установка из git по коммиту, реестр `registry/registry.json`, витрина в окне
«Маркет агентов», добавление по ссылке, проверка и применение обновлений. Как
это устроено — `packages/README.md`. Дальше — фаза 2: экспорт роли в пакет,
шаблон и CLI.

Сценарий, ради которого всё затевается: человек заводит новый офис, открывает
маркет, листает готовых агентов — с рабочими промптами, скилами, подключёнными
инструментами, на проверенной модели — и нанимает тех, кто нравится. Агентов
на маркете пишем и мы, и любой пользователь. Агент обновляется: у него
выходят новые версии. То есть **агент — это пакет**, и маркет — это реестр
пакетов с витриной.

Родственные документы:
- `employees/README.md` — что уже есть: пакет сотрудника как плагин Claude Code;
- `src/server/roles.ts`, `src/server/skills.ts`, `src/server/mcp.ts` — как роль,
  пакет и подключения собираются в сессию сегодня.

## 1. Что есть сейчас и чего не хватает

Сегодня агент размазан по трём местам, и ни одно из них не переносимо:

| Что | Где | Переносимо? |
|---|---|---|
| Модель, инструменты, режим доступа, лимиты, изоляция, MCP по id | `Role` в `state.json` офиса, база — `roles.ts` | нет: роль живёт в офисе |
| Бриф (системный промпт роли) | словари `i18n/roles-*.ts`, у правленных — `Role.brief` | нет: зашит в код офиса |
| Скилы, встроенные скилы, ссылки на плагины, просьбы о серверах | `employees/<роль>/` — плагин + `pack.json` | да, наполовину: папка переносима, но без роли она никто |

Чтобы отдать агента другому человеку, сегодня надо отдать папку пакета **и**
пересказать настройки роли словами. Маркет начинается с того, что эти три
места сворачиваются в одну папку с манифестом.

Что при этом уже решено правильно и переделывать не надо:

- **Формат — плагин Claude Code**, своего не заводим. Пакет ставится и в
  обычный Claude Code; у плагинов есть маркетплейсы и установщик.
- **Пакет объявляет умения, офис выдаёт инструменты.** Серверы из пакета —
  просьба, а не подключение (`employees/README.md`, «Чего пакету не хватает»).
- **Секреты только ссылками** `${NAME}` (`McpServerDef.env`).
- **Оверрайды поверх эталона** (`layoutOverrides`): хранится разница, эталон
  обновляется — правки человека остаются.

## 2. Три сущности, которые нельзя путать

```
Пакет ──install──► Роль офиса ──hire──► Сотрудник
(в реестре,       (пакет + правки     (живая сессия,
 версия, автор)    этого офиса)        стол, задачи)
```

- **Пакет** — неизменяемый, версионированный, ничей внутри офиса. Лежит в
  кеше `~/.office/packages/<имя>/<версия>/`. Один пакет может стоять в десяти
  офисах.
- **Роль** — то, что есть сейчас, плюс ссылка на пакет и **разница** с ним:
  человек поменял модель на подешевле или дописал в бриф абзац про свой
  проект. Разница хранится отдельно от пакета — иначе обновление пакета либо
  затирает правки, либо не доезжает.
- **Сотрудник** (`Instance`) — не меняется: нанимается в роль, как и сейчас.

«Нанять с маркета» = поставить пакет в кеш → завести роль из пакета → нанять
сотрудника. Первые два шага — новые, третий уже есть (`spawn`).

Роль **без** пакета остаётся возможной: заведённая из формы, она просто не
имеет ссылки. Это и есть путь автора: собрал роль в офисе — экспортировал в
пакет (§7).

## 3. Пакет: что лежит в папке

```
my-backend/
  .claude-plugin/plugin.json   имя, версия, описание — формат Claude Code, как есть
  agent.json                   манифест офиса (наследник pack.json)
  brief/ru.md, brief/en.md     системный промпт роли по языкам
  skills/<навык>/SKILL.md      навыки — формат Claude Code, как есть
  bench/cases.json             случаи стенда: на чём проверять срабатывание
  CHANGELOG.md                 что изменилось между версиями — читает человек при обновлении
  README.md                    витрина: что умеет, что просит, что стоит
  LICENSE
```

### 3.1 `agent.json`

Это `pack.json`, доросший до роли. Старый `pack.json` читается ещё долго —
поля те же, просто добавились новые.

```jsonc
{
  "schema": 1,                        // версия схемы манифеста, не пакета
  "name": "@office/backend",          // область/имя, как в npm — см. §4.3
  "kind": "agent",                    // задел под "team" — §9

  "title": { "ru": "Бэкенд-разработчик", "en": "Backend developer" },
  "summary": { "ru": "…", "en": "…" },
  "tags": ["code", "backend", "node"],
  "look": "dev_b",                    // внешность из shared/looks.ts; пусто — подберёт офис
  "manager": false,                   // пакет менеджера; в офисе он один
  "maxInstances": 3,
  "docsDir": "",                      // папка артефактов у ролей, работающих не кодом
  "license": "MIT",                   // обязательно: без лицензии в индекс не попасть (§12.3)

  "runtime": {
    "engine": "claude-code",          // единственное сегодня значение; см. §8
    "model": "sonnet",                // алиас, не полный id: id меняются раз в квартал
    "modelPinned": null,              // полный id, если автору важна именно эта модель
    "effort": "high",
    "tools": ["Read", "Edit", "Write", "Bash", "Grep", "Glob"],
    "permissionMode": null,           // null — как в офисе; пакет может только предложить
    "isolate": true,
    "maxTurns": null,
    "mcp": ["figma-bridge"]           // серверы каталога, на которые роль подписана по умолчанию
  },

  // Ровно то, что есть в pack.json сегодня.
  "skills": ["figma-screen"],
  "builtin": ["design"],
  "use": ["~/.claude/plugins/cache/claude-plugins-official/figma/*"],   // фаза 0: пути; фаза 1: ссылки на маркетплейс
  "servers": [ { "id": "figma-bridge", "transport": "stdio", "command": "npx", "args": ["…"] } ],

  // Чего пакет ждёт снаружи — показывается при найме как «разрешения» в магазине приложений.
  "requires": {
    "office": ">=0.6",
    "env": ["FIGMA_TOKEN"],           // имена переменных, не значения
    "network": true
  }
}
```

Что здесь важно:

- **Бриф — файлами, не строкой в JSON.** Он длинный, многострочный, на двух
  языках, и его правят руками. `brief/<lang>.md`, язык берётся из настроек
  офиса, нет своего — английский.
- **Модель — алиасом.** `opus`/`sonnet`/`haiku` разрешает офис в актуальный
  id; `modelPinned` — для тех, кому нужна именно та версия. Пакет,
  прибитый к `claude-sonnet-4-5`, через год не запустится вовсе.
- **`permissionMode` пакет может предложить, но не навязать.** Режим доступа —
  решение владельца машины, как и сейчас (агент → роль → офис).
- **`use` — ссылка на плагин из маркетплейса, а не путь на диске.** Путь
  `~/.claude/plugins/cache/…` работает у автора и ни у кого больше. Ссылка
  вида «плагин такой-то из маркетплейса такого-то» устанавливается у любого,
  а лицензия остаётся вопросом того, кто ставит (см. `employees/README.md`).
- **`requires` — витрина рисков.** Не механизм, а честный список: без какой
  переменной агент не работает, ходит ли в сеть, какие серверы просит. Офис
  показывает это до найма, а не после первого падения.

### 3.2 Что из плагина офис НЕ берёт

Плагин Claude Code может нести не только скилы: `hooks/` (shell-команды на
события сессии), `commands/`, `agents/` (сабагенты), `.mcp.json`. Пакет с
маркета — чужой код на вашей машине, и здесь правило то же, что с серверами:

| Часть плагина | Офис |
|---|---|
| `skills/` | берёт — это текст, который читает модель |
| `.mcp.json` | не читает (уже так: `skipMcpDiscovery`); серверы — только через `servers` и каталог |
| `hooks/` | **не берёт.** Хук — произвольная команда, выполняемая молча. Если однажды понадобится — только с явным согласием при найме, как сервер |
| `agents/` | не берёт в первой версии: сабагент — это ещё один системный промпт с инструментами мимо ролей офиса |
| `commands/` | не берёт: команд у сотрудника нет, у него задачи |

Валидатор (§7) предупреждает, если в пакете лежит то, что офис проигнорирует:
автор должен знать, что его хук не сработает, а не гадать.

## 4. Реестр: где пакеты лежат и как находятся

### 4.1 Источник правды — git

Пакет живёт в git-репозитории (GitHub в первую очередь, но не только). Версия
пакета = тег. Установка — по **коммиту**, а не по тегу: тег можно передвинуть,
коммит — нет, и в лок офиса (§5) ложится именно хеш.

В одном репозитории может лежать много пакетов (`agents/<имя>/`), поэтому
тег — с именем: `backend@1.2.0`. Одиночный пакет в корне репозитория
тегируется `v1.2.0`.

Это даёт бесплатно: историю, issue-трекер, форки, PR в чужого агента,
удаление/бан через удаление репозитория, и отсутствие нашего сервера как
единой точки отказа на старте.

### 4.2 Индекс — отдельный репозиторий, потом сервис

Маркет нужен не для хранения, а для **поиска и доверия**. Начинаем с самого
дешёвого, что решает обе задачи:

**Фаза 1 — индекс в репозитории** (`ai-office/registry`): один `registry.json`
со списком пакетов и ссылками на их репозитории. Попасть в него — PR, который
прогоняет валидатор в CI. Клиент офиса скачивает индекс, показывает витрину,
ставит пакеты прямо из их репозиториев. Так работают Homebrew taps,
маркетплейсы плагинов Claude Code, Go modules до proxy.

```jsonc
{
  "schema": 1,
  "packages": [
    {
      "name": "@office/backend",
      "repo": "https://github.com/ai-office/agents",
      "path": "agents/backend",
      "versions": [ { "version": "1.2.0", "commit": "a1b2c3…", "at": "2026-09-01" } ],
      "trust": "official"             // official | verified | community — §6
    }
  ]
}
```

**Фаза 3 — сервис индекса** (API): полнотекстовый поиск, категории, счётчики
установок, результаты стенда, зеркало архивов пакетов на случай удалённого
репозитория, страница пакета с README. Клиент ходит в API, а при его
недоступности — в git, как раньше. Формат записи тот же, что в файле:
сервис — это индекс с поиском, а не другой реестр.

Добавить пакет **по ссылке на репозиторий** можно всегда, минуя индекс: для
своих, приватных и ещё не опубликованных агентов. Такой пакет помечается как
«не из реестра» — доверия у него столько, сколько у ссылки.

### 4.3 Имена

`@область/имя`, как в npm. Область — издатель: `@office/*` наши,
`@<github-owner>/*` у пакетов с GitHub. Владение областью в фазе 1
подтверждается тем, что репозиторий лежит под этим владельцем; в сервисе —
входом через GitHub. Имя без области не бывает: коллизии «backend» против
«backend» решать нечем.

## 5. Установка, лок, обновление

### 5.1 Кеш

```
~/.office/packages/
  @office/backend/1.2.0/      неизменяемая копия дерева пакета
  @office/backend/1.3.0/
  @alice/lawyer/0.4.1/
```

Кеш общий на машину, версии не перезаписываются. Это готовая замена
`EMPLOYEES_DIR`: сессия получает `plugins: [{ type: 'local', path: <кеш> }]`
ровно как сейчас.

### 5.2 Лок в состоянии офиса

К `Role` добавляется:

```ts
package?: {
  name: string;
  version: string;
  commit: string;               // что реально стоит
  source: 'registry' | 'git';   // откуда взяли
  repo: string;
  overrides: Partial<Omit<RoleEditable, 'brief'>>;  // разница с пакетом по коротким полям
  briefExtra: string;           // приписка к брифу пакета снизу; сам бриф не правится (§12.1)
}
```

Роль **вычисляется**: умолчания пакета + `overrides`. Хранить результат, как
сейчас, нельзя — тогда при обновлении неотличимо, что человек менял сам, а что
приехало из старой версии. Это то же правило, что у `layoutOverrides`.

### 5.3 Обновление — руками, с чейнджлогом

Офис периодически спрашивает индекс и показывает «у трёх агентов есть новые
версии». Обновление — действие человека, по одной роли или всем разом, с
показом `CHANGELOG.md` между версиями. Автообновления нет: новый бриф
меняет поведение сотрудника, который прямо сейчас ведёт задачу.

Мажорная версия по semver — «поведение изменилось заметно»: офис показывает
её иначе. При обновлении оверрайды остаются; если пакет поменял поле, которое
человек переопределял, офис говорит об этом (как конфликт при слиянии, но
решается кликом).

Живые сессии обновление не трогают: новая версия достаётся следующей задаче.

## 6. Доверие

Пакет — это инструкции, которые модель исполнит с инструментами на вашей
машине. Всё, что описано в `employees/README.md` про чужие наборы, здесь
становится правилом реестра.

Три уровня, показываются на карточке:

| Уровень | Что значит |
|---|---|
| `official` | наш, `@office/*`, проходит наш стенд |
| `verified` | издатель подтверждён (GitHub-аккаунт, позже — организация), пакет прошёл валидатор и ручной просмотр при первой публикации |
| `community` | прошёл только валидатор |

Механизмы, независимые от уровня:

- **Пиннинг по коммиту.** Что проверялось, то и ставится; подмена тега не
  проходит.
- **Разрешения при найме.** Перед «нанять» — экран: какие инструменты, какие
  серверы просит (с командой, которая запустится), какие переменные окружения
  ждёт, ходит ли в сеть. Как в магазине приложений. Серверы, как и сейчас,
  подключает человек в каталоге, а не пакет.
- **Валидатор в CI индекса**: схема манифеста, фронтматтер скилов, отсутствие
  токенов в значениях (та же `checkMcpServers`), отсутствие игнорируемых
  частей плагина без пометки в README, размер.
- **Просмотр перед наймом.** Кнопка «показать бриф и скилы» — весь текст,
  который поедет в модель, читается до установки, а не после.
- **Отзыв пакета.** Запись в индексе с пометкой `yanked` и причиной: офисы, где
  он стоит, видят предупреждение; новые установки этой версии запрещены.

Чего валидатор не умеет и обещать нельзя: отличить хороший промпт от
вредоносного. Инъекция в скил — текст, и ловится только глазами. Поэтому
`verified` включает просмотр человеком, а `community` честно говорит «мы это не
читали».

## 7. Авторский путь

Три способа сделать пакет, от простого к дешёвому:

1. **Экспорт из офиса.** Человек собрал роль в форме, дописал бриф, положил
   скилы в `employees/<роль>/` — жмёт «экспортировать в пакет», получает папку
   по §3 с заполненным манифестом. Дальше — git и PR в индекс. Это
   «конструктор», и он уже почти есть: форма роли и есть конструктор.
2. **Шаблон.** Репозиторий-шаблон с пустым пакетом, `README`, стендом и CI с
   валидатором. `npx create-office-agent`.
3. **Руками**, по спеке. Для тех, кто уже пишет плагины Claude Code.

Инструменты, общие для всех трёх:

```
office-agent validate [dir]    схема, скилы, секреты, игнорируемые части
office-agent bench [dir]       стенд срабатывания скилов — то, что сейчас npm run bench
office-agent pack [dir]        архив для сервиса индекса (фаза 3)
office-agent publish           PR в индекс / загрузка в сервис
```

Стенд (`bench/cases.json`) едет **внутри пакета**: автор описывает, на каких
запросах его агент должен открыть какой скил и на каких — не должен. Индекс
может гонять стенд при публикации и показывать результат на карточке — это
единственная объективная метрика качества, которая у нас есть, и она уже
написана (`scripts/bench`).

## 8. Как пакет становится сессией

Ничего нового: те же опции `query(...)`, что сейчас собираются из `Role` и
`employeePack`, собираются из вычисленной роли (§5.2):

| Поле пакета | Куда |
|---|---|
| `brief/<lang>.md` + бриф проекта из `OFFICE.md` | `systemPrompt.append` |
| `runtime.model` через алиас | `model` |
| `runtime.tools` (+ `Skill`, если есть скилы — как `sessionTools`) | `allowedTools` |
| `skills`, `builtin`, `use` | `skills`, `plugins` |
| `servers` → каталог офиса → подписка роли | `mcpServers` |
| `permissionMode` пакета → роль → офис | `canUseTool` |

`runtime.engine` — задел, а не абстракция на вырост: сегодня единственное
значение `claude-code`, и формат скилов — его. Если однажды появится другой
раннер (в `CONCEPT.md` это заложено как `AgentRunner`), пакет для него будет
объявлять другой engine, и офис будет показывать «этот агент под движок,
которого у вас нет». Делать общий формат агента для всех движков сейчас —
значит не сделать ни одного.

## 9. Что оставляем на потом, но имя даём сейчас

- **`kind: "team"`** — пакет-команда: набор агентов и настройки офиса под
  задачу («стартап на Next.js», «контент-отдел»). Именно это по-настоящему
  закрывает сценарий «новый офис → нанял команду». Делается поверх агентов,
  когда их станет больше десятка.
- **Зависимости между пакетами** — не заводим. `use` ссылается на плагины
  Claude Code, и этого хватает; граф зависимостей агентов — это отдельный
  продукт с отдельными бедами.
- **Платные пакеты** — потребуют сервиса индекса с авторизацией и раздачей
  архивов по праву. В манифесте под это только `license`; никакого `pricing`
  до фазы 3.
- **Телеметрия «сколько стоит задача у этого агента»** — офис уже считает
  расход по роли; отправлять его в индекс можно только по согласию, и это
  отдельное решение.

## 10. Перенос: базовые роли становятся пакетами

Самый важный шаг, и он не про маркет, а про честность: если маркет —
единственный источник агентов, то и наши роли должны приезжать оттуда же.
Иначе будет два пути (`roles.ts` + i18n для своих, пакеты для чужих), и второй
всегда будет хуже первого.

1. `employees/<роль>/` → `packages/@office/<роль>/` с `agent.json` и
   `brief/{ru,en}.md`, вынесенными из `roles.ts` и словарей.
2. Офис при первом запуске ставит `@office/pm` и предлагает остальных с
   маркета — или ставит прежний набор целиком, чтобы поведение старых офисов
   не изменилось (это решает флаг миграции в состоянии).
3. `roles.ts` остаётся схемой `Role` и умолчаниями, а не набором ролей.
4. Старые сохранения: роль без `package` работает как сейчас; при желании —
   «привязать к пакету» с вычислением оверрайдов как разницы.

PM — тоже пакет, но обязательный и с `isManager`: командные инструменты
(`create_task` и прочие) выдаёт офис по этому флагу, а не пакет.

## 11. Порядок работ

| Фаза | Что | Сеть |
|---|---|---|
| 0 ✅ | `agent.json`, бриф файлами, загрузчик пакета вместо пары роль+пак, валидатор, базовые роли — пакетами (§10), ссылка роли на пакет с оверрайдами и припиской, отвязка | нет |
| 1 ✅ | Кеш пакетов, установка из git по коммиту, лок и оверрайды в роли, экран разрешений при найме, витрина по `registry.json` из нашего репозитория, «добавить по ссылке», проверка обновлений | git + один JSON |
| 2 | Экспорт роли в пакет, шаблон, CLI `validate/bench/publish`, CI индекса | PR в GitHub |
| 3 | Сервис индекса: поиск, страницы, счётчики, стенд на публикации, зеркало, вход через GitHub, `verified` | свой API |
| 4 | `kind: team`, платные пакеты, телеметрия по согласию | — |

Фаза 0 не даёт пользователю ничего видимого и именно поэтому обязана идти
первой: она превращает наши собственные роли в те же пакеты, что будут на
маркете, и всё дальнейшее проверяется на них.

## 12. Решённые вопросы

Четыре развилки, которые всплыли при написании, и выбор по каждой.

### 12.1 Бриф в офисе: не оверрайд, а приписка

Бриф пакета — неприкосновенен. Офис держит своё поле `briefExtra`, которое
приклеивается **снизу** к брифу пакета. Обновление пакета с новым брифом
никогда не конфликтует с правками человека: они лежат в разных полях.

Почему не оверрайд всего поля: практически все правки брифа в офисе — это
«дописать про свой проект» (стек, репозиторий, соглашения), а не переписать
роль. Оверрайд поля целиком при первом же обновлении пакета ставит человека
перед выбором «взять новый бриф и потерять свои три абзаца или остаться на
старом» — и он останется на старом, то есть обновления перестанут работать.

Кому нужно именно переписать бриф — тот делает форк: «отвязать от пакета»
превращает роль в обычную, без ссылки, и дальше её можно экспортировать как
свой пакет (§7). Это честнее, чем оверрайд, который выглядит как связь с
пакетом, но ею уже не является.

Для остальных полей (`model`, `tools`, `permissionMode`, `maxTurns`) оверрайд
по полю остаётся: они короткие, и конфликт по ним решается одним кликом.

### 12.2 Индекс отдаёт и `marketplace.json`

Да. Пакет — валидный плагин Claude Code, и стоимость этого решения — один
генератор из `registry.json` в CI индекса. Что даёт:

- автору — вторую аудиторию бесплатно: его скилы ставятся в голый Claude Code
  командой `claude plugin marketplace add ai-office/registry`;
- нам — проверку формата чужим установщиком: если плагин не встаёт в Claude
  Code, он сломан, и это ловится до нас;
- пользователю — понятную историю: «агенты офиса — это плагины Claude Code с
  ролью сверху», а не третий формат.

Граница: в `marketplace.json` едут только скилы. Роль (модель, инструменты,
бриф) — наша надстройка, и голый Claude Code её не видит. Это ожидаемо и
пишется в README индекса одним абзацем.

### 12.3 Зеркало: да, начиная с фазы 3, но git остаётся источником

Пока индекс — файл в репозитории (фазы 1–2), зеркала нет: клиент ставит из
git автора по коммиту, и коммит гарантирует неизменяемость.

С появлением сервиса (фаза 3) он зеркалит архив каждой опубликованной версии.
Причины:

- **удалённый репозиторий** ломает офисы, где пакет стоит, при первой же
  переустановке или новой машине. Авторы удаляют репозитории регулярно;
- **отзыв версии** (§6) должен работать даже когда автор недоступен;
- скорость и лимиты GitHub API при массовой установке.

Ответственность за чужой контент — не аргумент против: мы и так раздаём
ссылку и валидируем содержимое, а `yanked` с причиной есть именно для
случая, когда содержимое надо снять. Лицензия обязательна в манифесте
(`LICENSE` в корне, поле в `agent.json`), и пакет без лицензии в индекс не
попадает — это условие, при котором зеркалить можно.

Правило разрешения: клиент сначала идёт в зеркало, при его отсутствии — в git
автора; хеш дерева сверяется с индексом в обоих случаях, так что источник не
влияет на то, что поставится.

### 12.4 Издатель = владелец на GitHub, и так до фазы 3

Достаточно. Область `@alice` принадлежит тому, чей репозиторий лежит под
`github.com/alice/…`, и CI индекса проверяет это на каждом PR: добавить
`@alice/lawyer` из чужого репозитория нельзя. Регистрировать области отдельно
— значит завести аккаунты, вход и восстановление до того, как появился первый
чужой пакет.

Два следствия, которые надо зафиксировать сейчас, чтобы не переделывать:

- **область живёт в имени пакета навсегда.** Переименование владельца на
  GitHub — новый пакет; старый помечается `moved` со ссылкой, как это делают
  реестры Go и crates;
- **`@office` зарезервирована**, как и `@anthropic`, `@claude` и прочие
  имена, которые ввели бы в заблуждение на карточке.

В фазе 3 вход через GitHub OAuth привязывает ту же самую область к аккаунту
— без миграции имён.

# Спека: настраиваемая планировка офиса

Комната перестаёт быть картинкой с захардкоженным списком мебели и становится
**данными**: пол, стены, предметы и зоны описываются в JSON, а места (рабочие,
кухонные, за столом переговорки) считаются из самой мебели. Цель — собирать
разные конфигурации офиса: другой размер, другое число комнат, другой состав
мебели, — не трогая код отрисовки и не подгоняя координаты руками.

Повод — новый концепт визуала (пиксель-арт вид сверху, прислан в чате
2026-08-21): три комнаты за внутренними стенами — переговорка слева сверху,
кухня с зоной отдыха слева снизу, опенспейс с сеткой столов 3×3 справа; у комнат
разный пол, в стенах проёмы, окна и настенные экраны врезаны в стену. Текущая
архитектура такую сцену не выражает в принципе (см. §1).

Родственные документы:
- `docs/design/office-layout-draft.md` — черновик T-10 (состав зон и предметов;
  координаты оттуда брать нельзя, они из несуществующей сетки 30×18 по 32px);
- `docs/design/office-menu/spec.md` — образец формата спеки.

---

## 1. Почему сейчас нельзя собрать другую конфигурацию

| Что | Где | В чём упирается |
|---|---|---|
| Пол — одна запечённая картинка 1152×720 | `design/sprites/gen.py:135`, `out/*/floor.png` | Размер комнаты жёстко 24×15 (`GRID`, `src/shared/types.ts:367`); другой размер = перерисовать арт |
| Стена — одна полоса поверху | `design/sprites/gen.py:160` (`wall`, 24×2 тайла) | Внутренних стен и проёмов не бывает |
| Обстановка — массив в компоненте | `DECOR`, `src/web/Office.tsx:23` | Координаты дробные и подогнаны глазом: «ряд сдвинут вправо на 0.2 тайла, чтобы не залезать под стол №7» |
| Столы описаны дважды | `src/web/desks.ts:10` и `src/server/state.ts:20` | Любая правка — в двух местах, рассинхрон молчаливый |
| Места живут отдельно от мебели | `TABLE` (`desks.ts:32`) ↔ `dining_table` в `DECOR`; `TABLE_CENTER` (`meetingSeats.ts:8`) ↔ `round_table` | Двинули стол — человечки сели мимо; связь держится только на комментариях |
| Порядок слоёв — ручные числа | `zIndex: 2/3/4/6` в `Office.tsx` | Новая расстановка требует подгонки z |
| Ходьба — прямая линия | `transition: left .9s, top .9s` (`styles.css:345`) | С внутренними стенами агенты пойдут сквозь них |

Ни один из пунктов не чинится точечно: они все следствия одного решения —
**планировка хранится в коде и в пикселях, а не в данных**.

## 2. Система координат

Не меняется, она задана артом:

- 1 арт-пиксель = `SCALE` = 3 экранных;
- тайл = `T` = 16 арт-пикселей = **48 экранных**;
- позиции — в тайлах, дробные значения разрешены (нынешний `DECOR` весь дробный);
- якорь предмета — **левый верхний угол спрайта**, как сейчас
  (`left: px(x), top: px(y)`). Это сохраняет прямой перенос существующих
  координат в данные без пересчёта;
- размер комнаты — свойство раскладки (`size`), а не константа `GRID`.

`GRID.cell` остаётся (48px — свойство арта), `GRID.cols/cells` уходят в раскладку.
Подгонка масштаба (`Office.tsx:105`, шаг строго `k/3`) не меняется, только берёт
размер из раскладки.

## 3. Четыре слоя данных

```
каталог спрайтов (свойство арта)        design/sprites/out/catalog.json  ← генерирует gen.py
        ↓ размеры, след, слоты
раскладка (свойство офиса)              design/layouts/<id>.json         ← пресет
        ↓ комнаты, стены, предметы, зоны   + оверрайд в файле состояния офиса
производные (считает общий модуль)      src/shared/layout.ts
        ↓ desks() idleSeats() meetingSeats() hotspots() passability()
рендер (тупой)                          src/web/Office.tsx
```

### 3.1 Каталог спрайтов

Файл `design/sprites/out/catalog.json`, **генерируется вместе с PNG**: `save()` уже
знает точный размер картинки, поэтому размеры в каталоге не могут разъехаться с
пикселями. Слоты и след объявляются рядом с рисующей функцией — в том же
`gen.py` / `gen_kitchen.py`, одной таблицей.

```jsonc
{
  "version": 1,
  "tile": 16,            // арт-пикселей в тайле
  "scale": 3,
  "sprites": {
    "desk": {
      "size": [2, 1.375],              // тайлы, посчитано из PNG
      "footprint": [0, 0.4, 2, 1.0],   // x,y,w,h от якоря — что занято на полу
      "layer": "furniture",
      "slots": [
        { "kind": "work",  "x": 0.55, "y": -0.75 },
        { "kind": "plate", "x": 0.45, "y":  0.86 }
      ]
    },
    "dining_table": {
      "size": [6, 1.375], "footprint": [0, 0, 6, 1.375], "layer": "furniture",
      "slots": [
        { "kind": "seat", "side": "n", "count": 4 },
        { "kind": "seat", "side": "s", "count": 4 }
      ]
    },
    "round_table": {
      "size": [1.875, 1.375], "layer": "furniture",
      "slots": [{ "kind": "seat", "ring": 8, "rx": 2.6, "ry": 1.5, "grow": true }]
    },
    "wall_5": { "size": [1, 1.5], "footprint": [0, 0.5, 1, 1], "layer": "wall" }
  }
}
```

Числа `0.55 / -0.75 / 0.45 / 0.86` у `desk` — ровно те, что сейчас вшиты в
`Office.tsx:196` и `Office.tsx:180`; они переезжают из кода в описание предмета.

Виды слотов:

| kind | Что это | Кто пользуется |
|---|---|---|
| `work` | Где стоит человечек за своим столом | инстанс с задачей |
| `seat` | Сидячее место (кухня, переговорка, диван, аркада) | свободные агенты, участники совещания |
| `plate` | Якорь таблички с кодом задачи | `.plate` в рендере |
| `mount` | Точка крепления к стене | окна, доска, экран лога |

Разворачивание слотов:
- `side: n\|s\|e\|w` + `count` — ряд вдоль стороны предмета, шаг считается от его
  размера (`width / count`), отступ от кромки — `seatGap` (по умолчанию 0.75 тайла,
  ровно как нынешний `NORTH_Y = TABLE.y0 - 0.75`);
- `ring: N` + `rx/ry` — эллипс вокруг центра предмета; `grow: true` означает
  «при участниках сверх N эллипс растёт», это нынешнее поведение
  `meetingSeat()` (`meetingSeats.ts:22`) один в один;
- явный список `{x, y}` — когда место одно и особое.

`layer`: `floor_overlay` (ковры, кухонная плитка), `furniture`, `wall`,
`wall_mounted`, `hotspot`. Слой влияет только на правило сортировки (§5), а не на
жёсткий z.

### 3.2 Раскладка

Файл `design/layouts/<id>.json`. Пресеты в репозитории; офис может иметь свою
копию (§8).

```jsonc
{
  "version": 1,
  "id": "studio",
  "title": "Студия",
  "size": [30, 20],
  "rooms": [
    { "id": "meeting", "title": "Переговорка", "rect": [1, 1, 10, 7],   "floor": "parquet" },
    { "id": "lounge",  "title": "Зона отдыха", "rect": [1, 8, 10, 19],  "floor": "parquet" },
    { "id": "open",    "title": "Опенспейс",   "rect": [11, 1, 29, 19], "floor": "carpet" }
  ],
  "walls": [
    { "a": [0, 0],  "b": [30, 0] },                      // внешняя, север
    { "a": [11, 0], "b": [11, 20], "doors": [[7, 2]] },  // проём: смещение 7, длина 2
    { "a": [0, 8],  "b": [11, 8],  "doors": [[4, 2]] }
  ],
  "props": [
    { "sprite": "dining_table", "at": [17, 12.2] },
    { "sprite": "round_table",  "at": [2.7, 11.1], "id": "meeting_table", "scale": 1.6 },
    { "sprite": "window",       "at": [4, 0], "mount": "wall" },
    { "sprite": "plant_small",  "at": [19, 8.6], "flip": true }
  ],
  "zones": [
    { "kind": "work",     "room": "open",
      "fill": { "sprite": "desk", "origin": [13, 3], "cols": 3, "rows": 3, "step": [5, 4] } },
    { "kind": "meeting",  "prop": "meeting_table" },
    { "kind": "idle",     "room": "lounge" },
    { "kind": "entrance", "at": [0.1, 5.6] }
  ],
  "hotspots": [
    { "panel": "board", "sprite": "board",     "at": [12.6, 0.1], "key": "B" },
    { "panel": "log",   "sprite": "logscreen", "at": [6.2, 0.3],  "key": "L" }
  ]
}
```

Правила:

- **Комната** — прямоугольник и материал пола. Пол рисуется тайлом с повтором
  (§6), поэтому комната любого размера бесплатна. Необязательный `title` —
  название для человека: его показывают чипы фокуса камеры в трёхмерном офисе
  (`src/web/office3d/Camera3D.tsx`). Без него подпись берётся из запасного
  списка по `id`.
- **Стена** — отрезок по сетке (только горизонтальные и вертикальные) плюс
  проёмы `[смещение, длина]` в тайлах вдоль отрезка. Толщина всегда 1 тайл.
- **Предмет** — спрайт, позиция, необязательные `id`, `flip`, `scale`, `size`
  (`scale` уже используется у ковра и стола переговорки, `Office.tsx:33`).
  Без `id` предмет получает автоимя `<sprite>#<n>` по порядку — на него можно
  сослаться из зоны.
  `size: [w, h]` — явный габарит в тайлах: `{ "sprite": "desk", "at": [6, 4],
  "size": [2, 3] }` занимает ровно 2×3 тайла независимо от разрешения арта.
  Габарит главнее `scale` и размера из каталога; коэффициенты растяжения
  считаются по каждой оси отдельно (`propScale()`, `src/shared/layout.ts`) и
  применяются ко всему разом — к картинке, к footprint в сетке проходимости,
  к слотам (`work`, `plate`, `seat`) и к y-сортировке.
- **Зона** — смысл, а не координаты. `work` — где рабочие места, `meeting` —
  какой стол переговорный, `idle` — где ждут свободные, `entrance` — дверь наружу.
  У `work` есть `fill`: «поставить сетку столов cols×rows с шагом step» — это то,
  что на концепте (3×3), и это же даёт офису расти без правки арта.
- **Хотспот** — предмет, открывающий панель; отличается от обычного предмета
  только тем, что кликабелен и показывает бейдж.

### 3.3 Порядок и стабильность индексов

`index` рабочего места = порядковый номер в списке, полученном из зон `work`
(сначала явные предметы `desk`/`desk_pm` в порядке объявления, потом
сгенерированные `fill` — построчно слева направо). Индекс — контракт с сервером
(`Desk.index`, привязка кухонного места `kitchenSeatFor`, восстановление из
состояния `state.ts:318`), поэтому порядок обязан быть детерминированным и не
зависеть от порядка ключей в JSON.

Стол менеджера — тот, у которого спрайт `desk_pm`; если такого нет, менеджер
садится за место с индексом 0 (нынешнее поведение, `state.ts:405`).

### 3.4 Темы

Не меняются: раскладка оперирует **именами** спрайтов, тему подставляет
`spriteOf()` (`src/web/sprites.ts:26`) с откатом на `day`. Ночная версия новых
тайлов пола и стен обязана существовать под теми же именами.

## 4. Производные: общий модуль `src/shared/layout.ts`

`src/web/desks.ts` и `src/web/meetingSeats.ts` схлопываются сюда же — модуль
общий, чтобы убрать дубль столов с сервером.

```ts
export interface Layout { /* формат §3.2 */ }
export interface PlacedProp { id: string; sprite: string; x: number; y: number; flip?: boolean; scale?: number; size?: [number, number] }
export interface Slot { kind: SlotKind; x: number; y: number; propId: string }

/** Разложить раскладку: предметы из fill развёрнуты, слоты посчитаны. */
export function build(layout: Layout, catalog: Catalog): BuiltLayout;

interface BuiltLayout {
  size: { cols: number; rows: number };
  props: PlacedProp[];              // включая сгенерированные fill
  walls: WallTile[];                // тайл + маска соседей → имя спрайта
  floors: FloorRect[];
  desks: Desk[];                    // из слотов work, с index (§3.3)
  idleSeats: Slot[];                // все seat в зонах idle
  meetingSeats(n: number): Pos[];   // из слотов ring стола переговорки
  hotspots: Hotspot[];
  blocked: Uint8Array;              // сетка проходимости, cols*rows
}
```

Что это чинит: `desks.ts` перестаёт знать про `TABLE` и `SOUTH_Y`, а
`meetingSeats.ts` — про `TABLE_CENTER`. Двинули стол в JSON — места переехали
вместе с ним. Магический `SOUTH_Y = GRID.cells - AGENT_H - 0.2` («иначе фигура
упрётся в стену») исчезает: слот принадлежит предмету, а предмет стоит внутри
комнаты, значит и слот внутри.

Сервер (`state.ts`) берёт `desks` отсюда же вместо своего массива.

## 5. Отрисовка

Слои и правило порядка вместо ручных `zIndex`:

| Слой | z | Как считается |
|---|---|---|
| Пол | 0 | фон комнаты |
| Наложения на пол (ковры, плитка) | 1 | |
| Мебель, стены, человечки | 100…∞ | **y-сортировка**: `z = 100 + round((y + h) * 10)` |
| Настенное (окна, доска, экран, часы) | 900 | стена от них не зависит |
| Подписи, реплики, бейджи | 1000 | как сейчас, отдельным слоем |

Y-сортировка снимает главную ручную работу: сейчас человечек за своим столом
рисуется на `z:3`, а стол на `z:4` — именно чтобы фигура ушла за стол
(`Office.tsx:169`, `Office.tsx:206`). При сортировке по нижней кромке это выходит
само: слот `work` стола на 0.75 тайла выше самого стола, значит человечек в нём
сортируется раньше. Тот же механизм работает и в проходе, где сейчас нужен
отдельный `z:6`.

Пол рисуется не картинкой комнаты, а `div` на комнату с
`background-image: url(<tile>); background-repeat: repeat` — тайл 48×48 экранных
пикселей, кратность сохраняется, пиксель-арт не мылится. Стены — `img` на тайл
(периметр + перегородки, десятки элементов). Предметы — как сейчас, `img`.

## 6. Что нужно дорисовать в `gen.py`

### 6.1 Полы

Вместо цельного `floor()` — тайлы 16×16 арт-px по 2–4 варианта на материал,
варианты раскладываются детерминированно от координаты (хеш от `x,y`), чтобы
картинка не «мигала» при перерисовке:

`floor_parquet_0..3`, `floor_carpet_0..3`, `floor_tile_0..3`
(`kitchen_tiles` 8×6 становится материалом `tile`, а не отдельным предметом).

Цельный `floor.png` остаётся до конца этапа 2 ради `classic`-раскладки, потом
удаляется.

### 6.2 Стены

Автотайлинг по 4 соседям: биты `N=1, E=2, S=4, W=8`, имя `wall_<маска>` —
16 спрайтов, из них реально различимых 11 (прямая, угол, T, крест, тупик,
одиночный). Спрайт тайла: 16×24 арт-px (`size: [1, 1.5]`) — верхняя грань плюс
лицевая стенка с плинтусом, как на концепте; на карте занимает нижний тайл
(`footprint: [0, 0.5, 1, 1]`), рисуется со сдвигом вверх на 0.5 тайла.

Дополнительно: `wall_window` (окно, врезанное в стену — на концепте они именно
врезаны, а не висят), `wall_door_l` / `wall_door_r` (наличники проёма).

Нынешний `wall()` 24×2 тайла остаётся для `classic` до этапа 2.

### 6.3 Каталог

`save()` дополняется записью размера в общий словарь; таблица слотов и следов
объявляется рядом с `build()`; в конце — дамп `out/catalog.json` (один на обе
темы, размеры совпадают).

## 7. Проходимость и ходьба

### 7.1 Карта

Из тайлкарты получается сетка `blocked`: стены (кроме проёмов дверей) плюс
`footprint` предметов с `blocks`. И больше ничего.

След округляется до целых тайлов, а не занимает тайл по касанию (§4 спеки
единиц: «след — целые тайлы»). Пока пресеты не переехали на целые числа,
округление и есть способ выполнить это правило: захват по касанию отбирал у
комнаты по лишнему ряду клеток на каждый предмет, и рабочее место одного стола
оказывалось внутри следа соседнего.

**Слоты в карте не расчищаются.** Раньше расчищались: клетки `work`, `plate`,
`seat` помечались свободными, «чтобы агент мог встать на своё место». Расчистка
решала не ту задачу и ломала карту двумя способами. Место человека — не
проходимая клетка, а точка, **к которой подходят**: подушка дивана лежит на
самом диване и обязана оставаться занятой, иначе кратчайший путь пойдёт через
диван. А клетка под табличкой с кодом задачи (`plate`) лежит посреди
столешницы — расчистка пробивала в столе сквозную дыру, и путь через стол был
по карте законным.

### 7.2 Путь

**Карта спрашивается по ногам.** Точка человека в раскладке — это якорь его
спрайта (левый верхний угол), а занимает он клетку, в которой стоит: она лежит
на `FOOT_DY` ниже и на `FOOT_DX` правее (`walkerCell` — обратное к
`standingAt`). Путь считается и записывается в якорях, потому что в них же
работает рендер, но каждый вопрос к сетке — «занята ли клетка», «можно ли сюда
шагнуть» — задаётся о клетке ног.

Пока поиск пути считал по клетке якоря, вся ходьба была сдвинута ровно на
строку: маршрут обходил препятствия, которых на пути ног не было, и шёл сквозь
те, что были. Агент проходил по стене, стоящей строкой ниже нарисованного
маршрута, а проверки этого не видели — они мерили ту же не ту клетку.

A* по тайлам: 8 направлений, диагональ 1.41, диагональ сквозь угол запрещена
(нужны свободными оба ортогональных соседа угла). Из одинаково коротких путей
выбирается тот, где меньше поворотов, — иначе на пустом полу выходит лесенка
«вправо-вниз-вправо-вниз» той же длины, что и честная диагональ.

Путь **не спрямляется**. Прежнее «протягивание» (выкинуть узел, если до
следующего видно напрямую) спрямляло поверх карты и умело срезать угол вплотную
к кромке предмета. Ломаная идёт ровно по центрам клеток; выкидываются только
промежуточные точки прямых отрезков — геометрия от этого не меняется.

Концы — точные точки места, а не центры клеток. Если конец лежит внутри своей
клетки, её центр пропускается: заход в центр выглядел бы шагом назад перед
выходом и перед посадкой. Срезать при этом нечего — соседние клетки цепочки
свободны обе.

### 7.3 Входы и выходы мест

Место человека почти всегда лежит на самой мебели: подушка дивана — это диван,
стул у стола — клетка перед столом. Дойти до такого места значит зайти на
занятый тайл, и другого способа нет. Вопрос не «можно ли», а **с какой
стороны**: без ответа агент заходил на подушку с любой стороны, до которой
дотягивалась свободная клетка, — из-за спинки, через подлокотник, наискось
через угол.

Ответ записан у предмета: `approach` у слота `seat` или `work` в пресете —
список сторон в координатах предмета (`n`, `s`, `e`, `w`). Диван, кресло и
двухместный диванчик заходятся спереди (`s`), рабочее место — со всех сторон,
кроме самого стола (`n`, `w`, `e`). Ряд мест вдоль стороны предмета
(`shape: side`, обеденный стол) по умолчанию заходится с любой стороны, кроме
противоположной, — сквозь стол не садятся. Поворот предмета `approach` не
учитывает — ровно как `footprint` (§3.2).

`passability` собирает из этих слотов карту входов: клетка места (считается по
ногам) → маска разрешённых сторон и номер предмета. Правило одно и работает в
обе стороны: **войти в такую клетку и выйти из неё можно только через
объявленную сторону и только прямо.** По диагонали на место не заходят и с
места не сходят — человек садится ровно, а не наискось через угол
подлокотника.

Два послабления, и оба про мебель, а не про стены:

- **шаг внутри одного предмета разрешён всегда.** Три подушки дивана — одно
  место для сидения: если журнальный столик перегородил проход перед двумя из
  них, человек заходит с открытого края и переходит по дивану туда, куда
  собирался, а не встаёт рядом;
- **у клетки, на которой агента застигли, запрет на выход снимается, если по
  правилам выйти некуда.** Иначе диван, задвинутый к стене, оказался бы
  ловушкой.

Занятые клетки открываются только на концах маршрута и только вместе с
соседними местами того же предмета. Стены и прочая мебель не открываются
никогда — ни в середине пути, ни в конце.

Пути нет (цель отрезана, комната изолирована, к месту не подойти с его
стороны) — агент идёт настолько близко, насколько пускает карта, и там
останавливается (`bestEffort`). Запасного хода «идти напрямую» нет: он и
означал «сквозь стены».

### 7.4 Прохождение

Стор считает маршрут и отдаёт рендеру **ломаную целиком** вместе со скоростью
(тайлов в секунду). Проходит её рендер: `useFrame` везёт фигуру от точки к
точке на «скорость × время кадра».

Разделено так потому, что маршрут — это решение (его перебивают события офиса),
а прохождение — картинка (её рисуют кадры). Раньше стор сам шагал по ломаной
цепочкой `setTimeout`, выкладывая по точке за раз. В фоновой вкладке браузер
режет `setTimeout` до одного срабатывания в секунду, а `requestAnimationFrame`
останавливает вовсе — и, вернувшись на вкладку, человек видел не идущих агентов,
а уже стоящих по местам: стор успел доскакать до конца, пока рендер не рисовал
ни кадра.

Где фигура на самом деле, знает только рендер, и он сообщает это стору каждый
кадр (`reportPosition`) — не состоянием, а обычной картой в модуле. Новый
маршрут строится от этого места: путь, перебитый на полпути, обязан начинаться
там, где человек стоит, а не там, откуда вышел.

### 7.5 Проверки

`npm run test:nav` (`scripts/test-nav.ts`) — карта и маршруты по всем
раскладкам. Всё, что он мерит, он мерит по клетке ног:

- след мебели без дыр;
- ломаная не задевает занятых клеток нигде, кроме мест того предмета, с
  которого агент встаёт, и того, на который садится;
- середина маршрута идёт строго по сетке (вдоль оси или под 45°);
- последний шаг на место идёт с объявленной стороны;
- точечное место лежит внутри следа своего предмета. Это ловит перекос от
  дробной расстановки: след округляется до целых тайлов, а точка места — нет,
  и предмет, поставленный на полтайла, разъезжается со своим же местом.

`npm run test:reach` (`scripts/check-reachability.ts`) — таблица «докуда
дошли» по каждой значимой точке каждой раскладки. Отвечает на другой вопрос,
чем `test:nav`: тот проверяет, что путь честен, этот — что путь есть. Виноват
в его провале файл раскладки, и он его называет.

## 8. Где хранится раскладка

Решение: **пресеты в репозитории + оверрайд у офиса**.

- Пресеты — `design/layouts/*.json`, читает **сервер** (fs) при открытии офиса.
- У офиса в реестре (`OfficeEntry`, `src/server/offices.ts:10`) появляется
  `layoutId?: string` (новый офис заводится со `studio_4`; поле без значения —
  `classic`, см. совместимость ниже).
- Как только офис меняет расстановку, в его файл состояния кладётся полная копия
  раскладки (`layout?: Layout`) — офис «отрывается» от пресета. Это честнее
  патчей: обновление пресета не переставит мебель под пользователем.
- Раскладка едет в веб **в снапшоте** (`ClientCommand`/снапшот в
  `src/server/index.ts:181`), а не импортируется вебом отдельно, — тогда источник
  один и оверрайд работает сам собой.
- Каталог наоборот — свойство арта: и веб (`import.meta.glob`), и сервер (fs)
  читают `out/catalog.json` из репозитория.

Совместимость: офис без `layoutId` и без `layout` получает `classic` — комнату
24×15 с текущей расстановкой. Никакой миграции состояния не требуется.

## 10. Открытые вопросы

1. **Комната больше экрана.** `studio` 30×20 при `k=1` — 480×320 экранных
   пикселей, влезает. Но если раскладки станут крупнее, нужен либо скролл
   (камера), либо запрет на размер сверх «влезает при `k=1`». Предлагаю пока
   второе: валидировать размер при загрузке раскладки.
2. **Флип спрайтов.** `flip: true` даёт зеркальную мебель без нового арта, но у
   несимметричных предметов ломает светотень (свет на концепте падает слева).
   Возможно, ограничить флип растениями и стульями.
3. **Настенные предметы и толщина стены.** Окно врезается в стену — значит,
   спрайт окна должен быть нарисован под тайл стены (16×24), а не отдельной
   картинкой 102×72, как сейчас. На этапе 2 `window` перерисовывается; старый
   остаётся для `classic`.
4. **Зона `idle` без мебели.** Если в зоне отдыха нет предметов со слотами
   `seat`, свободным агентам некуда сесть. Поведение: заполнять зону сеткой
   стоячих мест — или считать раскладку невалидной? Предлагаю первое, с
   предупреждением в лог.

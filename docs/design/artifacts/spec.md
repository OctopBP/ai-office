# Спека: артефакты — файлы, которыми обмениваются люди и агенты

**Состояние: черновик для обсуждения.** Ничего из описанного не реализовано.

Сценарий, ради которого всё затевается: человек ставит менеджеру задачу и
прикладывает картинку-референс. Менеджер отдаёт её 3D-художнику, тот делает
модель и передаёт её фронтендеру, а фронтендер встраивает модель в сцену. И
обратный сценарий: попросили юриста написать политику — в ответ пришёл файл, а
не «готово, лежит в `docs/legal/T-12/`».

Родственные документы:
- `README.md`, разделы «Состав команды» и «Критерии готовности» — как задача
  ходит между менеджером и исполнителем сегодня;
- `docs/design/illustrator/spec.md` — роль, у которой результат уже сейчас
  файл, а не код; там же — правило «писать только внутрь рабочей копии»;
- `tools/imagegen/README.md` — периметр записи MCP-сервера, который мы
  повторяем для артефактов.

---

## 1. Что есть сейчас и почему этого не хватает

Между участниками офиса ходит **только текст**. Файлы ходят по одному
каналу — git — и только в одну сторону, «вниз по конвейеру»:

| Кто → кому | Как сегодня | Файлы |
|---|---|---|
| Человек → менеджер | `user_message` со строкой; в очередь сессии уходит строка | никак: у менеджера нет ни файловых инструментов, ни картинок в контексте |
| Менеджер → исполнитель | `create_task.description` — текст ТЗ | никак, кроме «посмотри `docs/…/T-5/`» — и то, если T-5 уже слит |
| Исполнитель → менеджер | `finish_task(summary, files)` — отчёт и **пути** в ветке задачи | пути умирают вместе с рабочей копией: после слияния `worktree` убирается |
| Исполнитель → исполнитель | через `dependsOn`: следующий начинает, когда работа предыдущего в основной ветке | работает, но только для того, что решили закоммитить, и только после ревью и слияния |
| Исполнитель → человек | отчёт менеджера в чате; в карточке задачи — список имён файлов строкой | сам файл человек ищет в папке проекта руками |

Три дыры, которые не закрываются текстом:

1. **Референс некуда положить.** Картинку менеджеру не отдать вовсе: он
   работает без файлов сознательно (README, «Состав команды»), а `MessageQueue`
   умеет пушить только строку — хотя SDK принимает в сообщении пользователя
   блоки `image` и `document`.
2. **Модель не доезжает до фронтендера, пока не пройдёт ревью.** Это правильно
   для кода и бессмысленно для `.glb`: ревьюер модель не смотрит, а бинарник в
   git-истории — сомнительный подарок проекту. Сегодня единственный способ
   передать файл коллеге — закоммитить его.
3. **Результат — не файл, а адрес.** Документные роли пишут в
   `docs/<роль>/<задача>/`, но человек получает от менеджера фразу, а не
   документ. В интерфейсе файл ни открыть, ни скачать.

## 2. Что такое артефакт

**Артефакт — файл, который офис хранит у себя и умеет передавать: человеку,
менеджеру, исполнителю.** У него есть номер, имя, тип, размер, автор и
происхождение. **Вложение** — это артефакт, прикреплённый к чему-то: к
сообщению в чате, ко входу задачи, к её результату.

Разделение сущности и связи важно: один и тот же референс прикрепляется к
сообщению человека, затем ко входу задачи модельера, затем ко входу задачи
фронтендера — а файл при этом один.

```ts
interface ArtifactView {
  id: string;          // 'A-7' — свой счётчик офиса, как у задач
  name: string;        // 'reference.png' — как назвал автор, без пути
  mime: string;        // по расширению; для чтения моделью — см. § 5
  size: number;
  sha256: string;      // дедупликация: один файл, приложенный дважды, лежит один раз
  /** 'user' | id сотрудника | OFFICE_SENDER */
  by: string;
  /** Задача, в которой родился. null — принёс человек в чате. */
  taskId: string | null;
  /** Подпись автора: «референс кресла», «модель без текстур». */
  note: string;
  createdAt: number;
}
```

Артефакт **иммутабелен**: «поправил и переложил» — это новый артефакт с новым
номером. Так номер в отчёте всегда значит один и тот же файл, и менеджер,
сославшись в ТЗ на `A-7`, не получит потом молча другую картинку.

### Что артефактом не является

- **Код.** Изменения в исходниках проекта по-прежнему едут через ветку,
  ревью и слияние. `finish_task.files` остаётся: это «что я поменял в
  репозитории», и оно нужно ревьюеру и диффу.
- **Транскрипт, лог, отчёт.** Это текст, у него свой канал.

Разница в одном вопросе: **это нужно проекту или адресату?** Нужно проекту —
коммитится. Нужно адресату (следующему исполнителю, человеку) — артефакт. Одно
не исключает другого: модельер может и закоммитить `.glb` в `design/models`,
и приложить его к сдаче — тогда фронтендер получит его сразу, а проект — после
ревью.

## 3. Где лежит

Свой каталог офиса, рядом с его состоянием:

```
.office/artifacts/<office>/<sha256[0:2]>/<sha256>     содержимое, по хешу
.office/offices/<office>.json  →  artifacts: ArtifactView[]   реестр
```

Содержимое адресуется хешем, реестр — номером. Два номера с одним хешем — один
файл на диске. Реестр живёт в состоянии офиса вместе с задачами и чатом:
ссылки на артефакты лежат в задачах и репликах, и разъехаться они не должны.

Рассмотренные и отклонённые варианты:

| Вариант | Почему нет |
|---|---|
| Только git: артефакт = путь в ветке | ветка задачи убирается после слияния; менеджер и человек не умеют читать из git; бинарники в истории; ничего нельзя передать до ревью |
| Общая папка в проекте (`shared/`), доступная всем рабочим копиям | конкурентная запись из параллельных задач; мусорит в чужом проекте; в облаке недоступна |
| Base64 в `state.json` | сохранение и так дебаунсится и переписывается целиком; мегабайты картинок его убьют |
| Папка внутри проекта `.office-artifacts/` | проект — чужой, и в его `.gitignore` мы не лезем; к тому же не отличается от `.office/` ничем, кроме риска |

Удаление офиса из списка файлы не трогает — как и его сохранение сегодня.
Сборка мусора (артефакты, на которые больше никто не ссылается) — не в первой
версии: файл, который человек приложил, дороже места, которое он занимает.

## 4. Как артефакт ходит

### 4.1 Человек → менеджер

В чате появляется скрепка, перетаскивание и вставка из буфера. Файл уходит по
HTTP — `POST /api/offices/<office>/artifacts`, ответ: `ArtifactView`, — а уже
потом по сокету идёт `user_message { text, attachments: ['A-7'] }`. Сокет у
нас JSON-строчный, и тащить через него бинарники значило бы ломать `Sink` и
рассылку офисам ради одного случая.

Менеджеру сообщение собирается **блоками**, а не строкой: `MessageQueue.push`
принимает `MessageParam.content` целиком.

| Тип | Как попадает в контекст менеджера |
|---|---|
| Картинка (png/jpg/webp/gif) до 5 МБ | блок `image` — он её видит |
| PDF до 100 страниц и 32 МБ | блок `document` — лимит API на документ |
| Текст (md/txt/csv/json/svg…) до 50 КБ | блок `text` с содержимым |
| Всё остальное (`.glb`, `.blend`, `.psd`, архивы, большие файлы) | строка «Вложение A-7: chair.glb, 2.1 МБ — “модель без текстур”» |

Менеджеру не нужно читать `.glb`, ему нужно знать, что он есть и кому его
отдать. Инструмент `view_artifact(id)` возвращает картинку или текст ещё раз —
на случай, если она уехала из контекста после сжатия.

Тот же путь — у прямого разговора с агентом (`talk`): у него тоже есть чат.

### 4.2 Менеджер → исполнитель

`create_task` получает `attachments: string[]`. Разрешены два вида ссылок:

- `A-7` — конкретный артефакт;
- `T-5` — **все результаты задачи T-5**. Это ради сценария «модельер сдал,
  фронтендер берёт»: менеджеру не надо переписывать номера из отчёта, а если
  модельер приложил три файла — уедут все три.

Ссылка на задачу разворачивается в момент запуска исполнителя, а не создания
задачи: с `dependsOn` менеджер заводит обе задачи разом, и результатов T-5 в
этот момент ещё нет.

Исполнитель получает вложения **файлами в своей рабочей копии**:

```
<рабочая директория задачи>/.office-in/A-7-reference.png
```

Почему копия, а не смонтированный каталог хранилища:

- относительный путь в промпте — то, с чем модель работает без ошибок;
  абсолютный путь в `.office/artifacts/ab/ab12…` — то, что она перепечатает с
  опечаткой;
- `imagegen` и разбор рисков считают периметром рабочую копию — вложения
  внутри неё не требуют исключений;
- у документных ролей рабочая директория — папка задачи, и `.office-in/`
  ложится в неё же; по имени файла видно, что это вход, а не результат.

В git это не попадает: `.office-in/` добавляется в `.git/info/exclude`
репозитория задачи один раз при первом использовании. `info/exclude` общий на
все рабочие копии и не трогает `.gitignore` проекта. `commitAll` делает
`git add -A`, и исключённое он пропускает; конвейер ревью — тоже.

Промпт задачи получает абзац:

> Вложения к задаче — в `.office-in/`:
> `A-7-reference.png` — от пользователя: «референс кресла»;
> `A-12-chair.glb` — результат T-5 (3D-художник): «модель без текстур».

Картинку исполнитель смотрит `Read` — он умеет png. PDF — тоже. Бинарник он
не «видит» и не должен: он его встраивает.

### 4.3 Исполнитель → результат

Новый инструмент в `office`-сервере исполнителя:

```
attach_result({ path: 'out/chair.glb', note: 'модель без текстур' }) → 'A-12'
```

Офис копирует файл из рабочей копии в хранилище и регистрирует артефакт с
`taskId` и автором. Путь обязан лежать внутри рабочей директории задачи —
та же проверка, что у `imagegen`; всё, что ведёт наружу, отклоняется с
объяснением. Записи через инструменты Claude Code здесь нет, копирует сам
офис, поэтому разбор рисков относит вызов к безопасным.

`finish_task` не меняется по форме: результаты — это всё, что приложили за
время задачи. Но у **документных ролей** офис прикладывает сам всё, что лежит
в папке задачи на момент `finish_task` (кроме `.office-in/`): их результат —
и есть файлы в этой папке, и просить юриста не забыть `attach_result` — снова
просьба в промпте, которую он нарушит.

При перезапуске задачи результаты прошлой попытки у задачи остаются, но
помечаются как прошлые: ссылка `T-5` разворачивается только в результаты
последней попытки. Файлы не удаляются — обещали, что сделанное не пропадёт.

### 4.4 Результат → менеджер и человек

Отчёт менеджеру дополняется строкой:

> Результаты: A-12 chair.glb (2.1 МБ) — «модель без текстур»; A-13 chair.png (340 КБ) — «рендер»

По ней менеджер решает, кому передать, и ссылается на `T-5` или на номер в
следующем `create_task`. Картинки-результаты он может посмотреть
`view_artifact`.

Человеку файл показывается **карточкой** везде, где виден результат задачи:

- в чате — реплика менеджера о сдаче задачи приходит с `attachments`, и под
  ней карточки: превью для картинок, имя и размер для остальных, скачать;
- в карточке задачи — секции «Вложения» (вход) и «Результаты»;
- в тосте «задача сдана» — кнопка ведёт в карточку, где файл уже есть.

Скачивание — `GET /api/offices/<office>/artifacts/A-12` с `Content-Disposition`
по имени. HTTP-сервер и так отдаёт `dist/` и `/api/offices`; маршрут ложится
рядом. Сервер локальный и односессионный, дополнительной авторизации нет —
как у всего остального.

### 4.5 Облачный режим

В облаке исполнитель работает в контейнере, и локального хранилища у него нет.
Что доезжает:

- **вход**: картинки, PDF и текст — блоками в стартовом сообщении, как
  менеджеру; бинарники — не доезжают, и менеджер узнаёт об этом при
  `assign_task`, как узнаёт сегодня о ненастроенном облаке;
- **результат**: `finish.files` — пути в ветке. После `fetchBranch` офис
  достаёт их из git (`git show <ветка>:<путь>`) и регистрирует как артефакты.
  Это единственный канал из контейнера наружу, и он уже есть.

Полноценная доставка бинарников в контейнер (через Files API или коммит во
входную ветку) — открытый вопрос, см. § 7.

## 5. Границы и размеры

| Что | Предел | Почему |
|---|---|---|
| Один артефакт | 100 МБ | `.blend` со сценой — десятки мегабайт; больше — уже не «приложить», а «положить в проект» |
| Картинка в контекст модели | 5 МБ и 8000 px по стороне | лимит API на блок `image`; больше — только файлом |
| Текст в контекст | 50 КБ | дальше это документ для `Read`, а не реплика |
| Вложений на задачу | 20 | больше — это папка, и её место в репозитории |

Картинку больше лимита офис в первой версии **не уменьшает**: `sharp` живёт
в `tools/props` и в корень не тянется, а без него уменьшать нечем. Такая
картинка прикладывается файлом, менеджер видит её как «вложение без
превью» и отдаёт исполнителю, который посмотрит её `Read`.

Тип определяется по расширению, не по содержимому: цель — выбрать блок для
модели и иконку для карточки, а не защититься от подмены. Сервер локальный.

## 6. Что нужно сделать

Порядок — по ценности: после первого шага уже работает «файл на выходе»,
после второго — «референс на входе», третий закрывает «исполнитель →
исполнитель».

**Шаг 1. Хранилище и результаты.**
- `src/server/artifacts.ts`: положить, достать, реестр, дедупликация,
  проверка периметра; `Persisted.artifacts`, `artifactSeq`.
- Инструмент `attach_result` у исполнителя; автоприложение папки задачи у
  документных ролей; результаты в отчёте менеджеру.
- HTTP `GET …/artifacts/:id`; события `artifact` и поле `attachments` у
  `ChatEntry` и `TaskView` (вход и результаты раздельно).
- Веб: карточка вложения, секция в `TaskDrawer`, карточки в чате.
- `npm run test:artifacts` без токенов: периметр, дедупликация, исключение
  из git, автоприложение, перезапуск задачи.

**Шаг 2. Вход от человека.**
- HTTP `POST …/artifacts`; скрепка, перетаскивание и вставка в `ChatThread`
  (чат менеджера и разговор с агентом).
- `MessageQueue.push` с блоками; сборка блоков по типу (§ 4.1); `view_artifact`
  у менеджера.
- Промпт менеджера: как ссылаться на вложения в ТЗ.

**Шаг 3. Вход в задачу.**
- `create_task.attachments` с номерами и ссылками на задачи; разворачивание
  при запуске; `.office-in/` и `info/exclude`; абзац в промпте задачи.
- `get_board` показывает результаты задач номерами — чтобы менеджер мог
  сослаться.
- Облако: блоки во входном сообщении, результаты из ветки после `fetch`.
- Сценарий в `test:pm`: «референс доезжает до исполнителя» — менеджер приложил
  вложение к задаче той роли, которой оно нужно, и не пересказал картинку
  словами.

Отдельно — тексты на двух языках (`prompts-*`, `ui`), README-раздел
«Артефакты» и строка в подсказке для `OFFICE.md`: «результат — файлом, не
адресом».

## 7. Открытые вопросы

1. **Облако и бинарники.** Достаточно ли на старте «картинки и текст доезжают,
   остальное нет», или облачный режим важен настолько, что нужно сразу
   загружать файлы в контейнер? Второе тянет за собой либо Files API
   Managed Agents (надо проверить, что он есть), либо коммит вложений во
   входную ветку — а это бинарники в истории, от которых мы уходим.
2. **Автопередача по `dependsOn`.** Стоит ли разворачивать результаты
   зависимостей во вход задачи автоматически, без `attachments: ['T-5']`?
   Меньше действий менеджеру, но фронтендер получит и рендеры, и промежуточные
   файлы, которые ему не нужны. Предлагаю явно: менеджер решает, что везти.
3. **Результаты кодовых ролей.** У документных ролей папка прикладывается сама.
   Нужно ли что-то похожее бэкенду и фронтенду — например, скриншот из
   проверки — или им хватит явного `attach_result`?
4. **Уменьшение картинок.** Если референсы с телефона (8–12 МБ) — норма, лимит в
   5 МБ будет мешать с первого дня, и `sharp` в корне оправдан.

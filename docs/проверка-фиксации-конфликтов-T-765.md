# T-765: фиксация доработки конфликта

## Доказано

В исходном review.ts функция settle игнорировала результат commitAll. После возврата failed узел fixConflict всё равно выдавал done. Следующий syncBase видел незавершённое слияние; при исчерпании перехода syncBase.exhausted вызывал abortMerge. Это подтверждённый дефект передачи результата фиксации, а не доказанная причина конкретной остановки T-737.

Временные репозитории воспроизводят два независимых отказа после содержательного разрешения конфликта: существующий index.lock запрещает stage, pre-commit с exit 1 запрещает commit после успешного stage. Регрессии конвейера подтверждают: новый код сохраняет файлы и MERGE_HEAD, оставляет прогон на узле доработки, не записывает done, не начинает ревью и не меняет main. После снятия искусственного отказа повтор того же временного конвейера успешно вливает разрешённое содержимое.

Также проверены: исходный unmerged-индекс без самостоятельного git add автора; фиксация merge-коммита при разрешении, полностью совпадающем с HEAD; отказ при оставшихся метках, включая уже подготовленные автором файлы; обычные пробелы не блокируют коммит.

## Патч

git.ts: зафиксироватьДоработку возвращает результат с диагностикой stage/commit и проверяет подготовленные конфликтные метки, незавершённые записи индекса, MERGE_HEAD и чистоту после фиксации. При пустом diff незавершённое слияние всё равно фиксируется. commitAll сохраняет прежний строковый контракт и использует эту же реализацию.

review.ts: settle проверяет результат и при failed останавливает прогон исключением, которое штатно обрабатывают runs.ts и runPipeline. Узел остаётся текущим; перехода к sync и его abortMerge не происходит. Служебный индекс обрабатывает сервер офиса, доступ автора к нему не требуется.

mergeBaseInto изучена: при оставшемся U-индексе повторный merge возвращает конфликт; если U-записей уже нет, отказ merge попадает в ветку failed с abort. Изменять её для устранения подтверждённой потери результата не потребовалось: отказ фиксации теперь останавливается раньше.

## Граница вывода и возобновление T-737

Отказ git add в песочнице автора T-737 остаётся сообщённым свидетельством. Доступ к служебному индексу серверного процесса T-737, его фактический результат commitAll и состояние той копии этой задачей не проверялись. Искусственный index.lock воспроизводит класс отказа stage, но не доказывает именно отказ прав в T-737.

После слияния T-765 и подтверждённого применения этого кода работающим офисом менеджер может штатно вызвать retry_review T-737. До запуска команда должна подтвердить сохранность готовых изменений T-737: сетевой профиль только одобренных доменов и allowWrite обоих режимов; разрешённое содержимое scripts/test-providers.ts и src/server/providers/codex-tools.ts без конфликтных меток. Сервер офиса должен штатно иметь возможность выполнить stage/commit служебного индекса. Если серверная фиксация откажет, новый конвейер явно остановится с причиной и сохранит доработку.

T-737, main, workflow, права, бюджет, сеть и модели не изменялись. Живой офис не перезапускался, retry_review не вызывался. Патч T-765 не заменяет готовые изменения T-737.

# Чек-лист выкатки

Полный разбор и обоснование — в [`merge-plan.md`](./merge-plan.md). Здесь —
последовательность действий сверху вниз для человека, который будет
проводить выкатку.

## 0. Быстрая проверка перед стартом (обязательно, займёт 2 минуты)

Прежде чем сливать что-либо, повторите проверку из этого разбора — список
веток задач мог измениться со дня анализа (2026-08-20):

```
git fetch --all --prune
git branch -a | grep 'task/'
git log main --oneline --merges | head -20
```

- [ ] 0.1. Если среди веток **нет** ничего кроме `task/T-12`, `task/T-13`
      (пустые, совпадают с `main`) и `task/T-7` (уже предок `main`) — сливать
      нечего, все шаги ниже не нужны. Смотрите раздел «Ветка T-7» в
      `merge-plan.md` и просто закройте задачу выкатки.
- [ ] 0.2. Если появились новые ветки задач с реальной работой — пересчитайте
      таблицу пересечений файлов из `merge-plan.md` под них вручную (карта
      «горячих» файлов: `src/web/store.ts`, `src/web/Office.tsx`,
      `src/shared/types.ts`, `src/server/agents.ts`, `src/server/index.ts`,
      `src/web/styles.css`) и только потом продолжайте по методике ниже.

## 1. Если найдены новые ветки с реальной работой — общая методика слияния

Повторяйте для каждой ветки по одной, не сливайте пачкой:

1. [ ] Обновите `main` локально: `git checkout main && git pull`.
2. [ ] Определите порядок по принципу из `merge-plan.md`: сначала ветки без
       пересечений по файлам, затем серверный контракт
       (`src/shared/types.ts`, `src/server/agents.ts`, `src/server/state.ts`),
       затем клиентские ветки в порядке зависимости друг от друга.
3. [ ] Перед слиянием очередной ветки — `git diff main...task/X --stat`,
       свериться с картой «горячих» файлов: если ветка трогает
       `store.ts` / `Office.tsx` / `types.ts` / `agents.ts` / `index.ts` /
       `styles.css` — заранее откройте эти файлы в обеих версиях
       (`git show main:путь` и `git show task/X:путь`), чтобы понимать, что
       разрешать руками.
4. [ ] `git merge --no-ff task/X` (сохраняем историю merge-коммитом, как было
       сделано для T-1…T-11).
5. [ ] Если конфликт — **не берите одну сторону целиком** для «горячих»
       файлов: в `store.ts`/`Office.tsx` разные задачи почти всегда добавляют
       *разные* срезы состояния/разметки, оставляйте оба блока рядом (см.
       примеры конфликтов в `merge-plan.md`, раздел «Пересечения по файлам»).
       В `types.ts` проверьте, что объединение типа команд (`Command`)
       синтаксически цельное и что каждый новый вариант команды обработан и
       на сервере (`agents.ts`/`index.ts`), и на клиенте (`store.ts`).
6. [ ] После разрешения конфликтов — `npm run typecheck`. Если падает — не
       коммитьте merge, чините конфликт до зелёного typecheck.
7. [ ] `npm run test:pm` — обязательно, если конфликт/слияние задели
       `src/server/agents.ts` или промпты/бриф ролей.
8. [ ] `npm run test:state` — обязательно, если конфликт/слияние задели
       `src/server/state.ts` или `src/shared/types.ts`.
9. [ ] Завершите merge-коммит с сообщением `Merge branch 'task/X'` (без флага
       `--no-verify`, без обхода хуков).
10. [ ] Переходите к следующей ветке по списку из шага 2.

## 2. Разовая уборка, не связанная с ветками задач

Не зависит от того, есть ли сейчас незалитые ветки — можно сделать отдельным
некодовым коммитом в любой момент:

- [ ] Перенести документацию T-6 из `docs/design/T-6/office-menu/` в
      `docs/design/office-menu/`:
      ```
      git mv docs/design/T-6/office-menu docs/design/office-menu
      rmdir docs/design/T-6 2>/dev/null || true
      ```
      Проверить, что в `src/` и других `docs/` нет ссылок на старый путь
      (`grep -rn "docs/design/T-6" --include='*.ts' --include='*.tsx' --include='*.md' .`)
      перед коммитом.
- [ ] После переноса — `npm run typecheck` (перенос документации не должен
      его затрагивать, но это дешёвая проверка, что ничего не задели мимоходом).

## 3. Финальная сверка после всех слияний

- [ ] `npm run typecheck` — чисто.
- [ ] `npm run test:pm` — зелёный.
- [ ] `npm run test:state` — зелёный.
- [ ] `grep -rn "MEETING_SEATS" src/` — пусто (константа должна остаться
      удалённой, см. риск по контракту T-4/T-8 в `merge-plan.md`).
- [ ] `grep -n "'hire'" src/shared/types.ts` — вариант команды на месте.
- [ ] Ручной прогон `npm run dev` — открыть офис в браузере, проверить, что
      совещание, наём/увольнение, кухня и экран меню одновременно работают
      (эти фичи как раз происходят из веток с пересекающимися файлами —
      T-1/T-8/T-9/T-5).
- [ ] Только после этого — сообщить PM, что выкатка готова к пушу в
      `origin/main` (сам пуш и слияние в `main` — вне мандата этого чек-листа,
      делает тот, кто отвечает за релиз).

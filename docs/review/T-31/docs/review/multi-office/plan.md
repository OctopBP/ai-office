# Разбор: что мешает держать несколько офисов сразу

Читал `src/server/offices.ts`, `src/server/index.ts`, `src/server/state.ts`,
`src/server/store.ts`, `src/server/agents.ts`, `src/shared/types.ts` на
`task/T-31` (коммит `5f90ef7`). Код не менял.

Короткий вывод: реестр офисов (`offices.ts`) уже умеет хранить много записей,
но **рантайм держит только один открытый офис одновременно** — это не баг
одного места, а сквозное свойство четырёх модулей: `state.ts` (один
`OfficeState`-синглтон), `store.ts` (один файл состояния и один дебаунс-таймер
на процесс), `agents.ts` (все сессии — PM, воркеры, talk, совещание — в
модульных `let`/`Map`, без ключа офиса) и `index.ts` (переключение = снести
текущий офис и поднять другой). Задача «несколько офисов сразу» — это не
доработка, а по сути параллельный рантайм на каждый офис поверх уже
существующего реестра.

## 1. Карта жизненного цикла офиса

### Реестр (`src/server/offices.ts`)
- `loadRegistry(defaultProjectDir)` (`offices.ts:60`) — читает `.office/offices.json`
  (или заводит первый офис `o-1` из `OFFICE_STATE_FILE`/`OFFICE_PROJECT_DIR`).
  Вызывается один раз на процесс, из `index.ts:85`.
- `currentOffice()` (`offices.ts:91`) — просто читает `registry.currentId`. Сам
  по себе не «открывает» офис, только сообщает, какой из записей реестра
  считается активным.
- `createOffice(input)` (`offices.ts:123`) — заводит запись `OfficeEntry`
  (id, `projectDir`, свой `stateFile: .office/offices/o-N.json`), не трогает
  рантайм-состояние.
- `setCurrent(id)` (`offices.ts:100`) — меняет `registry.currentId` и
  `lastOpenedAt`, пишет `offices.json`. Тоже не трогает `OfficeState`.
- `ensureOffice()` (`offices.ts:175`) — найти-или-создать по `projectDir`,
  используется только на старте процесса (`index.ts:89`).

Вывод: реестр — чистые данные, к «активности» офиса в смысле рантайма
отношения не имеет. Всю тяжесть открытия/закрытия несёт `index.ts`.

### Открытие и переключение (`src/server/index.ts`)
- `openOffice(entry)` (`index.ts:57-83`) — единственная функция, которая
  «поднимает» офис в рантайме:
  1. заводит `projectDir` на диске, кладёт `README.md`, если директория своя;
  2. `setStateFile(entry.stateFile)` (`store.ts:13`) — **глобально** переключает
     файл, в который пишет `store.ts` (module-level переменная `FILE`,
     `store.ts:10`), и синхронно `flush()`-ит хвост записи прежнего офиса;
  3. `office.officeId = entry.id; office.projectDir = entry.projectDir;`
     — прямая мутация полей глобального синглтона `office` (`state.ts:821`);
  4. `office.unload()` (`state.ts:714`) — стирает из памяти *весь* прежний
     офис: инстансы, задачи, чат, лог, ожидания разрешений, `always/never`,
     настройки (но не файл на диске — тот уже переключён на `entry.stateFile`);
  5. `office.restore()` (`state.ts:195`) — читает JSON нового офиса и
     заполняет тот же `office`; если файла нет — `office.seed()` (`state.ts:288`);
  6. `setupGit` / `reportRoleRepos` / `clearInitFlag` — побочные проверки git
     под новый `projectDir`.
- `switchOffice(officeId, ws)` (`index.ts:179-205`) — команда с фронта:
  1. если целевой офис уже текущий — просто `setCurrent` + снапшот тому, кто
     спросил (`index.ts:185-189`);
  2. если есть задачи `in_progress` — отказ с фиксированным текстом, **выход
     без побочных эффектов** (`index.ts:191-196`);
  3. иначе: `setCurrent(target.id)` → `resetSessions()` (`agents.ts:1438`) →
     `flush()` (сброс дебаунс-записи старого офиса) → `await openOffice(target)`
     → лог в чат нового офиса → `broadcastSnapshot()` всем клиентам, которые
     смотрят новый `office.officeId` (остальные молча не получают обновления,
     см. `broadcast`, `index.ts:148-153`).

Итого: «переключение офиса» в этой архитектуре буквально означает «убить
текущий процесс-состояние и поднять новый поверх того же единственного
`OfficeState`». Другого способа держать два офиса одновременно открытыми
сейчас нет вообще — не «не предусмотрено», а физически невозможно без правок.

## 2. Что завязано на «единственный активный офис»

Список конкретных мест (не общие слова — с указанием, что именно ломается
при попытке открыть два офиса параллельно):

1. **`office` — единственный синглтон-состояние** (`state.ts:821`,
   `export const office = new OfficeState()`). Все поля (`instances`,
   `tasks`, `chat`, `log`, `officeId`, `projectDir`, `usage`, `settings`,
   `paused`, `pending`-разрешения, `alwaysAllowed/Denied`) — на весь процесс
   один набор. Любой второй офис требует либо второго `OfficeState`, либо
   переработки в `Map<officeId, OfficeState>`.

2. **`store.ts` — один файл записи и один дебаунс-таймер на процесс**
   (`store.ts:10,62-63`: `let FILE`, `let timer`, `let pendingWrite`).
   `setStateFile()` (`store.ts:13`) переключает `FILE` глобально и не ждёт,
   пока допишется предыдущий: если бы два офиса писали «одновременно»,
   `pendingWrite` от одного затёр бы `pendingWrite` от другого — гонка,
   которую сегодня прячет тот факт, что офис ровно один.

3. **`offices.ts:41` — `let registry`** тоже модульный синглтон, но это не
   препятствие: сам реестр общий для всех офисов по определению (это список
   всех офисов), проблема не в нём.

4. **`agents.ts` — все сессии агентов без ключа офиса**:
   - `let pmQueue`, `let pmLoop` (`agents.ts:579-580`) — сессия PM одна на
     процесс. `startPm()` (`agents.ts:582`) резолвит `resumeId` из
     `office.instances.get('pm#1')` — то есть из *текущего* синглтона `office`,
     а не из офиса, которому реально принадлежит сессия.
   - `let running = 0` (`agents.ts:87`) — счётчик занятых воркеров на весь
     процесс; `MAX_CONCURRENT_WORKERS = 3` (`agents.ts:14`) — тоже глобальный
     лимит, не per-office.
   - `const talks = new Map<string, {...}>()` (`agents.ts:855`) — сессии
     прямых обращений к сотруднику, ключ — `instanceId`, без офиса; при двух
     открытых офисах `instanceId` вида `backend#1` может совпасть между ними
     (нет глобальной уникальности id инстанса) и один разговор перетрёт другой.
   - `const consultsByTask = new Map<string, number>()` (`agents.ts:945`) —
     то же самое, ключ `taskId` без офиса; `T-1` в одном офисе и `T-1` в
     другом — это разные задачи, но один счётчик.
   - `let meetingRunning = false` (`agents.ts:669`) — совещание одно на
     процесс.
   - `const stoppedByUser = new Set<string>()` (`agents.ts:89`) — ключ
     `taskId`, тот же риск коллизии id между офисами.
   - Каждый вызов `query()` (PM — `agents.ts:592`, воркер — `agents.ts:1272`)
     читает `office.projectDir`, `office.settings`, `office.gitReady` из
     текущего глобального `office` в момент старта сессии — если офис
     переключат, пока сессия жива, она продолжит с «чужими» на тот момент
     данными (частично это и есть причина запрета переключения при
     `in_progress`, см. п.3).

5. **Карта WebSocket-клиентов** (`index.ts:146`, `const clients = new
   Map<WebSocket, string>()`) на самом деле уже per-client и хранит id
   офиса, который смотрит клиент — это единственное место, которое *не*
   надо переделывать: `broadcast()` (`index.ts:148-153`) уже фильтрует по
   `watching !== office.officeId`. Проблема в другом: `office.officeId`
   здесь — это ID *единственного* открытого офиса, а не «одного из многих
   живых», поэтому фильтр сегодня по сути не нужен (совпадает всегда, кроме
   короткого окна между `setCurrent` и `broadcastSnapshot` в `switchOffice`).

6. **Таймеры/наблюдатели без owner-office**:
   - `office.subscribe()` (`state.ts:157-160`) — один список слушателей на
     единственный синглтон; при multi-office потребуется знать, какой
     слушатель к какому офису относится.
   - `setTimeout` на завершение permission-запроса (`state.ts:524-526`,
     `PERMISSION_TIMEOUT_MS`), на скрытие совещания (`agents.ts:848`), на
     возврат инстанса в `idle` после задачи (`agents.ts:1362-1364`) — все они
     захватывают в замыкании ссылки на `office`/`inst`/`task`, то есть привязаны
     к объектам, а не к глобальному состоянию напрямую; они переживут переход
     на `Map<officeId, OfficeState>` почти без изменений, если сами объекты
     (`Task`, `Instance`) будут жить внутри правильного `OfficeState`.

## 3. Отказ в переключении при `in_progress`

Место: `index.ts:191-196`.

```ts
const running = [...office.tasks.values()].filter((t) => t.status === 'in_progress');
if (running.length) {
  office.addChat('офис',
    `Сначала дождитесь или остановите задачи в работе: ${running.map((t) => t.id).join(', ')}.`);
  return;
}
```

Что произойдёт, если убрать проверку и просто вызвать `resetSessions()` +
`openOffice()` при живых задачах:

- `resetSessions()` (`agents.ts:1438-1449`) дёргает `inst.abort?.abort()` для
  каждого инстанса **текущего** `office.instances` — воркер получит
  `AbortError`, попадёт в `catch` (`agents.ts:1330-1355`). Ветка
  `stoppedByUser.delete(task.id)` не сработает (задачу никто явно не
  останавливал через `stopTask`), значит уйдёт в ветку «упала»
  (`agents.ts:1350-1355`): `status: 'failed'`, `notifyPm(...)`. Но
  `notifyPm()` → `startPm()` вызовет `office.instances.get('pm#1')` уже
  **после** `openOffice()` заменил `office` на данные нового офиса — то есть
  системное сообщение о провале задачи старого офиса могло бы улететь в PM
  нового офиса (в текущем коде это исключено проверкой, поэтому баг сегодня
  не воспроизводим, но именно так он появится, если проверку просто убрать).
- Хуже: `finally` в `startWorker` (`agents.ts:1356-1365`) выполнится
  асинхронно, уже после того как `openOffice()` мог полностью заменить
  `office.instances`/`office.tasks` на данные нового офиса. `inst.currentTaskId
  = null` и `office.setState(inst.id, ...)` будут писать в объект `inst`,
  которого либо уже нет в новой `office.instances` (если `unload()` создал
  новую Map — на самом деле `unload()` чистит ту же Map, а `office` — тот же
  объект, так что `inst` физически тот же, но принадлежит логически другому
  офису), либо, что хуже, id совпадёт с инстансом нового офиса и его
  состояние затрётся чужим статусом «done»/«failed».
- Итог: без правки состояния (см. раздел 4) простое удаление проверки даёт
  не «переключение с фоновой задачей», а порчу данных нового офиса
  сообщениями и статусами от чужой прерванной сессии. Проверку убирать
  нельзя, пока сессии не привязаны к конкретному `OfficeState`.

## 4. Что держит агентские сессии и что утечёт при переключении без сброса

Живые ресурсы одной агентской сессии (PM или воркер):
- сетевое соединение SDK (`query()` держит поток к Anthropic API);
- `AbortController` в `inst.abort` (`state.ts:84`) — единственный способ
  прервать сессию извне (`resetSessions`, `stopTask`, `fire`);
- `MessageQueue` у PM (`pmQueue`, `agents.ts:579`) и у talk-сессий
  (`talks`, `agents.ts:855`) — это открытый generator/итератор, который ждёт
  следующее сообщение; `close()` у него обязателен, иначе `for await`
  никогда не завершится;
- git worktree на диске (`createWorktree`, `agents.ts:1244`) — не сессия
  Node, а файлы; переживает `resetSessions()` без проблем (это и есть
  «наработки не теряются»), убирается отдельно через `mergeTask`/ручную
  очистку.

Почему `resetSessions()` (`agents.ts:1438-1449`) обязателен при
переключении: если оставить сессии жить —
- PM новой сессии не будет запущен (`pmLoop` уже not null было бы для
  старого офиса, а `startPm()` — `if (pmLoop) return;`, `agents.ts:583`), то
  есть новый офис вообще не получит своего PM, пока `pmLoop` держит ссылку на
  сессию старого;
- воркер старого офиса продолжит писать в `office.projectDir`/`workdir`,
  который к этому моменту уже указывает на **новый** проект (после
  `openOffice` меняет `office.projectDir`) — только пути внутри `query()` уже
  зафиксированы в момент старта (`cwd: workdir`), так что физическая запись
  файлов пойдёт туда же, куда шла; но все побочные обращения к `office.*`
  внутри цикла обработки сообщений (`consume`, `notifyPm`, `office.updateTask`)
  бьют уже по данным нового офиса — задача старого офиса «допишется» в чужую
  доску;
  - счётчик `running` (`agents.ts:87`) не обнулится сам — старая сессия
    рано или поздно завершится и корректно уменьшит его, но пока жива,
    занимает слот из общего `MAX_CONCURRENT_WORKERS = 3` (`agents.ts:14`),
    отбирая пропускную способность у нового офиса, хотя пользователь её не
    видит (не его вкладка);
- открытые permission-запросы (`office.pending`, `state.ts:151`) —
  `unload()` их резолвит как `'deny'` (`state.ts:714-719`), это корректно
  само по себе, но именно поэтому *обязано* выполняться синхронно с
  переключением, а не «когда-нибудь позже».

Если сессии не сбрасывать при multi-office (а вместо этого держать несколько
`OfficeState` живыми параллельно) — это меняет саму модель: тогда
`resetSessions()` не нужен вообще для случая «просто открыл другой офис в
UI», он остаётся только для явного `reset`/`hardReset`. Но тогда каждая
структура из раздела 2 (`pmQueue`, `talks`, `consultsByTask`, `running`,
`stoppedByUser`, `meetingRunning`) обязана стать `Map<officeId, ...>` —
иначе воркеры двух офисов будут делить один слот конкурентности и одну
Map разговоров.

## 5. Сохранение состояния на диск — достаточно ли его

Механизм уже per-office и рабочий сам по себе:
- у каждого `OfficeEntry` свой `stateFile` (`offices.ts:16,161`, для первого
  офиса — `STATE_FILE`/`OFFICE_STATE_FILE`, для остальных —
  `.office/offices/o-N.json`);
- `store.ts` пишет атомарно (tmp + rename, `store.ts:70-77`) с дебаунсом
  400 мс (`SAVE_DEBOUNCE_MS`, `store.ts:17`);
- `office.markDirty()` (`state.ts:167-169`) вызывается на каждое
  изменяющее действие (создание задачи, чат, расход и т.д.), так что при
  штатном переключении (`switchOffice` → `flush()` → `openOffice`) данные
  закрываемого офиса гарантированно долетают до диска до того, как
  `setStateFile` перекинет `FILE` на новый путь.

Но этого недостаточно для «работа в неоткрытом офисе не теряется» в смысле
задачи T-31 — и вот почему:
- **Диск хранит только то, что было сделано, пока офис был открыт.**
  Офис, который сейчас не активен, вообще не может ничего делать: у него нет
  ни PM-сессии, ни воркеров — весь rantайм привязан к единственному `office`.
  То есть «работа в неоткрытом офисе» сегодня в принципе не существует, её
  нечему терять. Вопрос стоит наоборот: при multi-office рантайме, если
  сохранение останется в текущем виде (один `FILE`, один дебаунс-таймер на
  процесс, см. раздел 2, п.2), офис B может начать сохраняться, пока не
  дописался офис A — `pendingWrite` (`store.ts:63`) один на модуль, второй
  вызов `save()` при живом `timer` просто заменит `pendingWrite`
  (`store.ts:84-90`: `if (timer) return;`), и первая версия (офиса A) вообще
  не попадёт на диск — это и есть гонка записи JSON, требуемая в критериях.
- Восстановление (`restore()`, `state.ts:195`) сверяет `data.projectDir !==
  this.projectDir` (`state.ts:198`) и просто отбрасывает чужое сохранение —
  разумная защита от смешения данных, но она защищает только от чтения не
  той пары (файл, синглтон), а не от гонки записи, описанной выше.
- Вывод: формат хранения (один файл на офис) менять не нужно — он уже
  правильный. Нужно раздать **запись** по офисам: свой дебаунс-таймер и
  свой `pendingWrite` на каждый `stateFile`, а не на процесс.

| 5 | `index.ts:179-205` `switchOffice()` | `resetSessions()` глобально, единственный отказ по `in_progress` | если офисы становятся параллельными рантаймами — убрать `resetSessions()`/отказ по `in_progress` из этой ветки полностью (задачи текущего офиса просто продолжают жить в своём runtime), оставить только переключение того, **какой** runtime транслируется конкретному `ws` |
| 6 | `index.ts:146-153` `clients`/`broadcast()` | фильтр по `office.officeId` (единственному) | не менять формат (`Map<WebSocket, officeId>` уже правильный), но `broadcast()` должен брать события от **всех** runtime и сверять `event.officeId === watching`, а не полагаться на единственный глобальный `office` |
| 7 | `agents.ts:592,1272` `query({ cwd: office.projectDir, ... })` | читает глобальный `office` в момент старта | если офис становится объектом (п.1), сессии должны захватывать `runtime`/`officeId`, а не читать глобальный `office` — иначе даже с раздельными Map возможна путаница, какая сессия к какому офису относится |

## Разбивка на шаги

Каждый шаг — это отдельная маленькая правка, которую можно сдать и
проверить независимо. Порядок важен: шаг 2 невозможен без шага 1, шаг 3 без
шага 2, и т.д.

### Шаг 1. Разорвать глобальный файл-синглтон в `store.ts`
- **Файлы:** `src/server/store.ts`, вызывающий код в `src/server/state.ts`
  (`markDirty`, `restore`) и `src/server/index.ts` (`setStateFile`, `flush` в
  обработчике SIGINT/SIGTERM).
- **Что менять:** `save()`, `flush()`, `load()`, `wipe()` перестают читать
  модульную `FILE`; вместо неё принимают путь к файлу состояния явным
  аргументом (или объект `{ path }`, который возвращает `openOffice`/реестр).
  Дебаунс-таймер и `pendingWrite` переезжают в `Map<string, {timer,
  pendingWrite}>`, ключ — абсолютный путь `stateFile`.
- **Готово, когда:** `npm run typecheck` проходит; `npm run test:pm`
  проходит (тесты используют `OFFICE_STATE_FILE`, поведение с одним офисом
  не должно измениться); вручную — два параллельных запуска
  `save()`-подобной операции с разными путями не теряют ни одну запись (можно
  добавить точечную проверку в `store.ts`, но тест не обязателен на этом шаге,
  если поведение с одним офисом не регрессирует).

### Шаг 2. Завести `Map<officeId, OfficeState>` вместо одного `office`
- **Файлы:** `src/server/state.ts` (класс `OfficeState`, экспорт `office`),
  все читатели `office` в `src/server/index.ts` и `src/server/agents.ts`
  (их много — это самая объёмная, но механическая правка).
- **Что менять:** экспортировать функцию `officeState(officeId): OfficeState`
  вместо `export const office`; в `index.ts`/`agents.ts` заменить обращения
  к глобальному `office` на обращения через явно переданный/захваченный
  `officeId` (PM-сессия, воркер, talk-сессия, обработчик WS-команды — у
  каждого из них уже есть или легко достаётся `officeId`, потому что запрос
  либо пришёл от конкретного `ws` из `clients`, либо начат из
  `openOffice(entry)` с известным `entry.id`). `openOffice()` перестаёт
  вызывать `unload()` — вместо этого создаёт **новый** `OfficeState` в
  Map, если его там ещё нет, и переиспользует существующий, если офис уже
  открывался в этом процессе.
- **Готово, когда:** `npm run typecheck` проходит без ошибок про
  отсутствующий `office`; `npm run test:pm` проходит; вручную — открыть один
  офис, поработать, переключиться на другой и обратно: данные первого
  офиса на месте (не считаны заново с диска, а сохранились в памяти) — это
  наблюдаемая разница с текущим поведением и главный признак, что шаг
  сделан правильно.

### Шаг 3. Разбить модульные Map/let в `agents.ts` по офисам
- **Файлы:** `src/server/agents.ts` — `pmQueue`, `pmLoop` (579-580),
  `running` (87), `talks` (855), `consultsByTask` (945), `meetingRunning`
  (669), `stoppedByUser` (89).
- **Что менять:** все семь переменных переезжают в структуру, привязанную
  к `officeId` (проще всего — добавить их полями в сам `OfficeState` из
  шага 2, раз он уже стал per-office контейнером: тогда `startPm()`,
  `startWorker()`, `talkTo()` и т.д. читают их через `officeState(id).pmQueue`
  и т.п. вместо модульных переменных). `MAX_CONCURRENT_WORKERS` — вопрос
  продукта: либо остаётся глобальным лимитом на процесс (оставить `let
  running` общим, но тогда он не относится к «местам под правку» этого
  шага), либо становится лимитом на офис — решить явно и написать в коде
  комментарий-обоснование, а не оставлять неявным.
- **Готово, когда:** `npm run typecheck` проходит; `npm run test:pm`
  проходит; вручную — запустить задачу в офисе A, пока она выполняется,
  открыть офис B и запросить в нём `talk` с сотрудником: сообщение уходит
  правильному инстансу правильного офиса, а не путается с офисом A (сегодня
  это физически непроверяемо, потому что офис B не может быть открыт
  параллельно).

### Шаг 4. Убрать отказ по `in_progress` и включить параллельный вывод в UI
- **Файлы:** `src/server/index.ts` (`switchOffice`, 179-205 — убрать блок
  191-196 и вызов `resetSessions()`/`flush()` в этой функции), `broadcast()`
  (148-153, убедиться что фильтрация по `officeId` работает при нескольких
  живых runtime), возможно `src/web/*` (если фронт как-то полагался на текст
  отказа — но это задача не про фронт, только зафиксировать в отчёте, что
  фронту может понадобиться убрать код, реагирующий на этот конкретный
  текст ошибки, если он есть).
- **Что менять:** `switchOffice()` больше не «пересоздаёт» офис, а либо
  находит уже поднятый `OfficeState` в Map (шаг 2), либо поднимает новый
  через `openOffice(target)` без выгрузки текущего. `resetSessions()`
  остаётся только для явной команды `reset`/`hardReset` (`index.ts:272-274`)
  и принимает `officeId`, чтобы не рвать сессии всех офисов разом.
- **Готово, когда:** `npm run typecheck` и `npm run test:pm` проходят;
  вручную — открыть офис A, запустить в нём задачу, переключиться на офис B
  без ошибки «дождитесь задач», вернуться в A и увидеть, что задача
  доработала (или продолжает работать) без потери прогресса.

## Риски

- **Дубли сессий.** Если шаг 3 сделан частично (например, `pmQueue`/`pmLoop`
  разнесли по офисам, а `talks`/`consultsByTask` — нет), то при двух
  открытых офисах возможна ситуация «два PM пишут в один `MessageQueue`»
  или «прямой разговор с `backend#1` одного офиса получает ответ от
  `backend#1` другого» — id инстансов не глобально уникальны (`roleId#n`,
  `state.ts:349`), уникальны только в пределах одного офиса. Любая
  Map-структура в `agents.ts`, которую забыли перевести на составной ключ
  `${officeId}:${instanceId}` (или на вложенность внутрь per-office
  контейнера), — источник этого риска. Проверять шаг 3 нужно именно на двух
  офисах с совпадающими id ролей/инстансов (это типичный случай, роли
  одинаковые в обоих офисах по умолчанию).
- **Утечки подписок.** `office.subscribe()` (`state.ts:157-160`) и
  `broadcast()` в `index.ts` держат список слушателей. Если `openOffice()`
  после шага 2 начнёт создавать новый `OfficeState` при каждом
  `switchOffice()`, а не переиспользовать существующий из Map, — старые
  подписчики (в первую очередь `office.subscribe((event) =>
  broadcast(...))`, добавленная один раз на процесс в `index.ts:155`, а не
  на офис) продолжат числиться в `listeners` умершего `OfficeState`, и
  событие туда будет уходить в никуда — не крах, но тихая утечка памяти при
  частом переключении/пересоздании. Проверять: `office.subscribe()`
  вызывается не более одного раза на реальный runtime за всё время жизни
  процесса.
- **Гонки при записи JSON.** Уже описано в разделе 5: до шага 1
  (`store.ts`) параллельная работа двух офисов **гарантированно** теряет
  сохранения — один `pendingWrite`/`timer` на процесс перезатирает данные
  между `save()` разных офисов. После шага 1 риск переходит в более тонкий:
  если `stateFile` двух `OfficeEntry` случайно совпадёт (например, ручное
  редактирование `.office/offices.json` пользователем) — тогда `Map` по
  пути `stateFile` из шага 1 не спасёт, потому что для стораджа это будет
  один и тот же ключ. Стоит на шаге 1 добавить проверку в `createOffice()`
  (`offices.ts:130-131`, там уже есть похожая проверка на дубль
  `projectDir` — по аналогии проверить и уникальность `stateFile`), либо
  явно зафиксировать инвариант, что `stateFile` генерируется только кодом
  (`offices.ts:161`) и вручную не редактируется.

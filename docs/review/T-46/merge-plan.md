## 3. Итоговый порядок слияния

1. Убедиться, что рабочая копия `main` чистая (см. пункт 0 — закоммитить или
   застэшить незакоммиченные правки).
2. Влить `task/T-43` в `main` (`git merge --no-ff task/T-43`). Конфликтов не
   будет (main + T-43 по отдельности — чисто, см. раздел 2).
   Прогнать: `npm run typecheck`, `npm run test:state` (T-43 — мультиофисный
   рефактор состояния), `npm run test:offices` (скрипт появляется только
   с T-43 — до слияния его не существует, значит запускать после).
   Если всё зелёное — коммит слияния.
3. Закрыть `task/T-44` без слияния — она указывает на тот же коммит, что и
   уже влитая на шаге 2 `task/T-43` (см. 1.4). Пустое слияние Git тоже
   покажет: `git merge task/T-44` после шага 2 не добавит ни одной строки.
4. Влить `task/T-45` в обновлённый `main` (`git merge --no-ff task/T-45`).
   **Здесь будет ручное разрешение конфликтов** — 3 файла из раздела 2:
   `src/server/agents.ts`, `src/server/cloud.ts`, `src/server/state.ts`.
   Разрешать по инструкции из раздела 2 (совмещать обе стороны, не выбирать
   одну версию целиком).
   Прогнать: `npm run typecheck`, `npm run test:perm` (T-45 — режимы
   доступа), `npm run test:state` (задета логика `effectiveMode` и логов),
   `npm run test:offices` (T-45 ложится поверх мультиофисного рантайма из
   шага 2 — стоит перепроверить, что личный режим доступа не сломал
   переключение офисов).
   Если всё зелёное — коммит слияния (сообщение коммита обязано перечислить
   файлы с ручным разрешением, как это уже принято в проекте, например
   `git log --grep=Conflicts` по прежним merge-коммитам).
5. Финальная сверка: `npm run typecheck` на всём `main` ещё раз (после обоих
   слияний, а не только после каждого по отдельности) и `npm run test:pm`
   на всякий случай — T-43/T-45 не должны были задеть промпт менеджера, но
   `PM_PROMPT` — код, который дешевле перепроверить, чем потом откатывать.

Почему именно в этом порядке (T-43 → T-45), а не наоборот: порядок не влияет
на список конфликтных файлов (проверено в обе стороны, раздел 2) — конфликт
одинаковый что при T-43-затем-T-45, что при обратном. Но T-43 — более
инвазивная архитектурная правка (вводит per-office `state` вместо глобального
`office`), а T-45 логически ложится «поверх» неё (использует
`state.settings`, а не глобальный singleton). Проще один раз завести
мультиофисный контекст и потом добавить в него личный режим доступа, чем
наоборот.

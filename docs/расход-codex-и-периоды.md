# Расход Codex и данные для строк 5h / 1w (T-730)

## Причина и исправление

`codexPrice` читал только `OFFICE_CODEX_PRICING`. Без этой настройки `total_cost_usd` оставался 0, хотя токены были известны, и результат имел `cost_unavailable: true`. `consume` переносил признак в `Usage.costUnavailable`, но Rail суммировал только `instances.today.costUsd`. Дополнительно Codex заменял usage последним запросом модели внутри хода, теряя предыдущие запросы этого хода.

Теперь цена выбирается по точному id модели, возвращённому app-server: корректная запись `OFFICE_CODEX_PRICING`, затем `OFFICE_MODEL_PRICING`, затем каталог models.dev, секция `openai`, сохранённая как `codex`. Старый кеш без секции Codex обновляется. Никаких догадок о цене неизвестной модели. Явная цена 0 допустима; неизвестная цена — `costUnavailable`. Запросы внутри хода складываются, повтор уведомления с тем же total не удваивает токены. Список моделей движка использует тот же источник цены.

При подписке ChatGPT доллары — **расчётная стоимость токенов по каталогу**, а не списание или оставшийся денежный баланс подписки. Проценты лимитов в доллары не переводятся. Старые записи без цены задним числом не переоцениваются: историческая цена неизвестна. После перезапуска сохраняются их токены и признак неизвестной цены.

## Контракт расходов

Суммы относятся ко всему выбранному офису, включая менеджера и разных провайдеров:

- WebSocket snapshot: `event.usage.windows`.
- WebSocket usage: `event.windows`.
- Zustand: `useStore(s => s.spendWindows)`; до snapshot значение `null`.
- Обновление в простое: `GET /api/spend?office=<id>&limit=1`, поле ответа `windows`. Параметры таблицы `from/to` не меняют эти два скользящих периода. UI следует периодически обновлять это поле, например раз в минуту: без новых результатов WebSocket usage не приходит. `calculatedAt` позволяет показывать/проверять свежесть.

Тип `РасходЗаПериоды` в `src/shared/types.ts`:

| Поле | Смысл |
|---|---|
| `calculatedAt` | Момент расчёта, мс эпохи |
| `historyFrom` | Нижняя граница сохранённого покрытия истории, мс |
| `fiveHour` | Последние 5 × 60 × 60 секунд |
| `sevenDay` | Последние 7 × 24 часа, а не календарная неделя |

Оба окна имеют одинаковые поля:

| Поле | Смысл |
|---|---|
| `from`, `to` | Включительные границы выборки по `SpendEntryView.at`, мс |
| `costUsd` | Известная часть суммы; `null`, когда известной стоимости нет или нет записей при неполном покрытии |
| `costStatus` | `available`: полная стоимость записей и покрытие; `partial`: известная часть при неизвестных ценах или неполном покрытии; `unavailable`: сумму показать нельзя |
| `historyPartial` | Нет покрытия части интервала либо граница пересекает старую посуточную свёртку |
| `unknownCostEntries` | Число выбранных записей с `costUnavailable` (свёртка считается одной записью) |
| `entries` | Число вошедших записей, включая неизвестные цены |

В UI `costUsd === null` означает «—», `partial` требует пометки приблизительности/неполноты. Значение 0 достоверно только вместе с `available`; нельзя писать `costUsd ?? 0`. Обе строки используют `spendWindows.fiveHour` / `.sevenDay`, а не `instances.today` и не бюджет `globalBudgetUsd`.

## Точность времени и сохранение

История `spend` сохраняется в файле офиса. Метка `at` — момент получения результата хода агента. Поэтому суммы точны по **времени регистрации результатов**; длительный незавершённый ход ещё не входит, а ход, пересёкший границу, целиком относится к моменту результата. Разложить его по реальному времени генерации токенов имеющиеся данные не позволяют.

Детальные записи теперь сохраняются 8 календарных суток: этого достаточно для любых последних 168 часов. Старая посуточная свёртка, полностью вошедшая в окно, суммируется; пересекающая границу исключается и выставляет `historyPartial`, без выдуманной пропорции по часам. После миграции такая погрешность исчезает по мере выхода старых свёрток из окна.

`spendHistoryFrom` сохраняется отдельно и переживает перезапуск; для старого файла без этого поля используется время самой ранней записи, а без записей — время загрузки. Потерянные до начала детализации расходы не восстанавливаются из суточных итогов. При удалении старых записей или превышении предела 5000 граница покрытия сдвигается к первой оставшейся записи. История старше 60 суток удаляется как прежде. Неполное покрытие остаётся явным, даже если известная сумма равна нулю.

## Контракт лимитов

Лимиты принадлежат аккаунту провайдера и могут включать использование вне этого офиса. Они независимы от сумм расходов офиса.

`account/rateLimits/read` и push `account/rateLimits/updated` проходят через один `rateReport`. Полный отчёт передаётся в `rate_limit_info.usageReport`, далее `consume → state.noteRateLimit → limits.noteUsageReport → event { t: 'limits' } → store.limits`. Длительность `windowDurationMins` сохраняется как `LimitWindow.windowMinutes` и попадает в кеш лимитов. Проценты отчёта уже имеют шкалу 0–100: 0.5 означает 0.5%, а не 50%. Обработка долей событий Claude сохранена.

Готовый селектор из `src/shared/types.ts`:

```ts
окноЛимита(limits, selectedProvider, '5h', Date.now())
окноЛимита(limits, selectedProvider, '1w', Date.now())
```

Для Codex выбираются длительности **300 / 10080 минут**; `primary` может оказаться недельным, а `secondary` пятичасовым. Длительность неизвестна — соответствующее окно не выбирается. Для Claude используются `five_hour` / `seven_day`. Селектор фильтрует провайдера и возвращает `null` для неизвестного или уже сброшенного окна; это не 0%. Объект результата содержит `utilization`, `resetsAt`, `updatedAt`, `provider`, `kind`, `windowMinutes`. UI должен передавать подключённого/выбранного провайдера и учитывать режим подключения: лимиты подписки не являются бюджетом API-ключа. Кеш Codex старого формата без длительности нельзя подписывать как 5h/1w до свежего отчёта.

- `npm run typecheck`.

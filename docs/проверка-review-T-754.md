## Воспроизведение

1. Исходная npm-команда в песочнице T-754 немедленно завершилась кодом 1, до первого сценария:

   `Error: listen EPERM: operation not permitted …/T/tsx-501/27886.pipe`

   Стек: `tsx/dist/cli.mjs → createIpcServer → Server.listen`; Node.js v22.23.1. sandbox_status подтверждает закрытые локальные порты. Это конкретный инфраструктурный блокер запуска через CLI tsx, отдельный от исходного гейта, который успел выполнить сценарии.

2. В /tmp/T-754-merged экспортировано дерево HEAD через git archive и применён только сохранённый `git diff --binary main...task/T-748`. Ветки и репозиторий офиса не переключались и не сливались. node_modules — ссылка на уже установленные зависимости. Тест сам создаёт временные git-репозитории и изолирует состояние через scripts/_isolate.ts.

3. На этом объединённом дереве `node --import tsx scripts/test-review.ts` завершился кодом 0: **все 228 проверок прошли**, в том числе сценарии после старого хвоста. Полный лог: /tmp/T-754-merged-before.log. Регрессия объединения в этой среде не воспроизведена. Успех не доказывает отсутствия прежнего инфраструктурного сбоя.

## Изменение

В package.json только для test:review заменено `tsx scripts/test-review.ts` на `node --import tsx scripts/test-review.ts`. Загрузчик TypeScript сохранён, вспомогательный IPC-сервер CLI больше не требуется. Такой запуск уже используется другими тестами проекта; engines требует Node >=22.

Тестовые сценарии и утверждения, workflow, обязательное ревью, инструменты явного вердикта, ограничение продолжения T-748, бюджеты и таймауты не изменены. Это подтверждённый фикс запуска в изолированной среде, **не установленная причина старого пятиминутного сбоя**.

## Дальнейший порядок

После обязательного ревью и слияния T-754 допустим один штатный retry_review T-748 для проверки нового запуска с актуальной main. Это контрольный запуск после исправления изоляции, а не доказательство устранения прежней причины. Для него следует сначала подтвердить, что работающий сервер загрузил диагностику T-750: при повторном отказе нужны gate.failed.диагностика, код/сигнал/таймаут и указанный полный лог; без этого прежняя потеря основания повторится. Изменение package.json гейт читает из проверяемого дерева; серверная диагностика требует загрузки соответствующего кода. Подготовка штатного обновления уже описана в T-753 — новую задачу или вопрос владельцу здесь не создаём.

Вручную ревьюить/сливать T-748 не требуется: её обязательный конвейер остаётся единственным путём. Для T-730 нужны успешный гейт и слияние T-748, доставка и подтверждённая загрузка её серверного патча штатным обновлением, затем штатное возобновление ревью T-730 с явным approve_pr/request_changes. После T-730 можно продолжать зависимую UI T-731.

В этой задаче retry_review, перезапуск живого офиса, сборка выпуска и scripts/test-pm.ts не выполнялись. Исходный первый сбой T-748 остаётся недоказанным: критерий 1 нельзя честно отметить выполненным по доступным данным. Для его закрытия требуется диагностированный повтор в среде гейта; фиктивных изменений серверной логики ради этого не вносилось.

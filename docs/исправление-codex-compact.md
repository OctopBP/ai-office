# Завершение сжатия Codex (T-740)

## Причина и путь ревью

Проверена main `667e00c`: HEAD совпадал с main, готового исправления в
`src/server/providers/codex.ts` не было (последнее изменение — `ae6e078`, T-712).

Продолжение ревью идёт через `reviewPr` в `src/server/agents.ts`
(передача `task.reviewerSessionId` в `runAgentSession`), затем
`resumedPrompt` → `driveWorker` → `startSession` → `codexQuery`.
`resumedPrompt` кладёт в очередь `/compact`, а на первый `result` —
актуальное задание ревью. Процесс ревью менять не требуется.

Адаптер отправляет `thread/resume`, затем `thread/compact/start`.
Раньше на `item/completed` с типом `contextCompaction` он выдавал
`compact_boundary` **и** `result`, разрешая очередной `turn/start`.
Граница контекста ещё не означает завершение хода Compact.
Если `turn/completed` приходит позже, следующий ввод попадает в активный Compact
и отклоняется: `failed to submit turn input: ActiveTurnNotSteerable { turn_kind: Compact }`.
Кроме того, поздний `turn/completed` мог выдать лишний результат.

Это подтверждено воспроизведением на уровне протокола: мок app-server сохраняет
Compact активным 80 мс после границы и отклоняет преждевременный ввод указанной
ошибкой. С новым тестом исходный файл из main падает именно этой ошибкой в
`providers/rpc.ts`; исправленный проходит. Это детерминированная регрессия
адаптера, а не запись платного прогона с настоящим Codex. Загрузка внешней
документации не удалась из-за DNS; версия SDK или его внутренний API не менялись.

## Исправление

`contextCompaction` остаётся уведомлением о границе контекста.
Только `turn/completed` выдаёт результат и освобождает ожидание хода,
для обычного ввода и ручного сжатия одинаково. Ошибка терминального события
передаётся как ошибочный результат. Последующий ввод сохраняется в очереди;
повторной отправки, параллельного хода и автоматических повторов нет.
Поздний ответ `turn/start` не восстанавливает ID уже завершённого хода.

Отмена прерывает активный ход через существующий `turn/interrupt` и закрывает
соединение; выход процесса завершает ожидание ошибкой. Если движок вообще
не прислал терминальное событие, ожидание можно отменить штатной остановкой
сессии. Фикс не вводит опрос и не повторяет неопределённо доставленный ввод.

## Применение

После включения исправления обновить серверный код / сборку приложения и
**перезапустить сервер офиса (или приложение)**: уже работающий процесс держит
старый адаптер. После обновления использовать штатное продолжение существующего
ревью. Если старая сессия ещё ждёт/оборвалась, сначала штатно остановить её,
затем продолжить через существующий механизм офиса. Новое ревью создавать
не нужно. Эта задача не запускает продолжение и не правит T-737/T-735/T-724.

### Условия возобновления остановленных ревью

Для T-737/T-735/T-724/T-730: сначала штатный конвейер должен проверить и
включить фикс в main, затем работающий офис должен получить обновлённый
серверный код / сборку и пройти штатный перезапуск сервера или приложения.
Одного слияния в main недостаточно: старый процесс продолжает использовать
старый адаптер. После подтверждения запуска обновлённого процесса и отсутствия
активной старой сессии ревью — `retry_review` для существующих задач, с
сохранением штатных ограничений и зависимостей. Если старая сессия остаётся
активной, сначала штатно остановить её. До применения фикса повторные ревью
не запускать. В T-741 `retry_review` не вызывался, ветки этих задач не менялись.

# Встроенный терминал: pty на сервере и в сборке приложения (T-292)

Исследование перед фичей «терминал в окне офиса»: xterm.js в вебе, pty на
сервере, оболочка открывается в папке проекта офиса. Кода здесь нет — только
факты, проверки и рекомендация.

## Итог одним абзацем

Брать **`node-pty@1.2.0-beta.15`** (Microsoft, MIT), с точной версией без `^`.
Это N-API модуль, поэтому один и тот же бинарь грузится и системным Node 22 в
разработке, и Node 24 внутри Electron 44 в приложении — пересборка под
Electron не нужна (проверено, §1). Бинарники для darwin-arm64, darwin-x64,
win32-x64 (и linux-x64/arm64) лежат в самом пакете, `npm ci` ничего не
компилирует. В сборке: вынести `node-pty` из бандла сервера и положить
урезанной папкой в `resources/node_modules` рядом с Agent SDK; асар его не
касается, подпись macOS electron-builder поставит сам, но надо проследить за
битом исполнения у `spawn-helper` (§3). Доступ: открыть терминал может только
владелец — в локальном режиме тот, кто подключён с правильным `Origin`, в
открытом режиме — сокет с сессией владельца (§5).

## 1. Каким Node работает сервер и какой нужен ABI

**В приложении.** `desktop/server.js` запускает сервер через
`fork(paths.serverEntry(), …)` с `ELECTRON_RUN_AS_NODE=1`. `fork` берёт
`process.execPath` главного процесса — то есть сам исполняемый файл
приложения, который при этой переменной работает как обычный Node. Отдельного
Node в приложении нет (тот же `process.execPath` уходит в `OFFICE_NODE_BIN`
для MCP-серверов). Сервер — один ESM-файл `resources/server/index.mjs`,
собранный esbuild (`scripts/build-server.mjs`, `target: 'node22'`).

Версии проверены запуском (Electron из `desktop/node_modules`, 44.4.3, как в
`desktop/package-lock.json`):

| Где | Node | `NODE_MODULE_VERSION` (ABI) | N-API |
|---|---|---|---|
| Приложение: Electron 44.4.3 + `ELECTRON_RUN_AS_NODE` | 24.21.0 | **149** | 10 |
| Разработка: `npm run office` / `tsx`, `.nvmrc` = 22 | 22.23.1 | **127** | 10 |
| «Офис на своём сервере» — системный Node ≥ 22 | 22/24 | 127/137 | 10 |

Вывод: модуль на старом V8 API (NAN) пришлось бы собирать дважды — под 127 для
разработки и под 149 через `@electron/rebuild` для приложения, и пересобирать
при каждом обновлении Electron. **Годится только N-API модуль** — он привязан не к
`NODE_MODULE_VERSION`, а к версии N-API, которая только растёт и обратно
совместима, поэтому один бинарь грузится везде.

`node-pty` с версии 1.0 — N-API (`node-addon-api`; в `pty.node` экспортируется
`napi_register_module_v1`). Проверено: готовый `prebuilds/darwin-arm64/pty.node`
из `node-pty@1.2.0-beta.15` без пересборки загрузился и в Node 22.23.1 (ABI 127),
и в Electron 44 как Node 24.21.0 (ABI 149): `require('node-pty').native.fork`
— функция.

Чего проверить не удалось: живой `spawn`. Песочница исполнителя запрещает
открывать псевдотерминал вообще — `python3 -c "import os; os.openpty()"` тоже
падает с `EPERM`, а `node-pty` — с `posix_spawnp failed`. Это ограничение
песочницы, а не модуля; первый живой запуск — на задаче реализации (см. §6,
проверки).

**Выбор: `node-pty@1.2.0-beta.15`, точная версия.**

- Бинарники darwin-arm64 и darwin-x64 лежат в одной папке пакета — обе
  dmg-сборки с одного arm64-раннера получат свой бинарь; win32-x64 — на
  Windows-раннере. Ни на одной из трёх целей ничего не компилируется.
- Есть linux-x64/arm64 — `npm ci` в CI (`ubuntu-latest`) и на «своём сервере»
  тоже без `node-gyp`, Python и компилятора. С 1.1.0 CI начал бы компилировать
  C++ на каждом прогоне.
- В 1.1.0 сломан бит исполнения у `spawn-helper` — терминал на macOS не
  запустился бы вовсе без ручного `chmod`.
- «Beta» здесь — канал, на котором `node-pty` выпускает Microsoft для VS Code;
  стабильный 1.1.0 старше и с известной поломкой выше. Поэтому версия пишется
  точно (`"node-pty": "1.2.0-beta.15"`), а обновление — отдельной задачей с
  проверкой §6.
- Runtime-зависимостей нет: `node-addon-api` — заголовки для сборки, в
  приложение его класть не нужно.

Размер в установщике после обрезки (§3): macOS — ~0,3 МБ (`lib/` 92 КБ +
две папки prebuilds по 70–140 КБ), Windows — ~1,5 МБ (`conpty.node`,
`conpty_console_list.node`, `conpty/conpty.dll`, `conpty/OpenConsole.exe`; без
`.pdb`, которые весят ~10 МБ).

## 3. Что поменять в сборке

Сейчас: `scripts/pack-desktop.mjs` собирает `desktop/resources/`, а
`desktop/builder.config.js` кладёт её в `Contents/Resources` через
`extraResources` (с отдельной строкой для `resources/node_modules` — общий
фильтр выбрасывает `node_modules`). **В `app.asar` едет только оболочка**, так
что `asarUnpack` не нужен: `node-pty` попадёт в обычную папку на диске, как
Agent SDK и `playwright-core`.

Изменения:

1. **`package.json` (корень)** — `"node-pty": "1.2.0-beta.15"` в
   `dependencies`. В `desktop/package.json` — ничего: сервер запускается не из
   оболочки.
2. **`scripts/build-server.mjs`** — `'node-pty'` в `external`. В бандл его не
   собрать: `lib/utils.js` ищет `pty.node` по путям относительно своего файла
   (`build/Release`, `prebuilds/<platform>-<arch>`), и `unixTerminal.js` так же
   находит `spawn-helper`. Ровно та же причина, по которой внешним оставлен
   Agent SDK. Бандл грузит его через `require` из шапки — `createRequire` уже
   есть.
3. **`scripts/pack-desktop.mjs`** — скопировать `node_modules/node-pty` в
   `resources/node_modules/node-pty` **с фильтром** (у `cpSync` есть
   `filter`):
   - оставить `package.json`, `LICENSE`, `lib/**` без `*.test.js` и `*.map`;
   - из `prebuilds/` — только папки цели: на `darwin` — `darwin-arm64` и
     `darwin-x64` (обе, потому что одна машина собирает обе архитектуры), на
     `win32` — `win32-x64` (цель NSIS только x64);
   - выбросить `*.pdb`, `src/`, `deps/`, `third_party/`, `scripts/`,
     `typings/`, `binding.gyp`.
   После копирования — `chmodSync(…/spawn-helper, 0o755)` для обеих
   darwin-архитектур: `cpSync` режим сохраняет, но 1.1.0 показал, что пакет
   может приехать без бита, и тогда это тихая поломка в установщике.
   Удобнее оформить как `packServerNative(root, out)` рядом с `packTools`
   (свой список, не `EXTERNAL_TOOL_DEPS`: тот про MCP-серверы).
4. **`desktop/builder.config.js`** — правок не требуется. `resources/node_modules`
   уже переносится строкой `{ from: 'resources/node_modules', to: 'node_modules' }`.
5. **Проверка ресурсов** (`npm run test:packtools` или соседняя) — на
   собранном `resources/` проверить: есть `node_modules/node-pty/lib/index.js`;
   на macOS — оба `pty.node` и оба `spawn-helper` с битом исполнения; на
   Windows — `conpty.node`, `conpty/conpty.dll`, `conpty/OpenConsole.exe`;
   нет ни одного `.pdb`.

### Подпись и нотаризация на macOS

- electron-builder (`@electron/osx-sign`) обходит весь бандл, включая
  `Contents/Resources`, и подписывает каждый Mach-O: `pty.node` (бандл) и
  `spawn-helper` (исполняемый). С сертификатом — Developer ID,
  `hardenedRuntime: true`, метка времени, права из `entitlementsInherit`;
  без сертификата — ad-hoc (`identity: '-'`). Отдельных шагов не нужно —
  так же уже подписываются бинари `playwright-core` и движка.
- Права в `build/entitlements.mac.plist` уже покрывают случай:
  `disable-library-validation` позволяет Node внутри Electron загрузить
  `pty.node`, `allow-jit`/`allow-unsigned-executable-memory` нужны V8 в
  дочернем `ELECTRON_RUN_AS_NODE`. Для `spawn-helper` ничего сверх не нужно:
  он только `chdir` + `execvp`.
- Нотаризация отвергает неподписанные или подписанные без hardened runtime
  исполняемые файлы. `spawn-helper` из npm подписан ad-hoc линкером
  (`flags=0x20002(adhoc,linker-signed)`), так что переподпись сборщиком
  обязательна — она и происходит, но проверить на первой сборке стоит:
  `codesign -dv --verbose=4 "AI Office.app/Contents/Resources/node_modules/node-pty/prebuilds/darwin-arm64/spawn-helper"`
  должен показать `Authority=Developer ID Application` и `flags=…(runtime)`, а
  `codesign --verify --deep --strict "AI Office.app"` — пройти.
- x64-сборка на arm64-раннере: в x64-приложении остаётся и arm64-папка
  prebuilds — она не мешает (`loadNativeModule` берёт
  `prebuilds/${platform}-${arch}`), но тоже подписывается. Хотим экономить
  140 КБ — фильтровать по архитектуре в хуке `afterPack` electron-builder;
  не стоит того.

### Windows

Подписи `.exe` в сборке сейчас нет, `OpenConsole.exe` ничего в этом не меняет.
ConPTY требует Windows 10 1809+ — ниже Electron 44 и так не работает.
`useConptyDll` по умолчанию `false`: используется системный ConPTY из
`kernel32`, а `conpty.dll`/`OpenConsole.exe` — запасные, их всё равно кладём.

## 4. Запасной вариант без нативного модуля

`child_process.spawn(shell, { stdio: 'pipe' })` без pty работает, но это не
терминал:

- у процесса нет tty: `isatty()` ложно, поэтому нет приглашения (zsh/bash без
  `-i` его не печатают, с `-i` ругаются на отсутствие управления заданиями),
  нет цветов, нет редактирования строки и истории;
- полноэкранные программы не работают вовсе: `vim`, `less`, `top`, `htop`,
  `git log` с пейджером, интерактивный `claude`, запросы пароля
  `ssh`/`sudo`/`git` (они читают пароль с `/dev/tty`);
- нет размера окна и `SIGWINCH` — `resize` выразить нечем;
- Ctrl+C надо эмулировать сигналом процессу, а не байтом `\x03`, и это
  убивает всю оболочку, а не текущую команду;
- вывод буферизуется блоками (stdout в трубу у libc — полная буферизация), и
  прогресс-бары с `\r` приходят рывками.

Промежуточный хак на macOS/Linux — `script -q /dev/null $SHELL` (BSD `script`
сам открывает pty): даёт tty и приглашение, но размер не меняется (нет
`ioctl(TIOCSWINSZ)` снаружи), а на Windows аналога нет совсем.

Вывод: запасной вариант годится как «окно команд» (выполнить `npm test` и
посмотреть вывод), но не как терминал. Держать его как деградацию стоит только
на случай, если `require('node-pty')` упал (повреждённая установка,
необычная платформа): тогда `term.error` с понятной причиной лучше полуживой
оболочки. Рекомендую **не** делать запасной режим в первой фазе — только
понятную ошибку.

## 5. Папка терминала и права доступа

### Где открывается

Папка — `projectDir` офиса, который смотрит сокет в момент открытия:
`officeById(watching(ws))?.projectDir` (`src/server/offices.ts`,
`OfficeEntry.projectDir` — «рабочая директория команды»; у офиса «без проекта»
(`noProject`) это служебный корень офиса, он тоже годится). В приложении
корень проекта по умолчанию задаёт `OFFICE_PROJECT_DIR` из `desktop/server.js`.

- Терминал привязан к офису, в котором открыт: переключение офиса в рейле
  его не закрывает и не переносит. Офис архивирован или удалён — его
  терминалы закрываются (тем же местом, что `setOfficeUnloader`).
- Клиент не передаёт путь. Если потом понадобится «открыть в репозитории
  роли» (поле «Репозиторий роли») — передавать `roleId`, а путь сервер берёт
  сам из роли; произвольный путь с клиента не принимать.
- Перед запуском — `existsSync` и `isDirectory`, иначе `term.error`.

### Окружение и оболочка

- macOS/Linux: `process.env.SHELL || '/bin/zsh'` с `-l` (входная оболочка —
  чтобы подтянулся `.zprofile`, как в обычном Терминале); Windows:
  `process.env.COMSPEC` не брать (это `cmd.exe`), а `powershell.exe`, если есть,
  иначе `COMSPEC`.
- `TERM=xterm-256color`, `COLORTERM=truecolor`; `LANG=en_US.UTF-8`, если `LANG`
  пуст — приложение из Finder стартует без локали, и кириллица в выводе
  превращается в `?`.
- **Убрать из окружения:** `ELECTRON_RUN_AS_NODE` (иначе любой Electron-софт,
  запущенный из терминала, стартует как голый Node), все `OFFICE_*`, ключи
  провайдеров (`ANTHROPIC_API_KEY` и т. п.) и `GH_TOKEN`/`GITHUB_TOKEN`, если
  сервер их держит. `PATH` оставить — сервер уже получает входной `PATH` из
  `loginPath()`.

### Кто имеет право открыть

Терминал — это выполнение кода от имени пользователя сервера. Права те же,
что у агентов, но без единой ступеньки между нажатием и выполнением, поэтому
правило строже, чем у остальных команд.

**Локальный режим** (приложение, `npm run office`, сервер на loopback без
`OFFICE_PUBLIC_URL`): входа нет, любой подключившийся — владелец. Но
сейчас нет и проверки `Origin` (спека «офис на своём сервере», §1): любая
страница, открытая в браузере владельца, может открыть сокет на
`127.0.0.1:<порт>`. Для `user_message` это «агент сделает что-то по
просьбе», для терминала — мгновенное выполнение. Поэтому **`term_open`
принимается только с сокета, чей `Origin` на апгрейде совпадает с `Host`**
(окно приложения грузит `http://127.0.0.1:<порт>` — совпадает) **или с
адресом dev-сервера vite в разработке**. Запомнить признак на сокете при
`connection` (`req.headers.origin`) — это не ждёт фазы входа.

**Открытый режим** (`OFFICE_HOST` не loopback или задан `OFFICE_PUBLIC_URL`):
- открыть терминал может только сокет с сессией владельца — по спеке аккаунт
  один, сессия проверяется на апгрейде, `Origin` там же. Отдельной галочки
  «разрешить терминал» нет: вошёл владелец — может то же, что агенты на этом
  сервере (так же спека решает про `list_dir` без ограничений по корню);
- выход, «выйти везде», смена или сброс пароля закрывают сокеты с кодом
  `4401` — **вместе с сокетом убиваются все его pty** (не отцеплять, не
  оставлять жить без хозяина);
- каждое открытие — строка в лог сервера: офис, папка, id сессии, адрес
  клиента. В журнал офиса не писать: журнал — для агентов и планёрки.
- Когда появится доверенный заголовок шлюза (§9 спеки, несколько людей) —
  терминал только для принципала-владельца, не для гостей.

Терминал не часть состояния офиса: не попадает в снапшот, не пишется на
диск, не рассылается другим клиентам и не видна агентам. Это канал между
одним сокетом и одним процессом.

## 6. Рекомендация целиком

### Пакет и сборка

- `node-pty@1.2.0-beta.15` — точная версия, в `dependencies` корня.
- `build-server.mjs`: `external += 'node-pty'`.
- `pack-desktop.mjs`: копия `node_modules/node-pty` → `resources/node_modules/node-pty`
  с фильтром по платформе цели, без `.pdb`/исходников, `chmod 0755` у
  `spawn-helper`.
- `builder.config.js`: без правок; проверить подпись `spawn-helper` на первой
  подписанной сборке.
- Тест ресурсов: наличие бинарей по цели и бит исполнения.

### Контракт WS-сообщений

В духе существующего протокола: команды клиента — `{ c: … }` в
`ClientCommand`, события сервера — `{ t: … }` в `ServerEvent`
(`src/shared/types.ts`). Все `term.*` события уходят **только сокету-владельцу
терминала** (`send(ws, …)`), не через `broadcast`.

Клиент → сервер:

```ts
// Открыть терминал в папке офиса этого сокета. nonce — чтобы сопоставить ответ.
{ c: 'term_open'; nonce: string; cols: number; rows: number }
// Ввод с клавиатуры как есть (включая \x03 для Ctrl+C). До 64 КБ за сообщение.
{ c: 'term_input'; id: string; data: string }
// Новый размер окна xterm.js (fit-аддон). cols 2..500, rows 1..200.
{ c: 'term_resize'; id: string; cols: number; rows: number }
// Закрыть: SIGHUP оболочке (на Windows — kill), затем term.exit.
{ c: 'term_close'; id: string }
```

Сервер → клиент:

```ts
{ t: 'term.opened'; nonce: string; id: string; cwd: string; shell: string; officeId: string }
{ t: 'term.output'; id: string; data: string }        // UTF-8, склеенный пакет
{ t: 'term.exit'; id: string; code: number | null; signal: number | null }
{ t: 'term.error'; nonce?: string; id?: string; reason: 'forbidden' | 'no_dir' | 'limit' | 'unavailable' | 'unknown_id'; message: string }
```

Правила на стороне сервера:

- `id` выдаёт сервер (`T1`, `T2`… или uuid); чужой `id` — `term.error` с
  `unknown_id`: терминалы одного сокета не видны другому, даже в том же
  офисе.
- Вывод склеивать: копить до 16 мс или 32 КБ и отправлять одним
  `term.output` — иначе `cat` большого файла превращается в тысячи
  сообщений.
- Обратное давление: `ws.bufferedAmount` больше 1 МБ — `pty.pause()`, после
  слива — `pty.resume()`. Иначе `yes` в терминале съест память сервера.
- Лимиты: 4 терминала на сокет, 16 на процесс (`limit`).
- Сокет закрылся — все его pty убиваются. Переподключение с восстановлением
  сеанса (буфер последних строк, `term_attach`) — не первая фаза.
- `require('node-pty')` делать лениво при первом `term_open` и упавший
  импорт превращать в `unavailable`: сервер без терминала должен подниматься
  как раньше.

### Проверки для задачи реализации

- Вне песочницы исполнителя (в ней pty запрещён): `npm run office` →
  открыть терминал, `vim`, `top`, Ctrl+C, resize окна, кириллица.
- Собранное приложение на macOS arm64 и x64 (через Rosetta) и Windows x64 —
  то же самое; `codesign` из §3 на подписанной сборке.
- Юнит: правило доступа (`Origin` в локальном режиме, сессия в открытом),
  чистка окружения, лимиты, убийство pty при закрытии сокета.

## Причина расхождения

Конвейер Q-94 не ждал. Устаревшей осталась только **подпись пулл-реквеста**:

1. `src/server/review.ts`, исполнитель `gate` (узел согласования): подпись
   `wf.gateWaiting` ставится через `state.patchPr(task.id, { note })` перед
   `whenQuestionClosed`. После ответа узел возвращает `no`/`yes`, а подпись
   **не меняет**.
2. Следующий узел — `rework` (`review.ts`, `const rework`) или агентский `step` —
   подпись PR тоже не трогает (все вызовы `patchPr(..., { note })` в review.ts:
   sync, checks, openPr, review, merge, gate, checkRunning; в `rework`/`step` их нет).
   Пока агент дорабатывает, PR показывает «жду Q-94», хотя Q-94 уже закрыт.
3. `list_owner_questions` (`src/server/agents.ts` → `openQuestionsText` в
   `src/server/questions.ts`) берёт `openQuestions` = `questionList().filter(isOpenQuestion)`,
   а `isOpenQuestion` (`src/shared/questions.ts`) отбрасывает отвеченные. Q-94
   отвечен, поэтому «открытых вопросов нет». Оба источника правы, врёт подпись.
4. Ошибку закрепила задача: менеджер переписал id из подписи в текст T-355/T-360,
   и к моменту их запуска диагноз уже относился к прошлому состоянию.

Гипотезы «влит в удалённый», «другой офис», «потеря при перезапуске», «фильтр по
типу» данные не подтверждают: Q-94 не `mergedInto`, относится к o-2,
`kind: "gate"`, перезапусков в окне не было.

## Как воспроизвести

1. Задача с процессом `design` (узел `approve` с согласованием), дойти до вопроса Q-N.
2. Ответить «Нужны правки: …».
3. Пока идёт `rework`, сравнить подпись PR (`prs[].note`) с `list_owner_questions`:
   подпись «Жду решения владельца (вопрос Q-N)», список пуст.
4. После сдачи `rework` подпись меняется на новый Q-(N+1) — само рассасывается.

## Предложение починки

1. В `gate` после `whenQuestionClosed` сразу менять подпись PR на итог («Владелец
   согласовал Q-N» / «Владелец попросил правки Q-N — доработка»). Такая заготовка
   (`gateClosedNote`) уже есть в ветке `task/T-355`.
2. Агентским узлам (`rework`, `step`) при старте ставить свою подпись («Доработка
   по отзыву: <роль>»), чтобы подпись PR всегда описывала текущий узел.
3. В `get_board`/`list_owner_questions` для задач в `review` показывать менеджеру
   `run.waitingOn` и статус этого вопроса, а не текст подписи PR: менеджер должен
   опираться на прогон, а не на подпись.
4. Сверку при старте (`repairGateWaits` из `task/T-355`) оставить как страховку от
   ожидания удалённого или влитого в никуда вопроса. Сейчас такого в данных нет,
   поэтому это вторично.
5. Ветку `task/T-355` (отменена) использовать как основу только для п.1 и п.4;
   перевод «вопрос удалён» в `STUCK` с `needsDecision` вынести отдельно, он к
   этому симптому не относится.

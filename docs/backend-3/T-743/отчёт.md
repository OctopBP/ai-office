# T-743 — адресное повышение предохранителя

Дата: 31 октября 2026 года. Статус: операционная настройка заблокирована доступом; лимиты не изменены.

## Подтверждённые результаты

- `sandbox_status` в текущей сессии дважды подтвердил: «Локальные порты: закрыты», собственных правил сетевых хостов нет. HTTP/WebSocket API работающего офиса недоступен по политике; попыток обхода не выполнялось.
- Создан стандартный запрос доступа **Q-268** для backend-3: `allowedHosts: ["localhost", "127.0.0.1"]`, без дополнительных путей записи. Согласие применяется только со следующей сессии роли. Само согласие ещё не подтверждает рабочую связь: после него нужно заново проверить `sandbox_status` и успешный ответ API.
- Сохранённый прежний и текущий `reviewer.spendFuseTokens`: **не прочитан, не подтверждён**. Новое значение **не установлено**. Цель — минимум **2 000 000**, с сохранением более высокого явного значения.
- Фактическая роль, исполнявшая verify T-726: **не установлена**, поскольку история запусков через API недоступна. Автор задачи не использовался как основание. Прежний и текущий явные лимиты этой роли **не подтверждены**, новое значение **не установлено**. Цель — минимум **3 000 000**, с сохранением более высокого явного значения.
- Из задания известны срабатывания: T-741 — расход 209 000 при пороге 200 000; verify T-726 — расход 2 238 000 при историческом пороге 2 195 000. Это сведения задания, а не прочитанные через API явные настройки роли.

## Продолжение после предоставления доступа

1. В новой сессии backend-3 подтвердить доступ к работающему локальному серверу и выбрать офис `o-2`. Порт 3001 — только умолчание исходного кода; фактический адрес необходимо подтвердить. Не запускать другой сервер и не перезапускать живой.
2. Через штатный API прочитать текущие роли и историю запусков T-726. Зафиксировать `roleId` именно запуска узла verify с указанным срабатыванием, а не автора задачи или предполагаемую роль из workflow.
3. Сохранить прежние явные значения. Штатная команда WebSocket: `{"c":"update_role","roleId":"reviewer","patch":{"spendFuseTokens":2000000}}`. Отправить её только если явного значения не ниже целевого ещё нет. Для установленной роли verify аналогично задать 3 000 000. Если verify исполнял reviewer, установить reviewer сразу минимум 3 000 000. Более высокие значения не понижать.
4. Дождаться `role.saved` (ошибка приходит как `role.error`), затем повторным чтением API, предпочтительно новым подключением и снимком офиса, подтвердить сохранённые явные значения. Зафиксировать прежние и новые значения в этом отчёте. Один ответ об успешном сохранении не заменяет контрольное чтение.
5. Новая сессия агента получит сохранённый порог: `src/server/agents.ts:4286–4298` берёт `Role.spendFuseTokens` из снимка роли при старте запуска. Изменение настройки не меняет порог уже идущей сессии.
6. Только после подтверждения настроек PM возобновляет T-741/T-726 через штатный `retry_review`. T-741/T-742 проходят обязательные проверки и штатное слияние; их ветки нельзя применять к серверу до этого. Дальнейшее продолжение зависимых T-724/T-730/T-735/T-737 выполняет PM с учётом устранения причины Compact и штатных зависимостей.
